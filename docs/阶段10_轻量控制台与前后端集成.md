# Z-Torque 社区版阶段 10：轻量控制台与前后端集成

**文档编号：** ZT-COMMUNITY-P10  
**文档版本：** 1.1（P1/P2 优化）  
**阶段名称：** 轻量控制台与前后端集成  
**前置阶段：** 阶段 0～9  
**阶段状态：** 待实施  
**前端技术栈：** React 18 + TypeScript + Vite + React Router（与阶段 0 一致）  
**错误展示：** 前端必须根据统一响应中的 `code` 和 Task 状态判断错误，不得解析 `message` 文本。SSE 中断不得直接判定 Task 失败，重连后应按事件序号和服务端状态恢复。

## 父子任务展示（本阶段必须实现）

在现有 Chat/Session 和任务展示区域增加轻量层级展示，不新增工作流编辑器。未选择 Agent 时显示默认父 Agent；发生委派时显示父 Task、子 Agent 及其 AgentVersion、子任务状态、进度、结果摘要和必要错误。用户只能查看自己有权访问的 Task、结果和审计信息。

复用现有 Task 查询和 SSE 机制，事件增加 `root_task_id`、`parent_task_id`、`delegation_depth` 和子任务摘要字段。取消父 Task 的操作应明确展示取消传播语义；前端不得自行推断终态或绕过服务端权限。

对于串行委派，界面应能显示子任务顺序、前置任务、等待原因和结果传递状态。例如先显示“数据获取 Agent”成功，再显示“数据分析 Agent”排队或运行，最后显示父 Agent 汇总输出。结果展示只显示当前用户有权查看的摘要或引用，不默认展示完整原始数据和子 Agent 中间推理。

## 1. 阶段目标

### 1.1 核心目标

在前面各阶段已实现的后端能力基础上，开发 Z-Torque 社区版轻量控制台，完成前后端 API 集成，让用户可以通过浏览器完成主要业务操作。

本阶段的重点不是重新开发内核，而是将已有能力组织成可使用、可观察、可管理的产品界面。

需要完成：

1. 建立前端工程和统一页面布局。
2. 实现登录、退出和用户权限相关交互。
3. 实现 Chat 对话、文件上传、Task 实时执行过程展示。
4. 实现 Agent、Skill、模型、Connector、Audit 五类管理页面。
5. 统一 API 请求、错误处理、SSE 连接和权限提示。
6. 验证前后端完整业务链路。

### 1.2 阶段完成标准

用户可以登录控制台，选择一个有权限使用的 Agent，发起对话；普通聊天直接返回消息，需要执行 Skill 时创建 Task，并实时展示执行状态、工具调用、人工确认和最终结果。

同时，用户可以根据权限管理或查看相应的 Agent、Skill、模型、Connector 和审计记录。

**本阶段的核心验收链路：**

登录 → 选择 Agent → 发起对话 → 模型回复或创建 Task → 实时查看执行过程 → 展示结果 → 查看审计记录。

## 2. 需求范围

### 2.1 页面范围

社区版采用轻量控制台，不开发复杂的可视化编排器。主要导航包含以下六个页面。

| 页面        | 核心职责               | 主要功能                                        |
| ----------- | ---------------------- | ----------------------------------------------- |
| Chat / 会话 | 面向用户的主要交互入口 | Agent 选择、对话、文件附件、Task 过程、结果展示 |
| Agent       | 管理智能体             | 列表、详情、创建、编辑、复制、发布、归档        |
| Skill       | 管理能力包             | 列表、详情、版本、复制、启停及关联 Tool 查看    |
| Model       | 管理模型资源           | Provider、Model、Endpoint 配置与连接测试        |
| Connector   | 管理外部连接           | REST、只读数据库、MCP 连接配置及状态            |
| Audit       | 查看审计事件           | 查询、筛选、详情、执行链路追踪                  |

Task 详情不单独设置为一级导航，优先集成在 Chat 的执行过程面板中。文件上传和附件状态也集成在 Chat 中。

### 2.2 登录与权限

- 用户通过用户名和密码登录。
- 浏览器使用 HttpOnly Cookie 传递认证信息。
- 提供登录状态恢复、退出登录和认证过期处理。
- 根据用户权限显示可访问的页面和操作按钮。
- 无权限时展示明确提示，不通过隐藏按钮代替后端权限校验。
- 登录连续失败 5 次后锁定 15 分钟，具体执行由后端负责。
- 前端不保存明文密码、模型密钥或 Connector 敏感凭证。

### 2.3 Chat 与 Task

Chat 页面需要支持：

- Agent 选择与会话列表。
- 创建会话、加载历史消息和继续对话。
- 发送消息、接收流式回复。
- 上传和展示文件附件。
- 区分普通聊天与 Task 执行。
- 展示 Task 状态、执行步骤、工具调用摘要和执行结果。
- 支持人工确认、拒绝和取消 Task。
- 网络断开后重新连接，并恢复必要的执行状态。
- 防止用户重复点击发送造成重复请求。

普通聊天与 Task 执行必须使用不同的流式事件处理逻辑，不能混为一套事件协议。

### 2.4 Agent 管理

Agent 页面需要支持：

- 查看当前用户有权访问的 Agent。
- 区分官方资源与用户自有资源。
- 查看 Agent 的当前发布版本。
- 创建个人 Agent、复制官方 Agent。
- 编辑草稿、发布版本、归档个人 Agent。
- 配置 Agent 基本信息、规则、模型绑定和 Skill 绑定。
- 展示每个 Skill 对应的准确版本。
- 查看相关权限和配置错误。

约束：

- 官方 Agent 不允许直接修改或删除。
- 修改官方 Agent 前必须复制到个人资源空间。
- 发布后生成不可变的 Agent Version 快照。
- 已创建的 Task 固定使用创建时选定的 Agent Version。
- Agent 只能绑定 Skill Version，不直接绑定 Tool。

### 2.5 Skill 管理

Skill 页面需要支持：

- 查看有权访问的 Skill。
- 区分官方 Skill 与个人 Skill。
- 查看 Skill 描述、版本、状态、权限要求和关联 Tool。
- 创建个人 Skill、复制官方 Skill。
- 编辑草稿和发布新版本。
- 展示 MD-Skill 的纯指令模式与脚本执行模式。
- 查看 Tool 的版本及执行能力描述。

约束：

- 官方 Skill 不允许直接修改或删除。
- Skill Version 必须绑定明确的 Tool Version。
- 已发布版本不能被原地修改。
- 所有 Tool 执行必须经过后端 SkillGateway。
- 前端不能直接执行脚本，也不能绕过 SkillGateway 调用外部能力。

### 2.6 模型管理

Model 页面需要支持：

- 查看 Provider、Model 和 Endpoint。
- 创建、编辑、启用或停用模型配置。
- 配置模型名称、接口地址、模型标识及必要参数。
- 通过 Secret URI 关联 API Key 等敏感信息。
- 测试模型连接并展示结果。
- 查看模型可用状态和最近错误摘要。

安全约束：

- API 不返回模型密钥明文。
- 页面仅展示密钥是否已配置、Secret URI 或经过脱敏的信息。
- 更换密钥应通过专用的安全配置流程完成。
- 模型调用仍然由后端 ModelGateway 统一执行。

### 2.7 Connector 管理

Connector 页面需要支持：

- 创建、查看、编辑和停用连接配置。
- 支持 REST API、只读数据库和 MCP。
- 支持 API Key/Bearer、Basic Auth，以及管理员明确允许的匿名连接。
- MCP 支持 stdio 和 HTTP 传输。
- MCP 使用 JSON-RPC 2.0，并支持 `tools/list` 和 `tools/call`。
- 展示连接状态、健康检查结果和可用能力摘要。
- 支持测试连接。
- 普通用户可提交连接访问申请，连接配置由管理员管理。

安全约束：

- 数据库连接必须限制为只读。
- 数据库访问必须配置允许访问的表和查询限制。
- Connector 目标地址、传输方式、认证模式和超时必须接受后端策略校验。
- 生产配置默认拒绝不安全的连接配置。
- 敏感环境变量只允许引用 Secret URI，不得明文写入普通配置。
- 前端不得绕过 Connector 和 SkillGateway 直接访问目标系统。

### 2.8 Audit 页面

Audit 页面需要支持：

- 按时间、事件类型、执行用户、Agent、Task 等条件筛选。
- 查看登录、权限判断、Task 状态变化、模型调用、Skill 执行和配置变更等事件。
- 查看事件发生时间、执行主体、资源标识、结果、耗时和关联 Trace ID。
- 从 Task 或审计事件进入相关执行记录。
- 展示脱敏后的参数摘要和错误摘要。

审计数据必须由后端写入。前端只提供查询和展示能力，不能提供关闭审计、修改历史审计记录或删除审计记录的功能。

### 2.9 本阶段不做的内容

- 可视化 Workflow 编排器。
- 完整知识库管理产品。
- 独立的长期记忆管理页面。
- 企业多租户管理、SSO 和企业级组织架构。
- 复杂审批流程设计器。
- 前端直接执行代码或访问数据库。
- 前端自行维护一套独立权限规则。
- 与内核无关的复杂大屏和运营分析系统。

## 3. 技术方案

### 3.1 前端技术栈

默认采用 React 18 + TypeScript + Vite。

| 技术                                    | 用途                               |
| --------------------------------------- | ---------------------------------- |
| React 18                                   | 页面组件与交互                     |
| TypeScript                              | API 类型、业务对象和状态类型约束   |
| Vite                                    | 前端开发服务器与生产构建           |
| React Router                              | 页面路由和导航                     |
| Zustand                                   | 用户认证、全局状态及必要的共享状态 |
| Axios 或统一 Fetch 封装                 | 普通 HTTP API 请求                 |
| 原生 Fetch ReadableStream 或 SSE 客户端 | Chat 与 Task 流式接收              |
| 现有项目 UI 组件库                      | 表格、表单、弹窗、通知、导航等     |

如果现有仓库已经确定使用其他前端框架，应优先沿用已有技术决策，不要为了本阶段重建工程。

### 3.2 前端模块划分

按职责划分页面、组件和服务，避免所有逻辑堆在单个组件文件中。

建议模块：

- `layouts`：整体布局、侧边栏、顶部栏。
- `views`：六个主要业务页面。
- `components`：对话框、状态标签、表格、附件卡片、执行过程面板等。
- `services`：统一 API 请求、认证、SSE、文件上传。
- `stores`：认证状态、用户信息及必要的共享状态。
- `router`：页面路由和基础路由守卫。
- `types`：API 请求、响应和业务实体类型。
- `utils`：错误映射、时间格式化、脱敏展示等工具。

目录结构是职责建议，不要求机械照搬；应结合现有仓库组织方式实现。

### 3.3 前后端交互原则

1. 前端所有业务数据都通过后端 API 获取。
2. 前端不得直接连接业务数据库。
3. 前端不实现模型推理、Tool 执行或 Skill 执行。
4. 前端只负责发起请求、展示状态、收集用户输入。
5. 后端始终是身份、权限、状态机和业务规则的权威来源。
6. 页面显示的执行状态以服务端状态为准。
7. 所有错误信息使用统一格式，并尽可能携带 Trace ID。
8. 对于重复提交、断线重连和超时，采用明确的恢复策略。

### 3.4 统一 API 请求层

建立统一请求封装，集中处理：

- API 基础地址。
- Cookie 认证及必要的 CSRF 防护。
- JSON 请求和响应。
- 文件上传及上传进度。
- 认证失效处理。
- 统一错误解析。
- Trace ID 展示和排查。
- 请求取消。
- `Idempotency-Key` 等幂等请求头。

业务页面不得各自重复实现一套认证、错误处理和请求基础配置。

统一错误结构沿用后端约定：

```
{ code, message, data, trace_id }
```

`code` 用于程序判断，`message` 用于用户提示，`trace_id` 用于问题排查。不要把原始堆栈、密钥或敏感请求参数直接展示给用户。

### 3.5 Chat 流式处理

普通聊天使用 Chat Stream，处理：

- `message.delta`
- `message.result`
- `message.done`

当对话需要执行 Skill 并创建 Task 时，后端返回 `task_id`，前端转入 Task Stream。

Task Stream 处理：

- `task.snapshot`
- `task.status`
- `task.delta`
- `task.tool_call`
- `task.tool_result`
- `task.waiting_human`
- `task.human_decision`
- `task.result`
- `task.error`
- `task.done`

具体事件名称和载荷结构必须与后端实际实现的 API 契约一致。若此前各阶段的事件命名与本文件存在差异，应先对齐契约，再进行前端开发，不要在前端自行创造第三套事件协议。

### 3.6 SSE 连接与恢复

前端需要考虑：

- 正常连接与流式增量展示。
- 用户主动停止当前输出。
- 网络中断、服务器断开和重新连接。
- 页面刷新后的 Task 状态恢复。
- 使用 `Last-Event-ID` 恢复可重放的事件。
- 已收到的事件不能因为重连而重复展示。
- Task 已结束时停止继续监听。
- 页面切换后合理清理不再需要的连接。

注意：浏览器原生 `EventSource` 对请求方法、请求头和认证的控制存在限制。如果后端需要 POST 建立流式请求、传递自定义请求头或配合特定认证方式，可使用 Fetch 流式读取或经过验证的 SSE 客户端实现。

断线恢复依赖后端提供可靠的事件序号和重放机制。前端不能单方面保证事件不会丢失。

### 3.7 Task 执行过程展示

采用简化执行过程面板，不向普通用户暴露全部底层实现细节。

建议展示：

1. 正在理解需求。
2. 正在执行某项能力。
3. 工具调用摘要。
4. 工具执行成功或失败。
5. 等待用户确认。
6. 正在整理结果。
7. 最终结果或失败原因。

这些阶段是前端展示层的解释性文案，应尽可能映射到真实服务端事件；不能为了视觉效果虚构已经发生的执行行为。

对于工具参数和返回值，只展示经过后端脱敏、裁剪后的摘要。

### 3.8 文件与附件交互

Chat 页面需要支持附件选择、上传状态和附件展示。

支持的文件类型：

- PDF、TXT、MD。
- CSV、XLSX。
- 图片。
- 音频。

默认上传上限为 50 MB，可通过后端配置调整。

前端需要处理文件类型提示、大小校验、上传中、上传成功、上传失败、移除未提交附件等状态。

前端校验仅用于改善用户体验。文件大小、扩展名、真实格式、用户权限和文件内容安全必须由后端重新验证。附件内容一律作为不可信输入处理。

### 3.9 权限和安全设计

前端权限主要用于改善操作体验，不作为安全边界。

- 未登录用户跳转登录页。
- 已登录用户访问无权限页面时展示无权限提示。
- 无权执行的操作不展示或禁用相应按钮。
- 对重要操作提供确认弹窗。
- 不允许在浏览器持久化模型密钥或 Connector 凭证。
- 不允许通过前端参数伪造用户身份或权限。
- 不允许前端直接执行任意脚本。
- 文件下载、会话查询和 Task 查询都必须经过后端权限检查。

后端仍然必须对每次 API 请求、每次资源读取和每次 Skill 执行进行授权判断。

### 3.10 页面交互与设计原则

控制台优先保证清晰、可理解和可操作。

- 采用统一导航、页面标题、操作区和内容区。
- 列表页支持必要的搜索、筛选、分页和状态展示。
- 表单按业务分组，避免一次展示过多底层配置。
- 对高级参数提供折叠区域或说明提示。
- 官方资源与个人资源具有清晰区分。
- 加载中、空数据、无权限、请求失败和操作成功均有明确反馈。
- 删除、归档、发布、取消 Task 等重要操作必须有合适的交互反馈。
- 不以复杂动画或大屏展示替代实际业务能力。

## 4. 接口与数据设计

### 4.1 API 基础约定

统一使用：

```
/api/z-torque/*
```

不强制把 `/v1` 放入 URL 路径。接口版本、兼容策略和字段变更规则由 API 契约管理。

前端开发前，应整理已有后端路由和响应结构，建立接口清单。以下路径是需要核对的接口范围，不代表后端尚未实现的接口可以直接假定存在。

### 4.2 接口范围

| 业务模块     | 接口范围                        | 主要用途                             |
| ------------ | ------------------------------- | ------------------------------------ |
| 认证         | `/api/z-torque/auth/*`          | 登录、退出、当前用户、刷新或续期     |
| Chat         | `/api/z-torque/chat/*`          | 发送消息、获取普通聊天流             |
| Conversation | `/api/z-torque/conversations/*` | 创建会话、查询会话、加载消息         |
| Task         | `/api/z-torque/tasks/*`         | 查询状态、取消、人工确认、执行流     |
| File         | `/api/z-torque/files/*`         | 上传、查询附件元数据、授权下载       |
| Agent        | `/api/z-torque/agents/*`        | 列表、详情、草稿、发布、复制、归档   |
| Skill        | `/api/z-torque/skills/*`        | 列表、详情、版本、复制和发布         |
| Model        | `/api/z-torque/models/*`        | Provider、Model、Endpoint 配置及测试 |
| Connector    | `/api/z-torque/connectors/*`    | 连接配置、健康状态、访问申请         |
| Audit        | `/api/z-torque/audit/*`         | 查询审计事件及详情                   |

每个模块都应核对请求方法、参数、响应体、错误码、权限要求和幂等要求。实际路由命名以已经冻结的后端 API 契约为准。

### 4.3 Chat 请求与响应

发送消息至少需要明确：

- `agent_id`
- `conversation_id`，允许按约定为空并由服务端创建会话
- `message`
- `file_ids`，没有附件时为空列表或按契约省略
- 幂等请求标识

请求结果应能区分普通聊天和 Task 执行两类情况。

普通聊天：建立 Chat Stream，持续接收消息增量。

Task 执行：获得 `task_id` 后连接对应 Task Stream。

前端不得根据模型回复文本猜测是否创建了 Task，应根据后端明确返回的响应类型判断。

### 4.4 Agent 与 Skill 数据展示

Agent 页面至少需要使用：

- Agent ID、名称、描述。
- 资源来源与所有者。
- 草稿、已发布或已归档状态。
- 当前发布版本。
- 已绑定 Skill Version 列表。
- 创建时间和更新时间。

Skill 页面至少需要使用：

- Skill ID、名称、描述。
- 资源来源与所有者。
- 实现类型。
- 版本与发布状态。
- 关联 Tool Version 列表。
- 所需权限摘要。

前端不自行拼接或推断版本关系。Agent Version 与 Skill Version 的绑定关系由后端返回并校验。

### 4.5 模型与 Connector 数据展示

模型页面展示非敏感配置和运行状态。密钥只能通过 Secret URI 进行引用，API 不得返回明文密钥。

Connector 页面展示连接类型、传输方式、认证模式、目标摘要、健康状态和允许的能力。敏感配置不得进入前端日志、浏览器持久化存储或错误上报。

### 4.6 Audit 数据展示

审计列表应支持分页，并优先使用服务端筛选。

展示字段至少包括：

- 事件 ID。
- 事件类型。
- 时间。
- 执行主体。
- 资源类型与资源 ID。
- 执行结果。
- Trace ID。
- 脱敏后的摘要。

详情页只能展示后端允许返回的内容。前端不得自行请求数据库、对象存储或内部路径获取完整原始载荷。

### 4.7 前端类型定义

为关键 API 响应建立 TypeScript 类型，至少覆盖：

- User / Permission。
- Conversation / Message。
- ChatResponse。
- Task / TaskEvent。
- Agent / AgentVersion。
- Skill / SkillVersion / Tool。
- ModelProvider / Model / ModelEndpoint。
- Connector。
- AuditEvent。
- FileMetadata。
- ApiError。

类型定义应与实际后端 API 契约保持一致。若后端使用 Pydantic 模型作为契约来源，应优先通过明确的契约导出或人工校验保持一致，避免前后端分别维护出互相矛盾的字段。

### 4.8 API 契约管理

前端开发开始前，建立一份 API 对照清单，逐项记录：

- 接口路径与方法。
- 请求参数。
- 响应结构。
- 错误码。
- 身份认证要求。
- 权限要求。
- 是否支持幂等。
- 是否支持流式响应和断线恢复。
- 当前实现状态。

接口未实现时，应标记为待开发，不能用静态模拟数据冒充真实功能已经完成。

## 6. 测试验收

### 6.1 页面基础验收

- 所有页面可以正常加载。
- 页面刷新后路由可恢复。
- 加载中、无数据、请求失败和无权限状态清晰。
- 表单具备必要的校验与提交状态。
- 重要操作具有明确的成功或失败反馈。
- 浏览器控制台无持续性未处理异常。

### 6.2 登录与权限验收

- 正确账号能够登录。
- 错误密码得到明确提示。
- 连续失败 5 次后的 15 分钟锁定由后端生效。
- 退出登录后受保护接口无法继续访问。
- Cookie 认证和 CSRF 防护符合后端设计。
- 普通用户不能通过手工构造请求越权读取其他用户的会话、文件或 Task。
- 隐藏按钮后，直接调用后端接口仍然会被正确授权检查拦截。

### 6.3 Chat 与 Task 验收

- 普通聊天不应无故创建 Task。
- 需要执行 Skill 时，前端根据后端响应进入 Task 流程。
- 普通聊天和 Task 使用正确的流式事件协议。
- Task 状态、工具调用摘要和最终结果展示正确。
- 重复点击或网络重试不会导致同一用户请求重复创建执行任务。
- 人工确认和拒绝行为与后端状态机一致。
- 用户取消 Task 后，界面能够展示取消过程和最终状态。
- 页面刷新后能够恢复必要的会话和 Task 信息。
- SSE 重连后不会重复展示同一事件。

### 6.4 Agent 与 Skill 验收

- 官方资源可查看但不能直接修改或删除。
- 复制后的个人资源可以独立编辑。
- Agent 发布后形成新的不可变版本。
- 已创建 Task 仍然引用创建时固定的 Agent Version。
- Agent 绑定 Skill Version，Skill 绑定 Tool Version。
- 无权限的 Skill 和 Tool 无法通过前端或直接 API 调用。

### 6.5 Model 与 Connector 验收

- 模型配置和连接测试正常。
- 密钥不会出现在 API 响应、页面明文、浏览器存储或前端日志中。
- 数据库 Connector 只能执行允许的只读操作。
- 未经允许的目标地址或连接配置被后端拒绝。
- MCP 的工具发现和调用状态展示与服务端结果一致。
- 连接失败时给出可理解的错误信息，不暴露敏感配置。

### 6.6 Audit 验收

- 登录、Task、模型调用、Skill 执行和配置变更等事件能够查询。
- 审计事件可关联相关 Task 或 Trace ID。
- 敏感字段已脱敏。
- 用户不能通过控制台关闭审计或修改历史记录。

### 6.7 端到端验收

至少完成以下链路：

1. 登录并选择一个有权限的 Agent。
2. 发起普通聊天，接收完整回复。
3. 继续提出需要执行 Skill 的请求，创建 Task。
4. 实时查看 Task 状态和执行过程。
5. 验证工具失败时的错误展示。
6. 验证需要人工确认时能够确认或拒绝。
7. 上传支持的文件并在会话中使用。
8. 查看相关审计事件。
9. 使用另一个用户验证会话和文件隔离。
10. 刷新页面或模拟网络中断，验证恢复能力。

只有真实后端链路通过验收，才可以标记功能完成。静态页面、Mock 数据和仅能打开的按钮不算业务验收通过。

## 7. 风险项

| 风险                        | 可能影响                    | 处理措施                                   |
| --------------------------- | --------------------------- | ------------------------------------------ |
| 前后端 API 契约不一致       | 页面无法正常工作            | 先核对接口清单，统一字段和错误码           |
| Chat 与 Task 流式协议混用   | 消息错乱、状态无法恢复      | 分离事件处理逻辑，统一事件契约             |
| SSE 重连造成事件重复        | 重复展示状态或结果          | 使用事件 ID、序号和前端去重                |
| 前端被误当成权限边界        | 越权访问资源                | 后端对每次资源读取和执行重新授权           |
| 页面逻辑过度集中            | 难以维护和测试              | 按页面、组件、服务、状态划分职责           |
| 模型密钥泄露                | 连接凭证暴露                | Secret URI、服务端脱敏、禁止前端持久化     |
| MCP 或 Connector 配置不安全 | 未授权访问外部系统          | 后端实施目标白名单、认证和权限校验         |
| 文件被当作可信指令          | Prompt Injection 或越权执行 | 文件内容作为不可信输入，服务端执行授权检查 |
| 长会话导致页面卡顿          | 消息列表性能下降            | 合理分页、分段渲染，避免重复全量刷新       |
| 后端能力尚未完成            | 页面只能使用 Mock           | 明确标注未完成接口，不伪造真实运行状态     |

## 9. 阶段总结

阶段 10 的交付目标，是将 Z-Torque 社区版前面构建的运行时能力整合成一个可操作、可观察、可管理的产品界面。

完成后，用户应当能够通过控制台完成：

- 对话和会话管理。
- Agent 与 Skill 的基础管理。
- 模型与外部连接管理。
- Task 实时执行过程查看。
- 文件附件使用。
- 审计记录查询。

本阶段仍然坚持 Z-Torque 的核心边界：

1. 前端负责交互，内核负责执行治理。
2. 用户身份和权限必须贯穿整个执行链。
3. Agent、Skill、Tool 的版本关系必须可追溯。
4. 所有 Tool 执行必须经过 SkillGateway。
5. Task 状态与执行结果以服务端为准。
6. 审计不可关闭，敏感数据必须脱敏。
7. 控制台是产品的一个入口，不能成为内核的强依赖。

**阶段完成后，Z-Torque 将拥有从后端运行时到用户控制台的完整基础链路。** 后续应优先进行全链路稳定性、安全性和部署验证，再考虑知识库产品化、插件扩展或企业版能力。

下一阶段建议进入：**阶段 11——全链路集成测试、安全加固与社区版发布验收**。
