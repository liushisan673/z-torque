# Z-Torque Windows 能力降级与沙箱边界

本文记录 Windows 桌面版的执行边界。能力声明必须与运行时行为一致；任何不满足安全前置条件的执行均采用 fail-closed，不得静默放宽权限或伪装成完整隔离。

## 能力状态

- `AI_CAPABILITY_UNAVAILABLE`：当前运行环境不具备请求的能力时返回此错误，不将不可用能力伪装为成功。
- `AI_SKILL_WINDOWS_UNTRUSTED`：Windows 下脚本 Skill 未被标记为可信时拒绝执行。
- `untrusted_execution`：不可信脚本不得直接进入宿主进程执行。
- `full_requires_container`：完整隔离模式必须依赖受支持的容器运行环境；不支持容器时不得降级为普通进程。
- `windows_requires_trusted`：Windows 进程模式要求 Skill 明确标记为可信。
- `windows_requires_confirmation`：Windows 脚本执行必须经过服务端人工确认。
- `fail-closed`：配置缺失、能力探测失败、审批信息不匹配或隔离边界无法保证时，拒绝执行。

## Windows 进程模式的实际边界

Windows 的受限进程模式不是完整操作系统沙箱。它不能等同于 Linux 容器的网络隔离、只读根文件系统、capability 丢弃或完整资源控制。产品界面和 API 不得宣称其提供上述能力。

脚本执行必须经过统一 Skill Gateway、服务端审批和运行时二次校验。审批恢复时应校验 Skill 版本、脚本入口、文件指纹、原始参数及 SandboxScope；任一项变化都拒绝恢复执行。

## 容器模式

容器模式仅在运行环境支持且经过能力探测时启用。完整隔离模式必须使用容器；容器不可用时返回能力不可用错误，不回退到宿主进程。

容器应采用无网络、只读根文件系统、no-new-privileges、丢弃不必要 capabilities、资源限制及非特权 UID/GID 等纵深防护。实际可用能力以运行时探测结果为准。

## 审批与审计

- 所有需要确认的脚本执行必须先挂起 Task 并保存 Checkpoint。
- 审批通过后从原 Checkpoint 恢复，不重新执行此前已完成的步骤。
- 审批人与发起人关系遵循产品当前单机单用户策略；权限判断由服务端执行。
- 执行请求、审批决定、恢复结果和失败原因均应留下可追溯审计记录。
- 审批拒绝、超时、指纹变化或权限变化时不得执行脚本。

## 桌面版使用建议

桌面版默认使用本机 SQLite 和用户数据目录。用户数据、密钥和运行日志不得写入安装包目录。打包自检只验证随包资源及已启用能力的必要配置；未配置的可选联网能力应明确显示为未启用，不得阻止本地知识库和普通 Agent 使用。
