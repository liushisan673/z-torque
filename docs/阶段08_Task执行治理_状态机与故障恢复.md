## 父子 Task 执行治理（本阶段必须完成）

父 Task 是用户请求对应的唯一根 Task；子 Task 是父 Task 通过受控委派创建的内部执行单元。子 Task 必须记录 `parent_task_id`、`root_task_id`、`delegation_depth=1`、子 AgentVersion 快照、委派序号、必要性和幂等键，并沿用现有状态机、Outbox、Worker、取消、超时和恢复机制。

### 资源与限制（使用阶段 0 配置默认值）

| 限制项 | 配置来源 | 默认参考 |
|:---|:---|:---|
| 最大子任务数 | `delegation.max_children_per_root` | 5 |
| 最大并发数 | `delegation.max_concurrency` | 3 |
| 总时间预算 | `delegation.max_total_timeout_seconds` | 600s |
| 单子任务超时 | `delegation.default_child_timeout_seconds` | 120s |
| 最大轮次 | `delegation.max_rounds_per_child` | 20 |
| 最大深度 | `delegation.max_depth` | 1（强制） |

父 Agent 仅能调用其 AgentVersion 白名单中的已发布子 AgentVersion。子 Agent 创建请求一律拒绝继续派生子 Task，循环、跨根和重复委派一律拒绝。

父 Task 必须跟踪子 Task 状态、结果摘要和错误摘要。必要子任务失败、超时或版本不可用时，父 Task 按失败策略终止或受控降级；非必要子任务允许部分成功后汇总。父 Task 取消时传播取消到未完成子 Task；服务重启后恢复未终态任务，但外部副作用不确定时不得无条件重放。

子 Task 可以在同一根 Task 内形成由父 Agent 控制的串行执行顺序，但不能形成新的委派层级。每个子 Task 应记录前置子 Task 引用或 `depends_on_task_ids`；只有前置任务达到允许的成功状态、结果通过结构化校验且预算仍然可用时，父 Agent 才能创建后续子 Task。后续子 Task 的输入应优先使用受权限保护的结果引用，避免把大体量数据无条件复制到模型上下文。

以“分析三月份销售数据”为例，数据获取子 Task 和数据分析子 Task 都直接归属于同一个根 Task：数据获取成功后，父 Agent 将经校验的数据引用传给分析子 Task，分析完成后再由父 Agent 统一汇总和标准化输出。禁止数据获取子 Agent 直接创建分析子 Task。

父子任务事件使用同一 `root_task_id` 和审计关联标识，分别记录创建、排队、运行、成功、失败、超时、取消、重试和汇总事件。Task 查询及 SSE 事件必须携带层级关系和子任务摘要，但不得泄露无权查看的子任务内容。

## 1. 阶段目标

本阶段完善 Z-Torque 的任务执行内核，将模型调用、SkillGateway、Tool 执行、人工确认、任务取消和服务重启恢复统一到可追踪的 Task 生命周期中。

完成后，系统应具备以下能力：

1. 统一管理 Task 状态及合法状态转换。
2. 将任务创建、事件记录与 Outbox 投递纳入可靠的事务边界。
3. 通过 Worker 执行任务，限制并发并处理异常。
4. 支持任务取消，并向模型调用、SkillGateway 和可取消的 Tool 传播取消信号。
5. 支持任务等待人工确认、继续执行或取消。
6. 通过 TaskEvent 记录执行过程，并支持 SSE 实时推送和断线恢复。
7. 支持幂等请求、失败处理、超时处理及服务重启恢复。
8. 保证身份、权限、AgentVersion 快照和审计记录贯穿任务全生命周期。

本阶段必须遵守六项内核不变量：

- **身份与会话**：SecurityContext 必须从 API 入口贯穿 Task、Worker、Skill 和外部调用。
- **任务状态机与事务边界**：只允许合法状态转换，终态不可变，Outbox 与任务创建保持事务一致。
- **AgentVersion 快照**：任务执行期间固定使用创建任务时确定的 AgentVersion。
- **审计事件流**：审计记录不可关闭，关键操作必须可追溯。
- **权限决策点**：权限检查在内核执行边界完成，不能依赖模型自觉遵守。
- **双 Gateway**：模型调用经过 ModelGateway，技能与 Tool 调用经过 SkillGateway。

## 3. 技术方案

### 3.1 Task 状态机

建议使用以下状态：

| 状态            | 含义                               | 是否终态 |
| --------------- | ---------------------------------- | -------- |
| `PENDING`       | 任务已创建，尚未完成调度           | 否       |
| `QUEUED`        | 任务已进入可执行队列               | 否       |
| `RUNNING`       | Worker 正在执行                    | 否       |
| `WAITING_HUMAN` | 等待用户或授权人员确认             | 否       |
| `CANCELING`     | 正在传播取消信号、等待执行单元停止 | 否       |
| `SUCCESS`       | 任务成功完成                       | 是       |
| `FAILED`        | 任务执行失败                       | 是       |
| `TIMEOUT`       | 任务超过允许执行时间               | 是       |
| `CANCELLED`     | 任务已取消                         | 是       |

合法转换应集中定义，不允许业务代码任意修改状态。

```
PENDING → QUEUED → RUNNING → SUCCESS
                         ├→ FAILED
                         ├→ TIMEOUT
                         ├→ WAITING_HUMAN
                         └→ CANCELING → CANCELLED

WAITING_HUMAN → RUNNING       （批准）
WAITING_HUMAN → CANCELLED     （拒绝或取消）
WAITING_HUMAN → TIMEOUT       （确认超时）

PENDING → CANCELLED
QUEUED  → CANCELLED
```

补充规则：

- 如果任务拒绝人工确认后仍需要返回解释，应由系统生成相应的用户可见结果，并按照既定业务语义结束任务。
- `CANCELING` 不能立即等同于 `CANCELLED`。只有在可取消的执行单元确认停止，或系统按已定义的取消策略完成收敛后，才能进入最终取消状态。
- 如果外部请求无法中断，应记录其实际状态，防止任务被错误地报告为“已停止”，同时继续执行必要的清理和审计。
- 终态不可修改为其他状态。需要重新执行时，应创建新的 Task，并关联原任务作为来源。
- 所有状态变更必须通过统一的状态转换函数完成。

### 3.2 Task 创建与事务边界

Task 创建必须保证任务记录、初始事件和待投递事件不会出现不一致。

建议流程：

1. 接收 Chat 层提交的任务请求。
2. 校验用户身份、Agent 可用状态及请求幂等键。
3. 固定本次任务使用的 AgentVersion。
4. 在同一个数据库事务中写入 Task、初始 TaskEvent 和 Outbox。
5. 提交事务。
6. 由调度器发现待处理 Outbox。
7. 将任务投递到进程内队列，并更新投递状态。
8. Worker 领取任务后，执行合法的状态转换。

**关键原则：先持久化，再投递。** 不能只把任务放进 `asyncio.Queue` 就认为任务创建成功，否则服务重启时可能丢失任务。

### 3.3 Outbox 与调度器

社区版使用数据库 Outbox 配合进程内队列，不引入额外消息中间件。

Outbox 的核心职责是记录“哪些工作需要被调度”，并在服务异常退出后重新发现尚未完成的投递。

建议字段包括：

- `id`
- `task_id`
- `event_type`
- `status`
- `attempt_count`
- `next_attempt_at`
- `last_error_code`
- `created_at`
- `updated_at`

投递规则：

1. 调度器周期性扫描待投递 Outbox。
2. 通过事务和条件更新保护领取过程。
3. 只有符合条件的记录才能被标记为正在投递。
4. 投递成功后更新 Outbox 状态，并推动任务进入 `QUEUED`。
5. 投递失败时记录错误、增加尝试次数并计算下次重试时间。
6. 超过重试上限后进入明确的失败处理流程，并产生审计事件。
7. 服务启动时重新扫描尚未完成的 Outbox。

调度器重复投递属于正常的故障场景。Worker 必须在执行前重新读取数据库中的 Task 状态，防止重复执行已领取、已取消或已进入终态的任务。

### 3.4 Worker 与并发控制

Worker 负责执行已经持久化并进入队列的 Task。

社区版使用：

- `asyncio.Queue`：进程内任务队列。
- `asyncio.Semaphore`：限制同时执行的任务数量。
- 数据库条件更新：保护任务领取和状态转换。
- 任务级执行上下文：保存 SecurityContext、AgentVersion 和取消信号。

默认并发数可以从 10 开始，但必须配置化，并结合模型服务、数据库和外部系统的容量调整。

Worker 执行前应检查：

1. Task 仍处于可执行状态。
2. 任务尚未超过总超时时间。
3. SecurityContext 已从持久化任务信息中恢复。
4. AgentVersion 与相关 SkillVersion、ToolVersion 绑定仍然有效。
5. 所需能力可用，且权限检查通过。

Worker 不得根据当前最新的 Agent 配置覆盖任务创建时的 AgentVersion 快照。

### 3.5 Task 执行循环

Worker 应复用阶段 5 的 ModelGateway 和阶段 6、7 的 SkillGateway 与 MD-Skill、Connector 能力。

基本流程：

1. 读取任务及其固定的 AgentVersion。
2. 构建执行上下文。
3. 调用 ModelGateway 获取模型结果。
4. 如果模型返回最终回答，则保存结果并进入 `SUCCESS`。
5. 如果模型提出 Tool Call，则校验对应 SkillVersion、ToolVersion 和输入 Schema。
6. 通过 SkillGateway 执行 Tool。
7. 将规范化的 Tool Result 加回模型上下文。
8. 继续下一轮模型调用。
9. 达到最大轮数仍无法完成时，按明确的终止规则结束任务并记录原因。

约束：

- 默认最多执行 5 轮模型与 Tool 的交互。
- 每轮 Tool Call 数量应有限制。
- Tool 结果应进行长度限制、敏感信息脱敏和结构校验。
- Tool 失败不一定立即导致 Task 失败；应将标准化错误交还模型，允许模型在剩余轮数内解释或调整。
- 达到轮数上限、任务超时或无法继续执行时，应按统一规则结束任务。
- 每次调用模型或 Tool 前后，都应检查任务取消状态与剩余时间。

### 3.6 取消机制

任务取消必须由统一的取消入口管理，不能只把数据库状态改成 `CANCELLED`。

建议流程：

1. 用户提交取消请求。
2. 校验当前用户是否拥有取消该 Task 的权限。
3. 通过状态机判断当前状态是否允许取消。
4. 更新任务状态，并写入 TaskEvent 和 Audit。
5. 向 Worker 发送取消信号。
6. Worker 将取消信号传递给当前模型请求、SkillGateway 和支持取消的 Tool。
7. 等待执行单元停止并清理资源。
8. 根据实际停止情况进入 `CANCELLED`，或保留 `CANCELING` 并继续跟踪。

对于无法中断的外部 HTTP 请求，系统应停止后续步骤，记录该请求的实际结果，并防止模型在取消后继续发起新调用。

取消请求本身也需要幂等：重复提交取消请求不能导致状态混乱或重复触发清理流程。

### 3.7 超时机制

至少区分三类超时：

| 类型           | 作用                                 |
| -------------- | ------------------------------------ |
| Task 总超时    | 限制整个任务从开始执行到结束的总时间 |
| Model 调用超时 | 限制单次模型请求的最长时间           |
| Tool 调用超时  | 限制单次外部工具或脚本执行的最长时间 |

实现要求：

- Task 总超时必须由统一的任务执行上下文管理。
- 单次调用超时不能覆盖任务总超时。
- 任务剩余时间不足时，不应启动新的长耗时步骤。
- 超时发生时应先停止后续执行，并按状态机记录结果。
- 对不能保证停止的外部请求，应记录其可能仍在外部运行的事实，避免产生虚假的取消保证。

### 3.8 人工确认

社区版只实现轻量人工确认，不建设复杂审批系统。

当某个 Tool 根据自身配置和全局策略要求确认时：

1. SkillGateway 暂停当前执行流程。
2. Task 转入 `WAITING_HUMAN`。
3. 生成确认事件并通过 SSE 通知前端。
4. 用户或具有相应权限的人员提交批准或拒绝决定。
5. 系统校验决定者权限及确认记录。
6. 批准后恢复任务，拒绝后按规则结束任务。
7. 记录决定人、决定时间、对应 Tool 和结果摘要。

等待期间不应持续占用普通 Worker 执行槽位。恢复任务时必须重新校验任务状态、权限与必要的执行条件。

### 3.9 TaskEvent 与 SSE

TaskEvent 是任务过程的持久化记录，SSE 只是向客户端传递这些记录的实时通道。

至少应记录：

- 任务创建和状态变化。
- 模型调用开始、结束及必要的用量摘要。
- Tool Call 请求摘要和参数脱敏摘要。
- Tool 执行结果摘要。
- 人工确认请求与决定。
- 取消请求与取消结果。
- 超时、失败和恢复事件。
- 最终结果或错误。

SSE 事件沿用已确定的事件命名：

`task.snapshot`、`task.status`、`task.delta`、`task.tool_call`、`task.tool_result`、`task.waiting_human`、`task.human_decision`、`task.result`、`task.error`、`task.done`。

要求：

1. 每条持久化事件具有可用于恢复的单调递增序号。
2. 客户端重连时可携带 `Last-Event-ID`。
3. 服务端根据事件序号补发遗漏事件。
4. 连接建立时发送必要的任务快照。
5. 实时推送失败不影响 TaskEvent 的持久化。
6. SSE 断开不应自动取消任务。
7. 事件内容只包含脱敏摘要，不直接暴露密钥或不必要的完整业务数据。

### 3.10 幂等与重复执行保护

系统需要同时处理请求层和任务执行层的重复问题。

**请求层：**

- Chat API 使用 `Idempotency-Key` 识别重复提交。
- 相同用户和相同幂等键在有效范围内重复提交时，返回已有请求对应的结果或 Task。
- 幂等键应具有唯一约束和明确的作用域。

**任务层：**

- Task 创建、状态转换和 Worker 领取必须通过数据库约束及条件更新保护。
- Worker 执行前重新确认 Task 状态。
- TaskEvent 应避免因重复处理同一状态转换而产生相互矛盾的记录。
- Tool 调用应在可能的情况下传递稳定的调用标识。
- 对具有外部副作用的 Tool，只有当目标系统支持幂等键或能够确认请求结果时，才可以安全地进行自动重试。

需要明确：数据库事务可以保证 Z-Torque 自身记录的一致性，但无法自动保证第三方系统的操作只执行一次。对已发出但响应丢失的外部请求，必须识别并处理执行结果不确定的情况。

### 3.11 服务重启与故障恢复

服务启动时，应先恢复数据状态，再开放正常的任务执行入口。

建议恢复顺序：

1. 初始化数据库连接并执行必要的迁移。
2. 检查未完成的 Outbox 记录。
3. 重新调度尚未执行的任务。
4. 检查遗留的 `QUEUED`、`RUNNING`、`WAITING_HUMAN` 和 `CANCELING` 任务。
5. 根据任务状态、心跳或执行租约及超时策略判断恢复方式。
6. 将可以安全恢复的任务重新入队。
7. 将无法确认是否可安全恢复的任务标记为需要进一步处理，或按明确策略进入失败状态。
8. 为恢复动作写入 TaskEvent 和 Audit。
9. 恢复 SSE 查询与任务管理能力。

不能简单地把所有遗留 `RUNNING` 任务重新执行，因为其中可能已经完成外部操作，只是尚未保存最终结果。

### 3.12 事务、终态与审计一致性

以下操作应通过统一的事务边界处理：

- 创建 Task、初始 TaskEvent 和 Outbox。
- 更新 Task 状态并写入对应 TaskEvent。
- 保存最终任务结果及必要的状态事件。
- 记录人工确认决定及任务后续状态。

审计事件流不能被关闭。若审计写入暂时失败，应使用可靠的重试或待处理机制，并明确记录告警；不能静默丢弃关键审计记录。

## 4. 接口与数据设计

### 4.1 核心数据对象

复用已有 Task、TaskEvent、Outbox 和 Audit 数据模型。只有字段不足以实现本阶段要求时，才进行增量迁移。

| 对象                     | 主要职责                                                   |
| ------------------------ | ---------------------------------------------------------- |
| `zr_task`                | 任务状态、用户、会话、AgentVersion、时间信息和最终结果引用 |
| `zr_task_event`          | 任务过程、状态变化和 SSE 恢复依据                          |
| `zr_outbox`              | 待调度事件、重试次数及投递状态                             |
| `zr_conversation`        | 任务所属会话                                               |
| `zr_message`             | 用户消息及最终可见回复                                     |
| `zr_skill_execution_log` | Skill 执行记录                                             |
| `zr_audit_log`           | 安全、权限和关键操作审计                                   |

建议确认以下约束：

- Task 使用 UUIDv7。
- Task 创建时固定 `agent_version_id`。
- TaskEvent 只追加，不直接覆盖历史事件。
- Task 的终态不能被普通更新接口修改。
- Outbox 记录具备可重试状态和下次尝试时间。
- Task 与 TaskEvent 之间存在可追踪关联。
- 需要并发保护的状态更新采用条件更新或版本字段。
- 事件序号应在同一个 Task 范围内有序且可用于断线恢复。

### 4.2 建议 API

统一使用 `/api/z-torque/*` 前缀，并优先复用前面阶段已建立的 Task 接口。

| 方法   | 路径                                    | 用途                         |
| ------ | --------------------------------------- | ---------------------------- |
| `GET`  | `/api/z-torque/tasks`                   | 查询当前用户可访问的任务     |
| `GET`  | `/api/z-torque/tasks/{task_id}`         | 查询任务详情和状态           |
| `GET`  | `/api/z-torque/tasks/{task_id}/events`  | 查询历史任务事件             |
| `GET`  | `/api/z-torque/tasks/{task_id}/stream`  | 订阅任务 SSE                 |
| `POST` | `/api/z-torque/tasks/{task_id}/cancel`  | 请求取消任务                 |
| `POST` | `/api/z-torque/tasks/{task_id}/confirm` | 提交人工确认决定             |
| `POST` | `/api/z-torque/tasks/{task_id}/retry`   | 在策略允许时创建新的执行任务 |

重试接口应创建新的 Task，并保留原 Task 的关联关系，不得直接将失败或终态 Task 重置为 `RUNNING`。

### 4.3 API 约束

- 所有 Task 查询、取消和确认操作必须执行用户权限检查。
- 用户不能通过猜测 Task ID 访问其他用户的私有任务。
- SSE 订阅必须检查任务访问权限。
- `Last-Event-ID` 只能用于查询当前用户有权访问的任务事件。
- 终态任务不能通过普通接口修改状态。
- 取消请求必须检查当前状态是否允许取消。
- 人工确认必须校验决定者权限、任务状态及确认记录。
- 任务错误响应应使用稳定的 `AI_` 错误码。
- 对重复请求返回已有结果或明确的冲突响应，不得静默创建重复任务。

## 6. 测试验收

### 6.1 功能验收

- 

  Task 只能按照定义的状态机转换。

- 

  Task、初始 TaskEvent 和 Outbox 能在同一事务中创建。

- 

  Worker 能执行模型与 Tool 多轮交互。

- 

  达到最大轮数后能够按规则结束任务。

- 

  用户可以取消允许取消的任务。

- 

  模型调用、SkillGateway 和可取消 Tool 能接收取消信号。

- 

  人工确认可以暂停和恢复任务。

- 

  SSE 能推送任务状态、步骤和最终结果。

- 

  客户端可以使用 `Last-Event-ID` 补取遗漏事件。

- 

  服务重启后能够恢复可安全恢复的任务。

- 

  重试操作创建新的 Task，并保留原任务关联关系。

### 6.2 一致性验收

- 

  重复 Chat 请求不会重复创建 Task。

- 

  重复 Outbox 投递不会执行已终结的任务。

- 

  Worker 不会同时执行同一个 Task 的两个有效实例。

- 

  Task 终态不可被普通更新覆盖。

- 

  TaskEvent 能反映真实的状态转换。

- 

  AgentVersion 在整个 Task 生命周期内保持固定。

- 

  Task 创建与初始事件不会出现部分提交。

- 

  最终结果、任务状态与关键事件具有一致的事务处理策略。

- 

  外部操作结果不确定时，不会盲目重复执行有副作用的调用。

### 6.3 故障恢复验收

至少在以下时间点进行故障注入测试：

- 

  Task 数据库事务提交后、Outbox 投递前。

- 

  Outbox 投递后、Worker 开始执行前。

- 

  Worker 执行期间。

- 

  模型已返回结果、任务结果尚未提交时。

- 

  外部 Tool 已执行、响应尚未保存时。

- 

  任务进入 `WAITING_HUMAN` 时。

- 

  用户发起取消、执行单元尚未停止时。

- 

  SSE 已断开但任务仍在执行时。

每个场景都必须有明确的恢复或终止策略，并能够通过 TaskEvent 与 Audit 解释发生了什么。

### 6.4 权限与审计验收

- 

  用户只能查看有权访问的 Task。

- 

  用户不能取消或确认无权操作的 Task。

- 

  SecurityContext 能从任务入口贯穿到 Tool 调用。

- 

  所有关键状态变化均有可追踪事件。

- 

  关键审计记录不能通过配置关闭。

- 

  日志不包含不必要的完整敏感参数。

- 

  任务失败、取消和恢复均能追踪到原因。

## 7. 风险项

| 风险                       | 影响                 | 应对措施                                 |
| -------------------------- | -------------------- | ---------------------------------------- |
| 只使用内存队列             | 服务重启后丢任务     | 数据库 Outbox 持久化与启动恢复           |
| 重复投递                   | 重复执行任务         | 数据库条件更新、状态检查和幂等控制       |
| 终态被覆盖                 | 历史结果不可信       | 集中状态机和终态不可变约束               |
| 取消只修改数据库           | 模型或脚本仍继续运行 | 传播取消信号并跟踪执行单元状态           |
| 外部操作已完成但本地未记录 | 重启后重复执行       | 记录不确定状态，优先核对外部结果         |
| SSE 与任务状态脱节         | 前端显示错误         | 以持久化 TaskEvent 为事实来源            |
| 审计写入失败               | 无法追踪关键操作     | 可靠重试、告警和待处理机制               |
| Worker 重启恢复错误        | 重复执行或丢失任务   | 按状态、执行租约和外部副作用风险分类恢复 |
| Agent 配置变化影响旧任务   | 同一任务执行逻辑变化 | 固定 AgentVersion 与依赖版本快照         |
| 长时间等待人工确认         | 占用执行资源         | 暂停任务并释放普通 Worker 执行槽位       |

### 8.2 启动检查

Runtime 启动时应：

1. 检查数据库连接和迁移状态。
2. 初始化 Worker、队列和并发控制。
3. 启动 Outbox 调度器。
4. 恢复待处理任务和事件。

如果内核所需的关键能力缺失，应遵循已有契约的 fail-fast 规则，不允许系统在缺少关键执行治理的情况下假装正常启动。

## 9. 阶段总结

阶段 8 的核心，是把之前独立实现的能力组织成一个具有可靠生命周期的任务运行时。

完成后，系统应形成以下闭环：

**请求进入 → 固定执行版本 → 持久化任务 → Outbox 调度 → Worker 执行 → ModelGateway / SkillGateway → TaskEvent 与 Audit → SSE 推送 → 终态或故障恢复。**

需要特别记住三点：

1. **任务可靠性不等于保证所有外部操作只执行一次。** Z-Torque 可以保证内部状态和调度记录的一致性，但外部系统是否支持幂等，仍决定副作用能否安全重试。
2. **取消不等于立即停止。** 必须跟踪执行单元的实际状态，不能仅修改数据库字段。
3. **恢复不等于重新执行。** 服务重启后必须先判断任务执行到了哪里、外部副作用是否可能已经发生，再决定重试、终止或人工处理。

下一阶段建议进入阶段 9：Memory、Conversation 上下文组装与文件附件处理。重点是在不破坏当前 Task 执行边界的前提下，让 Agent 能够理解近期对话、利用记忆摘要并安全处理用户上传的文件。
