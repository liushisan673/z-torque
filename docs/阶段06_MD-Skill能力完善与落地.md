# Z-Torque 社区版阶段 6：MD-Skill 能力完善与落地

**文档编号：** ZT-COMMUNITY-P6  
**文档版本：** 1.1（P1/P2 优化）  
**阶段名称：** MD-Skill 能力完善与落地  
**前置阶段：** 阶段 0—5  
**阶段状态：** 待实施  
**错误码：** 本阶段引用阶段 0 主表。新增错误码前必须检查既有语义，并登记 HTTP 映射、触发条件、用户提示和可重试规则，避免重复定义同义错误码。

## 1. 阶段目标

本阶段完成 MD-Skill 的本地发现、格式解析、配置校验、版本管理、发布、加载与执行能力，使 Z-Torque 能够通过 Markdown 文件定义可复用的 AI 技能。

完成后，系统应支持两种 MD-Skill 模式：

1. **纯指令模式**：通过 `SKILL.md` 描述技能目标、执行规则、适用场景和输出要求，由 Agent 在模型推理过程中使用。
2. **脚本执行模式**：在 Markdown 指令之外，通过受控脚本完成确定性计算或数据处理。脚本必须经过独立运行时执行，不能由业务代码任意调用系统命令。

本阶段交付目标：

- 自动发现指定目录中的 MD-Skill。
- 解析并校验 `SKILL.md` 的 YAML Front Matter 和正文。
- 支持技能启用、停用、复制、版本创建与发布。
- 支持文件变更检测和新版本生成。
- 支持纯指令模式和受控脚本模式。
- 将 MD-Skill 接入现有 SkillGateway。
- 保留权限检查、用户确认、执行日志和审计记录。
- 为后续控制台开发提供稳定的管理接口。

**阶段边界：** 本阶段只实现 MD-Skill 的运行与管理基础，不建设完整的可视化技能编辑器、在线代码 IDE、第三方代码插件市场或复杂沙箱平台。

## 3. 技术方案

### 3.1 目录结构

建议采用以下目录组织技能文件：

```
md-skills/
├── data-analysis/
│   ├── SKILL.md
│   ├── scripts/
│   │   └── summarize.py
│   └── examples/
│       └── sample.csv
└── text-summary/
    └── SKILL.md
```

目录约定：

- 每个技能目录必须包含一个 `SKILL.md`。
- `scripts/` 为可选目录，仅在脚本模式下使用。
- `examples/` 为可选示例目录，供开发和测试参考。
- 技能目录名称应满足统一命名规则，不能包含路径穿越字符。
- 技能文件必须位于允许的技能根目录内，不允许通过符号链接逃逸到其他目录。
- 示例文件不能因为被放在技能目录中就自动获得执行权限。

文件目录是技能内容的来源，不是最终执行权限的来源。实际运行时必须使用系统登记、校验并发布的 SkillVersion。

### 3.2 SKILL.md 格式

建议采用 YAML Front Matter 加 Markdown 正文的形式。

格式示例：

```
---
name: data-analysis
description: 分析结构化数据并生成摘要
implementation: md_instruction
version: 1
input_schema:
  type: object
  properties:
    question:
      type: string
  required:
    - question
output_schema:
  type: object
  properties:
    summary:
      type: string
  required:
    - summary
allow_scripts: false
required_permissions: []
---
```

正文示例：

```
# 数据分析技能

## 适用场景
分析用户提供的结构化数据，提炼关键变化和异常。

## 执行要求
1. 先确认数据范围和分析目标。
2. 说明关键发现及其依据。
3. 不得编造数据中不存在的指标。
4. 如果数据不足以支持结论，应明确说明。

## 输出要求
输出结论、关键依据和必要的局限性说明。
```

字段说明：

| 字段                   | 作用                                                       |
| ---------------------- | ---------------------------------------------------------- |
| `name`                 | 技能唯一标识                                               |
| `description`          | 技能用途说明                                               |
| `implementation`       | 实现类型，例如 `md_instruction` 或 `md_script`             |
| `version`              | 文件包中声明的版本信息；系统内部版本仍由 SkillVersion 管理 |
| `input_schema`         | 输入参数结构                                               |
| `output_schema`        | 输出结果结构                                               |
| `allow_scripts`        | 是否允许脚本模式                                           |
| `required_permissions` | 执行技能所需的权限集合                                     |

注意：文件中声明的 `version` 不得覆盖数据库中的正式 SkillVersion 版本号。数据库版本使用递增整数，由系统统一管理。

`implementation` 与 `allow_scripts` 必须经过一致性校验。纯指令模式不得因为目录中存在脚本就自动执行脚本；脚本模式也不得在未授权的情况下启用脚本能力。

### 3.3 MD-Skill 的加载流程

文件发现与运行加载应分离。

**发现与登记流程：**

1. 扫描技能根目录。
2. 检查技能目录与 `SKILL.md` 是否存在。
3. 解析 YAML Front Matter 和 Markdown 正文。
4. 校验字段、Schema、路径与文件清单。
5. 对技能内容生成摘要或文件指纹，用于检测变更。
6. 将发现结果与已有 Skill、SkillVersion 记录进行匹配。
7. 对新内容创建草稿版本，等待必要的检查与发布。
8. 对官方技能和用户自建技能应用各自的所有权规则。

**运行时加载流程：**

1. 根据 AgentVersion 找到其绑定的精确 SkillVersion。
2. 读取已发布版本的不可变内容。
3. 将技能指令作为受约束的上下文提供给模型，或准备脚本运行所需的输入。
4. 对脚本模式执行权限、确认、资源限制和路径校验。
5. 统一通过 SkillGateway 进入执行流程。
6. 规范化结果并记录执行日志、TaskEvent 和审计事件。

文件监听器负责发现变化，不负责直接修改运行中的已发布版本。

### 3.4 文件变更与版本管理

使用文件监听机制监控 `md-skills/`，并设置定期扫描作为补充，目标是在文件变更后 30 秒内发现变化。

处理规则：

- 新增技能：校验后登记为草稿。
- 修改草稿：允许重新解析和更新草稿内容。
- 修改已发布版本对应的文件：创建新的草稿版本，不覆盖已发布版本。
- 删除文件：标记为待处理或不可用，并记录审计；不能直接删除仍被历史任务引用的版本。
- 修改官方技能：不得直接覆盖官方资源；用户应复制为自有资源后修改。
- 发现格式错误：记录错误信息，不将无效内容加载为可执行版本。

发布后的 SkillVersion 必须固定指令内容、输入输出 Schema、脚本清单及必要的运行配置快照。AgentVersion 绑定的是具体 SkillVersion，而不是一个会随文件变化的技能目录。

### 3.5 纯指令模式

纯指令模式不执行技能目录中的脚本。

运行步骤：

1. Agent 选择其 AgentVersion 已绑定的 SkillVersion。
2. 系统完成 Skill 权限检查。
3. 将技能指令及必要的输入约束加入模型上下文。
4. 模型根据技能指令生成回复，或提出需要调用 Tool 的请求。
5. 如果模型请求调用 Tool，仍由 SkillGateway 校验并执行。
6. 将执行结果返回模型，继续后续推理或输出最终答复。

`SKILL.md` 的内容属于不可信输入。即使其中包含要求忽略系统规则、泄露密钥、绕过权限或调用未授权工具的文字，也不能覆盖系统策略、SecurityContext、权限判断或 SkillGateway 的控制规则。

### 3.6 脚本执行模式

脚本模式用于可明确约束输入和输出的确定性任务，例如数据清洗、格式转换和简单统计。

执行链路：

```
Agent
  ↓
SkillGateway
  ↓
Skill / SkillVersion 校验
  ↓
权限检查与确认判断
  ↓
MD-Skill Runtime
  ↓
受控脚本进程
  ↓
输出 Schema 校验
  ↓
结果规范化、日志与审计
```

脚本执行必须通过独立的 MD-Skill Runtime。不得在 API 路由、Agent 推理循环或普通业务模块中直接调用任意 `subprocess`。

最低安全要求：

- 只有明确允许脚本执行的已发布版本才能运行脚本。
- 脚本路径必须位于当前 SkillVersion 的允许文件清单内。
- 使用固定的允许扩展名；禁止动态导入外部任意代码包。
- 限制执行时间、CPU、内存、输出大小和并发数量。
- 默认禁止网络访问。
- 限制工作目录和文件访问范围。
- 不向脚本暴露 Secret Store 中的明文密钥。
- 对退出码、标准输出、标准错误进行长度限制和敏感信息脱敏。
- 校验最终输出是否符合 `output_schema`。
- 脚本失败时返回标准化错误，不泄露服务器路径、环境变量或堆栈中的敏感信息。

仅使用超时参数或捕获异常，不等于完成了安全隔离。若当前操作系统或容器配置无法提供可靠的进程、文件和网络限制，应将脚本能力标记为不可用，而不是降级为无约束执行。

### 3.7 权限与人工确认

MD-Skill 必须复用现有权限体系，不自行实现独立的授权机制。

执行前至少检查：

1. 当前用户是否有权使用该 Skill。
2. 当前 SkillVersion 是否处于允许执行的状态。
3. Skill 所声明的 `required_permissions` 是否全部满足。
4. 脚本模式是否已由管理员启用。
5. 所涉及 Tool 的权限和确认规则是否满足。
6. 全局安全策略是否要求人工确认。

Skill 级权限与 Tool 级权限均应执行检查；涉及写操作时，继续遵守 Tool 级确认规则与全局策略的共同约束。

官方 Skill 不允许直接编辑或删除。用户需要通过复制创建自己的 Skill，并保留来源 Skill ID、来源版本 ID，以便追溯。

### 3.8 与现有内核的集成边界

MD-Skill 不直接依赖或修改 Kernel 内部实现。

- **SkillGateway**：唯一技能执行入口，负责校验、权限、确认、执行路由和结果规范化。
- **Skill / SkillVersion**：沿用既有模型和生命周期，不新建平行体系。
- **AgentVersion**：固定绑定的 SkillVersion。
- **Task / TaskEvent**：记录运行状态、步骤摘要和必要的脱敏参数。
- **Audit**：记录技能发布、启停、配置变化和执行行为。
- **Secret Store**：管理敏感配置，MD-Skill 文件不得存放明文密钥。

如果脚本运行需要新增内部执行接口，应将其作为受控 Runtime 能力实现，并通过现有执行边界接入，不增加绕过 SkillGateway 的第二条执行通道。

## 4. 接口与数据设计

### 4.1 核心数据复用

本阶段优先复用现有数据模型，不额外建立一套 MD-Skill 主表。

| 数据对象                 | 本阶段用途                                 |
| ------------------------ | ------------------------------------------ |
| `zr_skill`               | Skill 基础信息、所有权、来源关系、启用状态 |
| `zr_skill_version`       | 不可变版本配置、指令内容、Schema、脚本清单 |
| `zr_agent_version`       | 固定绑定具体 SkillVersion                  |
| `zr_task`                | 关联运行任务                               |
| `zr_task_event`          | 记录执行过程摘要和状态变化                 |
| `zr_skill_execution_log` | 记录技能执行结果、耗时和错误摘要           |
| `zr_audit_log`           | 记录发布、启停、复制和执行审计             |

如果现有 SkillVersion 结构无法表达 MD-Skill 所需配置，可以增加受控的版本配置字段或 JSON 快照，但不得让发布版本依赖可变目录中的实时内容。

### 4.2 建议 API

统一使用 `/api/z-torque/*` 前缀。

| 方法   | 路径                                       | 用途                           |
| ------ | ------------------------------------------ | ------------------------------ |
| `GET`  | `/api/z-torque/skills`                     | 查询技能列表                   |
| `GET`  | `/api/z-torque/skills/{skill_id}`          | 查询技能详情                   |
| `GET`  | `/api/z-torque/skills/{skill_id}/versions` | 查询技能版本                   |
| `POST` | `/api/z-torque/skills/{skill_id}/versions` | 创建新草稿版本                 |
| `POST` | `/api/z-torque/skills/{skill_id}/publish`  | 发布符合条件的草稿             |
| `POST` | `/api/z-torque/skills/{skill_id}/disable`  | 停用技能                       |
| `POST` | `/api/z-torque/skills/{skill_id}/copy`     | 复制技能到当前用户或指定所有者 |
| `POST` | `/api/z-torque/skills/scan`                | 触发技能目录扫描               |
| `GET`  | `/api/z-torque/skills/scan/status`         | 查询最近扫描状态               |

以上是接口职责建议。实际开发时应先检查前面阶段已定义的 Skill API，优先扩展现有接口，避免重复创建同义路由。

### 4.3 接口约束

- 列表查询必须执行用户权限过滤。
- 草稿编辑和发布操作必须校验资源所有权与操作权限。
- 官方资源不允许通过普通更新接口覆盖。
- 发布接口必须验证 Schema、文件清单、脚本策略和版本状态。
- 扫描接口应具备权限控制，不能让普通用户任意读取服务器文件。
- API 不返回 Secret 明文、绝对服务器路径或完整敏感执行参数。
- 发布、停用、复制、扫描和执行失败均应留下必要审计记录。

建议统一响应格式：

```
{
  "code": "AI_SUCCESS",
  "message": "操作成功",
  "data": {},
  "trace_id": "请求追踪标识"
}
```

错误码应使用稳定的 `AI_` 前缀，例如 `AI_SKILL_INVALID_MANIFEST`、`AI_SKILL_VERSION_IMMUTABLE`、`AI_SKILL_SCRIPT_DISABLED`、`AI_SKILL_PERMISSION_DENIED`。错误码应在接口契约中集中定义，避免不同模块重复发明含义相近的错误码。

交付物：文件监听模块、发布治理测试。

### T6-07：完成集成验收

工作内容：

- 接入 SkillGateway、TaskEvent、执行日志与审计。
- 验证失败返回标准化结果。
- 验证取消任务时脚本进程能够按策略停止。
- 验证旧 AgentVersion 不会意外切换到新 SkillVersion。
- 整理启动配置、运行说明和已知限制。

交付物：阶段测试报告、配置说明、阶段验收清单。

## 6. 测试验收

### 6.1 功能验收

- 

  能扫描并识别合法的 `SKILL.md`。

- 

  缺少必填字段或 Schema 不合法时，能返回清晰错误。

- 

  纯指令模式可以向 Agent 提供已发布技能内容。

- 

  纯指令模式不会执行目录中意外存在的脚本。

- 

  脚本模式可以运行允许的脚本并校验输出。

- 

  文件变更可在目标 30 秒内被发现。

- 

  已发布版本被修改时会创建新草稿，而不是覆盖旧版本。

- 

  AgentVersion 仍绑定原有 SkillVersion。

- 

  官方 Skill 只能被复制后修改，不能直接编辑或删除。

- 

  技能执行过程可通过现有日志和审计追溯。

### 6.2 安全验收

- 

  无权限用户不能执行受保护的 Skill。

- 

  `SKILL.md` 中的提示注入内容不能绕过系统策略和权限检查。

- 

  未授权脚本不能被执行。

- 

  路径穿越、符号链接逃逸和不允许的文件扩展名会被拒绝。

- 

  脚本超时后能够终止或进入明确的取消处理状态。

- 

  脚本不能默认访问网络。

- 

  脚本输出过大时会被限制。

- 

  错误日志不泄露密钥、环境变量和敏感服务器信息。

- 

  写操作遵守 Tool 级确认与全局策略。

- 

  所有实际执行均通过 SkillGateway。

### 6.3 稳定性验收

- 

  目录中存在格式错误的技能，不影响其他合法技能加载。

- 

  文件监听器异常后，定期扫描仍可发现变化。

- 

  重启后可以重新扫描并恢复技能登记状态。

- 

  任务取消时，不会把尚未结束的脚本错误标记为正常成功。

- 

  多个任务并发执行时，输入、输出和日志不发生串线。

- 

  SkillGateway、TaskEvent 和审计记录之间能够通过追踪标识关联。

## 7. 风险项

| 风险                       | 影响                         | 应对措施                                     |
| -------------------------- | ---------------------------- | -------------------------------------------- |
| 文件内容与数据库版本不一致 | 历史任务无法复现             | 发布时保存不可变内容快照及文件指纹           |
| Markdown 指令包含恶意内容  | 诱导模型越权或泄露数据       | 将内容视为不可信输入，权限检查放在内核和网关 |
| 脚本具有过高系统权限       | 读取文件、访问网络或破坏环境 | 独立 Runtime、最小权限、资源限制与网络隔离   |
| 监听事件丢失               | 新版本未及时发现             | 文件监听加定期扫描                           |
| 发布后内容被修改           | Agent 行为不可追溯           | 版本不可变，变更生成新草稿                   |
| 官方技能被用户覆盖         | 破坏公共资源和来源追溯       | 所有权检查、复制机制、来源 ID                |
| 取消任务未终止子进程       | 占用资源、继续执行           | 运行时传播取消信号并跟踪进程退出状态         |
| 脚本运行环境不具备隔离能力 | 无法满足安全要求             | 将脚本能力标记为不可用，不退化为任意本机执行 |

本阶段的关键风险不是 Markdown 解析本身，而是**把可编辑的技能文件错误地当成可信代码或可信权限配置**。必须区分技能描述、系统策略、用户权限和实际执行能力。

## 8. 上线交付

### 8.1 配置项

建议提供以下配置，并通过现有配置模块统一管理：

| 配置项                            | 用途                 |
| --------------------------------- | -------------------- |
| `MD_SKILLS_DIR`                   | 技能根目录           |
| `MD_SKILL_WATCH_ENABLED`          | 是否启用文件监听     |
| `MD_SKILL_SCAN_INTERVAL`          | 定期扫描间隔         |
| `MD_SKILL_SCRIPT_ENABLED`         | 是否允许脚本执行能力 |
| `MD_SKILL_SCRIPT_TIMEOUT`         | 单次脚本最大执行时间 |
| `MD_SKILL_SCRIPT_MAX_OUTPUT`      | 脚本输出大小限制     |
| `MD_SKILL_SCRIPT_MAX_CONCURRENCY` | 脚本并发限制         |

具体默认值应结合已有配置体系、部署方式和测试结果统一确定，不在多个模块中分别写死。

### 8.2 启动与运行检查

启动时应：

1. 检查技能根目录是否存在或可创建。
2. 检查目录读写权限。
3. 加载已有 SkillVersion 登记信息。
4. 执行必要的目录扫描和格式校验。
5. 检查脚本运行能力是否具备所需的隔离条件。
6. 对不可用的能力给出明确状态和原因。
7. 确保文件监听、定期扫描与运行时加载互不冲突。

首次启用的技能必须遵守管理员确认规则。文件被发现不代表它已经获得发布和执行权限。

### 8.3 交付内容

本阶段结束时应提交：

- MD-Skill 文件格式规范。
- 技能发现、解析与校验模块。
- SkillVersion 集成及发布治理。
- 纯指令模式实现。
- 受控脚本 Runtime；如果当前环境不能安全实现，则明确交付不可用状态及限制。
- 文件监听与定期扫描。
- API 契约与错误码说明。
- 功能、安全、稳定性测试报告。
- 示例 Skill 和本地运行说明。

## 9. 阶段总结

阶段 6 的目标不是让 Z-Torque 可以运行任意 Markdown 或 Python 文件，而是建立一种**可管理、可版本化、受权限控制、可审计的 Skill 实现机制**。

完成后，Z-Torque 应形成以下关系：

- Skill 定义可复用的业务能力。
- SkillVersion 固定能力的具体实现。
- MD-Skill 通过 Markdown 描述能力，也可以选择受控脚本执行。
- AgentVersion 绑定明确的 SkillVersion。
- SkillGateway 统一管理执行、权限、确认与结果。
- TaskEvent、执行日志和 Audit 共同提供运行追踪。

**下一阶段建议：阶段 7——Connector 与业务系统接入。** 重点是将 REST API、只读数据库等企业现有能力转化为可治理的 Tool，再由 Skill 进行组合；同时把身份、凭据、目标地址白名单和权限校验贯穿整个调用链。
