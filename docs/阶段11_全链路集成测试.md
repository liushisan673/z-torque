# Z-Torque 社区版阶段 11：全链路集成测试、安全加固与社区版发布验收

**文档编号：** ZT-COMMUNITY-P11  
**文档版本：** 1.1（P1/P2 优化）  
**阶段名称：** 全链路集成测试、安全加固与社区版发布验收  
**前置阶段：** 阶段 0～10  
**阶段状态：** 待实施  

## 统一错误码与父子协作验收要求

全链路验收必须检查错误码均登记在阶段 0 主表、HTTP 映射一致、未知异常安全转换，以及 Task 状态机、幂等、Outbox、重试、取消、恢复和父子任务错误策略均有测试覆盖。

### 父子 Agent 协作强制验收用例

必须增加以下测试：

1. 未选择 Agent 时使用默认父 Agent。
2. 默认父 Agent 不委派时原有流程不变。
3. 父 Agent 按白名单创建并执行多个子 Task。
4. 未授权、停用或未发布的子 AgentVersion 被拒绝。
5. 子 Agent 无法提升权限或创建下一层子 Task。
6. 循环、超出数量、并发、时间或轮次上限的委派被拒绝。
7. 子任务失败、超时、取消和部分成功按策略汇总。
8. 父 Task 取消能传播到未完成子 Task。
9. 重启后父子 Task 按治理规则恢复。
10. 重复委派不产生重复执行。
11. AgentVersion 更新不改变进行中的父子 Task。
12. Conversation、Memory、文件、Connector 和审计不存在跨用户泄露。
13. SSE 能展示父子关系且不泄露无权内容。

还必须验证串行委派场景：父 Agent 先创建数据获取子 Task，成功后再创建数据分析子 Task；分析子 Task 只能接收经校验的前序结果引用；前序失败、空结果、格式错误、权限不足或超出预算时不得创建后续子 Task；两个子 Task 均为根 Task 的直接子任务；父 Agent 最终统一汇总并输出结果。

## 1. 阶段目标

### 1.1 核心目标

对 Z-Torque 社区版已经实现的后端内核、API、Worker、Agent、Skill、Tool、ModelGateway、SkillGateway、Conversation、Memory、文件处理和前端控制台进行系统性验证。

本阶段的核心不是默认前面所有功能已经完成，而是**以实际代码、实际接口和实际运行结果为依据，逐项确认功能是否实现、是否符合内核契约、是否能够稳定运行**。

主要目标：

1. 验证从用户登录到 Agent 执行完成的完整业务链路。
2. 验证身份、权限、版本快照和审计等不可破坏的内核约束。
3. 验证 Task 状态机、Outbox、Worker、取消和异常恢复。
4. 验证模型、Skill、Tool、Connector、MCP 和文件处理的安全边界。
5. 验证多用户并发使用时的数据隔离和状态一致性。
6. 完成部署验证、配置检查、故障排查和发布材料准备。
7. 建立明确的发布门槛，防止未完成或未验证的能力被误认为可用。

### 1.2 阶段完成标准

只有满足以下条件，才能将社区版标记为通过发布验收：

- 核心业务链路真实运行成功。
- 六项内核不变量未发现违反情况。
- 核心权限与数据隔离测试通过。
- Task 状态、执行结果和审计记录保持一致。
- 关键故障场景有明确、可验证的处理行为。
- 敏感信息未在 API、日志、审计或前端暴露。
- 单机部署、重启恢复和数据库迁移通过验证。
- 已知问题、未实现能力和发布限制均有记录。

| AuthZ / PEP           | API 授权、资源授权、Skill 执行前授权       |

| ModelGateway          | 模型选择、失败处理、端点切换和调用记录     |
| SkillGateway          | 统一执行入口、权限、确认、超时和结果规范化 |

### 2.2 六项内核不变量验收

以下约束是发布验收的核心，不得为了测试方便而跳过。

**不变量一：身份与会话**

SecurityContext 必须从 API 入口传递到 Task、Worker、Skill 和外部调用。异步执行不能丢失用户身份，也不能默认把普通用户提升为系统管理员。

**不变量二：Task 状态机与事务边界**

状态只能按照合法状态机迁移；Task、TaskEvent 和 Outbox 的关键写入必须符合既定事务边界；终态不可被普通执行逻辑改写。

**不变量三：Agent 版本快照**

已发布 Agent Version 不允许原地修改。新发布版本不得改变已经创建的 Task 所绑定的旧版本配置。

**不变量四：审计事件流**

关键安全与执行事件必须进入审计链路。不能因为前端关闭功能、某个插件不可用或普通配置变更而关闭审计。

**不变量五：权限决策点**

API、资源查询和 Skill 执行前均必须进行相应权限检查。模型输出、前端按钮和用户提交的参数不能直接授予权限。

**不变量六：双网关**

模型调用必须经过 ModelGateway；所有 Tool 执行必须经过 SkillGateway。不能存在绕过网关直接访问模型或执行 Tool 的业务路径。

### 2.3 非目标

本阶段不新增以下能力：

- 企业版多租户管理。
- SSO、LDAP、OIDC。
- A2A 网关。
- 复杂可视化工作流编辑器。
- 完整知识库产品。
- 长期记忆管理控制台。
- 多节点集群和 Kubernetes 部署。
- 大规模压测平台或完整商业监控平台。

发现上述能力的相关问题时，只记录其对社区版现有范围的影响，不因此扩大开发范围。

## 3. 技术方案

### 3.1 测试分层

按从小到大的顺序开展测试。

| 测试层       | 目标         | 典型检查                           |
| ------------ | ------------ | ---------------------------------- |
| 单元测试     | 验证局部规则 | 状态迁移、权限判断、参数校验       |
| 集成测试     | 验证模块协作 | 数据库事务、网关、Worker、文件处理 |
| API 测试     | 验证接口契约 | 请求响应、鉴权、错误码、幂等       |
| 端到端测试   | 验证完整业务 | 登录、对话、Task、工具、审计       |
| 安全测试     | 验证信任边界 | 越权、敏感信息、恶意输入、连接目标 |
| 故障恢复测试 | 验证异常行为 | 进程重启、模型失败、Worker 中断    |
| 部署验收     | 验证交付能力 | 新环境启动、迁移、备份、恢复       |

先验证基础规则，再验证模块集成，最后执行端到端与故障恢复测试。不要只依靠手工点击页面判断系统是否正确。

### 3.2 测试环境

建立独立的测试环境，避免测试数据与真实业务数据混用。

要求：

- 使用独立测试数据库或独立数据库实例。
- 使用专门的测试用户和角色。
- 使用测试模型凭证和测试 Connector。
- 不使用真实生产密钥进行故障注入。
- 测试文件存放于独立测试目录。
- 记录数据库版本、应用版本和关键配置。
- 每次测试保留可追踪的测试结果。

SQLite 是社区版默认部署选项时，需要在 SQLite WAL 配置下验证核心事务行为。如果项目同时支持 PostgreSQL，也应针对实际支持的数据库运行对应集成测试。

### 3.3 测试数据设计

至少准备以下测试主体：

- 管理员用户。
- 普通用户 A。
- 普通用户 B。
- 一个官方 Agent。
- 一个个人 Agent。
- 一个官方 Skill 和一个个人 Skill。
- 一个正常可用的模型配置。
- 一个不可用的模型配置。
- 一个只读数据库 Connector。
- 一个 MCP 测试服务。
- 一个允许访问的文件和一个无权访问的文件。

测试数据需要覆盖不同资源所有权、版本状态、权限组合和失败情况。

测试结束后，按既定清理策略清理测试数据。不要因测试清理而删除仍被历史 Task、Agent Version 或 Audit 引用的记录。

### 3.4 测试执行与结果记录

每项测试都需要明确：

- 测试编号。
- 测试前置条件。
- 操作步骤。
- 预期结果。
- 实际结果。
- 通过或失败状态。
- 相关日志、Trace ID 或事件 ID。
- 失败问题及修复记录。

建议将测试结果统一放入项目的测试文档目录，并记录测试对应的代码版本。

**测试通过必须有实际证据。** 不能仅凭接口返回 HTTP 200、页面没有报错或日志中出现“success”就判断业务通过。

### 3.5 自动化测试策略

将高风险、容易回归的规则纳入自动化测试：

- Task 合法状态迁移。
- 终态不可变。
- 幂等请求去重。
- SecurityContext 传播。
- 官方版本不可修改。
- Agent Version 与 Skill Version 绑定。
- SkillGateway 权限检查。
- Audit 关键事件写入。
- 敏感信息脱敏。
- Conversation 和 File 的用户隔离。

模型服务和外部连接可以使用可控的测试替身进行常规自动化测试，但还必须至少保留必要的真实集成验证，确认真实网络、认证、超时和返回格式符合预期。

### 3.6 故障注入原则

故障测试应在隔离的测试环境中执行，且一次只引入一种主要故障。

重点模拟：

- 模型连接失败。
- 模型调用超时。
- Tool 执行失败。
- MCP 进程异常退出。
- Worker 在执行中退出。
- 数据库连接中断。
- SSE 客户端断开。
- 任务投递过程中应用重启。
- 文件解析失败。
- 审计写入异常。

测试时需要确认系统实际表现与契约一致，并验证恢复后不会出现静默丢失、越权执行或不确定副作用被盲目重放。

## 4. 接口与数据设计

### 4.1 API 契约检查

统一检查 `/api/z-torque/*` 范围内的接口。

检查项目：

- 请求方法与路径是否一致。
- 请求参数、必填字段和数据类型是否一致。
- 响应结构是否符合约定。
- 错误码是否稳定且可识别。
- 是否正确执行身份认证和资源授权。
- 幂等接口是否正确处理重复请求。
- 文件上传和下载是否执行权限校验。
- SSE 是否具有正确的事件类型和重连行为。
- 敏感信息是否从响应中排除。

内部接口必须保持内部边界。面向公网的请求访问 `/internal/*` 时，应按既定契约返回 404，不能因前端配置或路由误配暴露内部操作。

### 4.2 Task 与 Outbox 数据一致性

针对 Task、TaskEvent 和 Outbox 验证以下规则：

1. 创建 Task 时，关键状态记录与 Outbox 写入满足同一事务约束。
2. 不存在 Task 已提交但关键投递记录无故缺失的情况。
3. 重复处理同一 Outbox 事件不会产生未经允许的重复 Task 执行。
4. Task 状态变化与 TaskEvent 记录保持一致。
5. Task 到达终态后，普通执行逻辑不能再次修改其终态。
6. 恢复程序能够区分可安全重试与执行结果不确定的任务。

对于可能已经产生外部副作用、但尚未成功写入最终结果的 Tool 调用，不能仅凭 Task 仍处于 RUNNING 就自动重新执行。必须结合目标系统幂等能力、执行记录或人工核查决定恢复方式。

### 4.3 版本快照一致性

验证以下数据关系：

- Task 绑定唯一的 Agent Version。
- Agent Version 保存完整的不可变配置快照。
- Agent Version 绑定明确的 Skill Version。
- Skill Version 绑定明确的 Tool Version。
- 新发布版本不会覆盖历史版本。
- 官方资源复制后，原资源和复制资源独立演进。
- 归档或软删除不破坏历史 Task 的追溯能力。

修改草稿、发布新版本、归档资源后，都需要验证历史执行记录仍然可以追溯当时的配置。

### 4.4 权限与数据隔离

至少验证：

- 用户 A 不能读取用户 B 的私有 Conversation。
- 用户 A 不能读取用户 B 的私有 Memory。
- 用户 A 不能下载用户 B 无权访问的 File。
- 用户 A 不能取消或确认用户 B 无权操作的 Task。
- 普通用户不能修改官方 Agent、Skill 和 Tool。
- 未获得授权的 Skill 或 Tool 不会因为模型请求而执行。
- 数据库 Connector 不会访问允许列表之外的表。
- 用户提交的 `user_id`、`tenant_id`、角色或权限字段不能覆盖服务端认证结果。

社区版即使是单租户，也必须保留用户级别的资源隔离；不能将“单租户”误解为“所有用户共享全部会话和文件”。

### 4.5 审计数据检查

核对关键操作与审计记录之间的对应关系：

- 登录与认证失败。
- 权限决策。
- Task 创建和状态迁移。
- 模型调用。
- Skill 执行。
- 人工确认与取消操作。
- Agent、Skill、Model、Connector 配置变更。
- 发布、归档和文件访问等需要审计的操作。

审计数据需要保留关联标识，例如 Task ID、Agent Version ID、用户 ID 和 Trace ID，具体字段以已冻结的数据模型为准。

### 4.6 数据迁移与恢复

验证：

- 全新数据库可以完成初始化。
- 已有数据库可以通过迁移升级。
- 重复启动不会意外重复初始化或破坏已有数据。
- 迁移失败时有清晰的错误信息。
- 备份能够覆盖数据库及必要的文件数据。
- 恢复后数据库中的文件元数据与实际文件保持一致。
- 恢复后的 Task、版本和审计记录能够正常查询。

数据库备份与文件存储备份需要统一考虑。仅备份数据库而遗漏实际附件文件，不能视为完整备份。

## 5. 任务排期

建议按以下顺序执行。发现阻塞性问题时，应先修复再进入依赖该能力的后续验收。

| 编号   | 任务                 | 主要交付物                  | 验收重点                 |
| ------ | -------------------- | --------------------------- | ------------------------ |
| T11-01 | 盘点现有实现         | 功能清单、缺口清单          | 不把计划功能误记为已实现 |
| T11-02 | 自动化基础测试       | 单元与集成测试集            | 核心规则可重复验证       |
| T11-03 | 权限与安全测试       | 安全测试记录                | 无已知高危越权问题       |
| T11-04 | Task 与恢复测试      | 故障测试记录                | 状态和恢复行为符合契约   |
| T11-05 | 端到端集成测试       | E2E 测试记录                | 核心用户链路通过         |
| T11-06 | 性能与稳定性检查     | 测试结果和容量限制          | 无明显阻塞性问题         |
| T11-07 | 部署、迁移与备份验证 | 部署及恢复说明              | 新环境可部署、数据可恢复 |
| T11-08 | 发布验收             | Release Checklist、已知问题 | 满足发布门槛             |

### T11-01：盘点现有实现

- 汇总阶段 1–10 的已实现内容。
- 检查实际目录、模块和接口。
- 区分已实现、部分实现、未实现和未验证。
- 对照内核契约检查六项不变量。
- 对照非目标列表检查是否出现未经确认的范围扩张。

交付物：`docs/release/implementation-inventory.md`。

### T11-02：自动化基础测试

- 补齐核心状态机和权限测试。
- 补齐版本快照测试。
- 补齐网关统一入口测试。
- 补齐审计和敏感信息脱敏测试。
- 验证幂等与重复事件处理。
- 确保测试可重复执行。

交付物：测试用例、执行记录和失败问题清单。

### T11-03：权限与安全测试

- 测试不同用户之间的资源隔离。
- 测试伪造资源 ID 和用户 ID。
- 测试未经授权的 Tool 调用。
- 测试官方资源修改限制。
- 测试文件访问控制。
- 检查日志、审计、API 响应和前端是否泄露敏感信息。
- 检查 Connector 和 MCP 目标地址约束。

交付物：安全检查表及问题修复记录。

### T11-04：Task 与恢复测试

- 验证全部合法和非法状态迁移。
- 模拟 Outbox 投递失败。
- 模拟 Worker 执行中断。
- 模拟应用重启和 SSE 断线。
- 验证超时、取消和人工确认。
- 验证终态不可变。
- 检查外部副作用不确定时的恢复策略。

交付物：Task 故障恢复测试报告。

### T11-05：端到端集成测试

从真实控制台发起请求，跑通登录、对话、模型调用、Skill 执行、Task 状态更新、最终结果展示和审计查询。

同时验证普通聊天不创建 Task，以及需要执行 Skill 时才根据后端响应进入 Task 流程。

交付物：端到端测试记录及问题清单。

### T11-06：性能与稳定性检查

针对社区版单机定位进行合理测试：

- 多用户同时访问。
- 多个 Task 并发执行。
- 模型响应较慢时的行为。
- 长时间 SSE 连接。
- 大量历史消息的查询。
- 接近上传上限的文件。
- Worker 队列积压。
- 数据库文件或存储空间不足。

检查默认并发限制、超时配置和错误反馈是否生效。记录实际测试环境和结果，不在缺少实测数据时承诺具体吞吐量。

### T11-07：部署、迁移与备份验证

- 在干净环境完成安装。
- 验证环境变量和 Secret Store 配置。
- 验证数据库迁移。
- 验证持久化目录和文件权限。
- 验证应用重启后的恢复。
- 验证数据库与文件联合备份和恢复。
- 验证服务停止和启动流程。
- 整理故障排查说明。

交付物：部署说明、备份恢复说明和部署验收记录。

### T11-08：发布验收

- 汇总测试结果。
- 关闭所有阻塞发布的问题。
- 标注未实现和未验证能力。
- 检查默认配置的安全性。
- 确认许可证、第三方依赖和发行文件准备情况。
- 确认发布包与测试版本一致。
- 输出最终发布检查清单。

交付物：社区版发布验收报告。

## 6. 测试验收

### 6.1 核心业务链路

- 

  用户能够登录并获取正确的权限上下文。

- 

  用户能够选择有权访问的 Agent。

- 

  普通聊天能够完成模型回复。

- 

  普通聊天不会无故创建 Task。

- 

  需要执行 Skill 时，后端创建 Task 并返回正确标识。

- 

  Task 使用创建时确定的 Agent Version。

- 

  模型调用经过 ModelGateway。

- 

  Tool 调用经过 SkillGateway。

- 

  Task 事件能够被前端正确接收和展示。

- 

  最终结果、Task 状态与审计记录保持一致。

### 6.2 内核不变量

- 

  SecurityContext 沿执行链传播。

- 

  Task 只能进行合法状态迁移。

- 

  Task 终态不可被普通执行逻辑修改。

- 

  已发布 Agent Version 不可原地修改。

- 

  审计关键事件流不能关闭。

- 

  未授权操作不能通过模型或前端绕过。

- 

  ModelGateway 和 SkillGateway 是唯一规定的执行入口。

### 6.3 故障恢复

- 

  模型不可用时返回明确错误或执行已配置的合法备用策略。

- 

  Skill 或 Tool 失败时生成规范化结果。

- 

  Outbox 失败能够按策略重试。

- 

  Worker 中断后任务能够进入正确的恢复路径。

- 

  外部副作用不确定时不会盲目重复执行。

- 

  SSE 断开后能够查询当前 Task 状态。

- 

  人工确认、取消和超时行为符合状态机。

- 

  应用重启后历史任务、会话和审计记录可查询。

### 6.4 安全性

- 

  不同用户之间的私有会话、记忆和文件隔离。

- 

  API 不能通过伪造用户 ID 或资源 ID 越权。

- 

  官方资源不可被普通用户直接修改或删除。

- 

  Secret 不以明文存入普通业务字段、日志或审计。

- 

  Connector 只能访问允许的目标和操作范围。

- 

  上传文件经过后端类型、大小和权限检查。

- 

  文件内容被视为不可信输入。

- 

  内部接口不会通过公网路由暴露。

- 

  生产错误响应不泄露敏感堆栈。

### 6.5 部署与数据

- 

  全新环境可以安装并启动。

- 

  数据库迁移成功。

- 

  应用重启后必要数据保持完整。

- 

  数据库和文件可以联合备份。

- 

  备份可以实际恢复。

- 

  文件元数据与实际文件一致。

- 

  默认配置和启动日志不包含明文凭证。

- 

  部署说明经过实际操作验证。

### 6.6 发布门槛

采用以下发布判定：

**通过发布验收：**

- 所有核心业务链路通过。
- 六项内核不变量全部通过。
- 没有未修复的已知高危安全问题。
- 没有导致核心数据丢失或权限绕过的阻塞问题。
- 关键故障恢复、备份恢复和部署流程通过。

**暂缓发布：**

- 任一内核不变量未通过。
- 存在可复现的跨用户数据泄露或权限绕过。
- Task 可能被无保护地重复执行并造成严重外部副作用。
- 审计链路可以被普通用户关闭。
- 数据迁移或恢复可能造成不可接受的数据损坏。
- 核心端到端链路无法稳定完成。

非核心问题可以进入已知问题清单，但必须说明影响范围、规避方法和后续计划。不能把未测试的功能标记为已通过。

## 7. 风险项

| 风险                    | 影响                      | 处理措施                             |
| ----------------------- | ------------------------- | ------------------------------------ |
| 只测试成功路径          | 异常时行为不可预测        | 增加失败、超时、取消和恢复测试       |
| 将计划功能视为已完成    | 发布后功能缺失            | 逐项盘点实际代码与接口               |
| Task 恢复时盲目重放     | 外部系统产生重复副作用    | 区分可重试与结果不确定的操作         |
| 权限只在前端检查        | 用户可以直接调用 API 越权 | 后端强制授权并加入自动化测试         |
| 审计与业务状态不一致    | 无法追溯执行过程          | 验证关键事件写入、关联标识和失败策略 |
| SQLite 与并发行为不匹配 | 数据库锁争用、请求失败    | 测试实际并发条件，设置合理超时与重试 |
| 外部服务不稳定          | Task 堵塞或长时间等待     | 设置超时、有限重试和明确失败状态     |
| 文件与数据库备份不一致  | 恢复后附件丢失            | 联合备份并实际验证恢复               |
| 性能结论缺少实测        | 误导用户部署预期          | 发布实测环境、负载和结果             |
| 发布范围持续扩大        | 验收无限延期              | 严格执行社区版范围和发布门槛         |

- `docs/release/test-report.md`：测试执行结果。

- `docs/release/known-issues.md`：已知问题与限制。
- `docs/release/deployment.md`：安装与部署说明。
- `docs/release/backup-restore.md`：备份与恢复说明。
- `docs/release/release-checklist.md`：发布检查清单。
- `CHANGELOG.md`：版本变更记录。
- `LICENSE`：与实际发行方式匹配的许可证文件。

这些文件需要根据真实实现填写，不能只创建空文件后就视为完成。

### 8.2 版本与发行检查

- 确认应用版本号。
- 确认数据库迁移版本。
- 确认 API 契约与前端构建版本匹配。
- 确认依赖版本和安装方式。
- 确认发行包不包含测试凭证、个人数据或本地环境文件。
- 确认 Secret Store、数据库和附件目录的初始化方式。
- 确认许可证与第三方依赖声明。
- 确认发布说明准确描述已实现能力和已知限制。

### 8.3 安全默认值

发布时检查：

- 默认管理员凭证是否必须在首次启动时设置或安全初始化。
- 是否禁止将明文密钥写入日志。
- 是否限制外部连接目标。
- 是否限制上传大小和文件类型。
- 是否启用必要的认证与授权。
- 是否限制危险操作。
- 是否启用审计。
- 是否配置合理的请求超时、Task 超时和并发限制。
- 是否防止内部接口被公开访问。
- 是否明确说明社区版的单机部署与数据备份责任。

### 8.4 发布后的观察

发布后优先观察：

- Task 失败率与超时情况。
- 模型连接失败和限流。
- Worker 队列积压。
- 数据库锁争用和存储空间。
- 文件上传、解析和下载失败。
- MCP 连接健康状态。
- SSE 连接异常。
- 审计写入失败。
- 认证和权限错误异常增长。

社区版不要求在本阶段建立复杂的企业级监控体系，但必须提供足够的日志、状态和排查方法，能够定位主要运行问题。

### 8.5 最终发布决策

发布前，由开发者逐项核对发布检查清单，记录：

- 当前版本。
- 测试环境。
- 测试结果。
- 未解决问题。
- 已知限制。
- 发布结论。
- 发布日期。

任何无法验证的项目都应明确标记为“未验证”，不得默认视为通过。

## 9. 阶段总结

阶段 11 的目标是证明 Z-Torque 社区版不仅能够运行，而且能够在可预期的安全边界内运行，并且在出现常见故障时具备明确的处理和恢复策略。

本阶段完成后，应获得：

1. 一份真实的实现情况清单。
2. 一套可重复执行的核心自动化测试。
3. 一份端到端业务链路测试报告。
4. 一份权限与安全检查报告。
5. 一份 Task 故障恢复测试报告。
6. 一份部署、备份和恢复说明。
7. 一份发布验收与已知问题清单。

本阶段仍然遵守 Z-Torque 的核心设计原则：

- 身份与权限贯穿执行链。
- Task 状态与事务边界明确。
- 已发布版本保持不可变。
- 审计关键事件不可关闭。
- 权限决策由内核执行。
- 模型和工具执行必须经过统一网关。

**阶段完成的标志不是所有测试都显示绿色，而是每一项发布结论都有证据支撑，每一个未解决的问题都有明确的影响说明。**

下一步建议进入：**阶段 12——社区版正式发布、安装包与开源仓库交付**。如果实际验收发现核心缺陷，应优先修复并重新测试，而不是为了推进阶段编号直接进入发布。
