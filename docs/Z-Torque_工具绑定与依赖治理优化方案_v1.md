# Z-Torque 工具绑定与依赖治理优化方案

**文档版本：** v1.0

**状态：** 已确认，待实施  
**适用范围：** 社区版控制台（Skill / Agent 创建与编辑）、Tool 注册链路、SkillGateway 执行层  
**上游依据：**

## 一、背景与问题

在当前开发文档与前端实现中，Connector 连接后支持批量将 API / MCP 能力登记为 Tool。但在 Skill 创建、Agent 创建阶段绑定 Tool 时，存在以下明显缺口：

### 1.1 工具选择交互问题

- 仅有单一的下拉选择框
- 工具数量可达上百甚至更多时，无法有效查找
- 没有按 Connector 分组
- 没有搜索、过滤、标签能力
- 没有已选工具的清晰管理与排序

### 1.2 业务 API 参数依赖问题

真实业务系统中，大量接口存在前后依赖关系。例如：

1. 先调用获取 token / 会话 / 租户上下文的接口
2. 再调用「获取客户列表」接口（需要上一步的 token、org_id 等参数）
3. 再调用客户详情、订单等接口

如果只是把每个 API 原样注册为独立原子 Tool，模型在单独调用「获取客户列表」时极易因缺少上下文参数而失败。当前设计缺少对「工具间输入依赖」和「业务封装」的明确治理。

### 1.3 核心约束（必须遵守）

本方案**不破坏**现有核心契约：

- Tool 仍是最小可执行动作
- SkillVersion 精确绑定 ToolVersion
- AgentVersion 精确绑定 SkillVersion
- 所有执行必须经过 SkillGateway
- 不引入完整工作流引擎或 DAG 编排器作为本期目标

---

## 二、总体原则

1. **分层解决**：交互层优先解决「选得出来」；建模层解决「用得正确」。
2. **渐进落地**：先做高价值、低侵入改动，再补依赖元数据与业务封装能力。
3. **对模型友好优先**：暴露给模型的有效工具数量和语义清晰度，比「接口全量开放」更重要。
4. **保持架构稳定**：核心对象关系与执行入口不变。

## 三、方案 A：工具选择器 UX 重做（P0，优先落地）

### 3.1 目标交互形态

Skill / Agent 编辑页的「绑定工具」区域改为双栏 + 搜索过滤结构：

```
┌─────────────────────────────────────────────────────────────┐
│  搜索框（名称 / 描述 / 路径 / 标签）          [按连接器筛选 ▼] │
│  类型：全部 | REST | MCP | DB     标签：客户 订单 库存 …     │
├──────────────────────────────┬──────────────────────────────┤
│  可选工具（按连接器分组）     │  已绑定工具（可拖拽排序）     │
│  ▼ 客户管理系统 (12)         │  1. 查询客户列表              │
│    □ 查询客户列表            │  2. 查询客户订单              │
│    □ 查询客户订单            │  3. …                        │
│  ▼ 订单中心 (8)              │  [移除] [上移] [下移]         │
│    …                         │                              │
└──────────────────────────────┴──────────────────────────────┘
```

### 3.2 功能清单

| 能力                     | 说明                                       | 优先级 |
|--------------------------|--------------------------------------------|--------|
| 按 Connector 分组折叠    | 默认展开最近使用的连接器，其余折叠         | P0     |
| 全文搜索                 | 支持名称、描述、HTTP path、标签            | P0     |
| 多维过滤                 | 连接器、类型（REST/MCP/DB）、业务标签      | P0     |
| 多选 + 已选区            | 左侧勾选，右侧展示已绑定，支持删除与排序   | P0     |
| 工具卡片信息             | 来源连接器、简要参数、是否需确认、引用次数 | P1     |
| 最近使用 / 推荐          | 顶部快速区                                 | P1     |
| 空状态与引导             | 无工具时引导去 Connector 登记              | P1     |

### 3.3 后端支撑接口建议

```
GET /api/tools/selectable
  ?q=关键字
  &connector_id=
  &type=REST|MCP|DB
  &tag=
  &page=&size=
```

返回结构建议按 Connector 分组：

```json
{
  "groups": [
    {
      "connector_id": "...",
      "connector_name": "客户管理系统",
      "tools": [
        {
          "tool_version_id": "...",
          "name": "查询客户列表",
          "description": "...",
          "tags": ["客户"],
          "requires_confirmation": false,
          "param_summary": "page, page_size, keyword"
        }
      ]
    }
  ],
  "total": 128
}
```

SkillVersion 保存时继续只提交精确的 `tool_version_ids`（可带顺序），保持版本不可变原则。

### 3.4 前端改动范围

- 重点改造 Skill 创建/编辑与 Agent 创建/编辑中的「绑定工具」区块
- 不改变「Agent 只绑定 SkillVersion、Skill 绑定 ToolVersion」的层级关系
- 现有 ui-optimized 中的简化下拉应替换为上述选择器

## 四、方案 B：参数依赖与调用链治理

采用「三层组合」策略，避免一开始就上重型工作流引擎。

### 4.1 第一层：业务封装 Tool（强烈推荐，P0/P1）

**核心原则**：不要把所有底层 API 原样暴露给模型。

对强依赖的接口链，由管理员或开发者封装成**业务级 Tool**：

| 场景                         | 错误做法                                      | 正确做法                                           |
|------------------------------|-----------------------------------------------|----------------------------------------------------|
| 查客户列表需要 token + org_id | 暴露 `get_token` + `get_customer_list`        | 封装 `list_customers`，内部自动处理鉴权与上下文    |
| 查客户详情再查订单           | 两个原子 Tool 让模型自己串                    | 封装 `get_customer_with_orders` 或在 Skill 中明确顺序 |

**落地方式**：

- Connector 登记操作时增加「是否封装为业务 Tool」选项
- 支持简单映射/脚本规则，将多个底层调用组合成一个对外 Tool
- 对外只暴露业务参数 Schema，内部参数由系统注入
- 标记 `is_business_tool = true`，便于在选择器中区分

### 4.2 第二层：Skill 层编排强化（P1）

在 SkillVersion 上增加轻量编排信息（软约束，不强制执行引擎）：

```json
{
  "tool_bindings": [
    {
      "tool_version_id": "...",
      "order": 1,
      "role": "prerequisite",
      "note": "必须先调用，获取 access_token"
    },
    {
      "tool_version_id": "...",
      "order": 2,
      "depends_on": ["上一个 tool 的 output.access_token"],
      "note": "使用上一步的 token 填充 Authorization"
    }
  ],
  "orchestration_hint": "先调用认证工具获取 token，再调用客户列表工具，将 token 放入请求头。"
}
```

说明：

- `orchestration_hint` 注入到模型可见的 Skill 描述中，提升正确调用率
- `order` / `depends_on` / `note` 用于控制台展示与辅助校验
- 运行时仍由模型通过 Function Calling 决定实际调用顺序（保持现有模式）

### 4.3 第三层：轻量依赖元数据（P2，中后期）

在 ToolVersion 扩展字段中增加可选依赖声明：

```json
{
  "input_schema": { ... },
  "depends_on": [
    {
      "tool_name": "auth.get_token",
      "output_json_path": "$.access_token",
      "inject_as": "header.Authorization",
      "required": true
    }
  ]
}
```

SkillGateway 可在执行前做检查：

- 若当前上下文中已有对应结果 → 自动注入
- 若缺失且 `required = true` → 返回明确错误，提示模型先调用前置工具

此层可后置，不阻塞前两层上线。

## 五、数据模型与字段调整建议

### 5.1 Tool / ToolVersion

| 字段               | 说明                           | 建议动作          |
|--------------------|--------------------------------|-------------------|
| `connector_id`     | 来源连接器                     | 强制/强化展示     |
| `tags`             | 业务标签数组                   | 新增或强化        |
| `business_domain`  | 客户 / 订单 / 库存等           | 可选新增          |
| `is_business_tool` | 是否业务封装 Tool              | 建议新增          |
| `depends_on`       | 依赖声明（可选）               | P2 新增           |
| `param_summary`    | 给选择器用的简短参数摘要       | 建议新增          |

### 5.2 SkillVersion

| 字段                  | 说明                                           |
|-----------------------|------------------------------------------------|
| `tool_bindings`       | 从简单 id 列表升级为带 order / role / note 的对象数组 |
| `orchestration_hint`  | 给模型的调用顺序与参数传递说明                 |

### 5.3 文档同步更新点

- **阶段 4（Skill / Tool）**：补充「业务封装 Tool」推荐实践与 `tool_bindings` 结构
- **阶段 7（Connector）**：在「登记为 Tool」流程中增加「是否需要业务封装」引导
- **控制台产品说明**：明确「原子 Tool 可以很多，但暴露给模型的有效能力应经过筛选与封装」

## 六、落地优先级与里程碑

| 阶段 | 内容                                                         | 预计工作量                     | 产出                     |
|------|--------------------------------------------------------------|--------------------------------|--------------------------|
| **P0** | 工具选择器重做（分组 + 搜索 + 多选 + 已选区）               | 前端 3–5 人日 + 后端接口 1–2 人日 | 可用选择器               |
| **P0** | Tool 强制携带 connector 信息 + tags，选择器按连接器分组     | 后端小改 + 前端展示            | 分组可用                 |
| **P1** | 业务封装 Tool 机制（Connector 登记时支持简单组合）          | 中等                           | 减少碎片化工具           |
| **P1** | SkillVersion 增加 `orchestration_hint` + 绑定顺序           | 小                             | 模型调用成功率提升       |
| **P2** | `depends_on` 元数据 + SkillGateway 轻量注入/检查            | 中                             | 硬依赖场景覆盖           |
| **P2** | 选择器「最近使用 / 推荐」与引用统计                         | 小                             | 体验优化                 |

## 七、预期效果

| 指标                           | 优化前               | 优化后目标                               |
|--------------------------------|----------------------|------------------------------------------|
| 从 200+ Tool 中找到目标工具    | 困难，依赖记忆       | 10 秒内通过搜索/分组完成                 |
| 强依赖 API 单独调用失败率      | 高                   | 通过业务封装或编排提示显著下降           |
| 管理员配置 Skill 的认知负担    | 高                   | 可按业务域与连接器快速组装               |
| 架构侵入性                     | —                    | 核心契约不变，仅扩展字段与交互           |

## 八、本期明确不做的内容

- 模型侧强制多步规划（仍保持现有 Function Calling 循环）
- 第三方插件市场或动态加载
