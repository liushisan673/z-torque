# Z-Torque 社区版阶段 9：Memory、Conversation 上下文组装与文件附件处理

**文档编号：** ZT-COMMUNITY-P9  
**文档版本：** 1.1（P1/P2 优化）  
**阶段名称：** Memory、Conversation 上下文组装与文件附件处理  
**前置阶段：** 阶段 0—8  
**阶段状态：** 已实施，待阶段验收  
**错误码：** 本阶段引用阶段 0 主表。文件大小和类型错误分别使用 `AI_FILE_TOO_LARGE`、`AI_FILE_TYPE_UNSUPPORTED`；Conversation、Memory、文件和上下文访问必须执行资源归属与权限检查。

## 父子 Task 上下文隔离（本阶段必须实现）

默认只向子 Agent 传递完成子任务所必需的结构化目标、输入引用、权限范围、文件引用和已授权上下文摘要，不自动传递完整 Conversation、父 Agent 私有 Memory 或全部历史消息。子 Task 拥有独立执行上下文，并通过结构化结果、依据摘要、状态和错误回传父 Task。

父子 Task 不默认共享 Memory。任何共享 Memory 必须同时满足原始用户归属、现有 MemoryPolicy、资源权限和生命周期约束；子 Agent 的中间推理不写入共享 Memory。文件访问继续执行用户、Conversation、Task 和文件权限校验，不能因父子关系扩大访问范围。

串行子 Task 之间不直接共享完整 Conversation 或 Memory。父 Agent 负责把前序子 Task 的结构化结果转换为后续子 Task 所需的最小输入，可以使用受权限控制的数据引用、文件引用或临时结果引用。结果引用必须绑定 `root_task_id`、用户身份、有效期和访问策略，任务终止或超时后按生命周期策略失效。

## 1. 阶段目标

本阶段建设 Z-Torque 的对话上下文与记忆管理能力，使 Agent 能够在完整保存对话历史的基础上，选择合适的信息参与当前模型推理，并安全处理用户上传的文件。

本阶段围绕三个核心问题展开：

1. **Conversation**：如何保存完整对话历史，并区分不同 Agent、用户与会话。
2. **Memory**：如何保留近期对话中的重要信息，减少重复询问，同时避免无约束地积累历史内容。
3. **File**：如何接收、保存、解析和使用用户上传的文件，并保证文件内容不能绕过权限和安全策略。

完成后，系统应具备以下能力：

- 完整保存 Conversation 与 Message 历史。
- 将对话上下文与 Task 执行过程分离管理。
- 支持 Working Memory 与 Short-term Memory。
- 按确定的上下文策略组装模型输入。
- 支持自动生成和手动触发短期记忆摘要。
- 默认不启用 Long-term Memory。
- 支持 PDF、TXT、MD、CSV、XLSX、附件。
- 依据文件类型执行相应解析，并对文件访问进行权限检查。
- 将文件内容作为不可信输入处理。
- 支持文件大小限制、敏感信息保护和生命周期管理。
- 让 Memory、Conversation 和 File 与既有 ModelGateway、Task、SkillGateway、Audit 正确集成。

本阶段不建设完整知识库产品。文件可以被当前会话或任务使用，但不等于自动进入全局知识库。

## 3. 技术方案

### 3.1 Conversation、Message、Task 的关系

三者承担不同职责，不应合并成一个对象。

```
User
  │
  ▼
Conversation
  │
  ├── Message 1
  ├── Message 2
  ├── Message 3
  ├── Message 4
  │      │
  │      └── 可触发一个 Task
  │
  ├── Message 5
  └── Memory Summary

Task
  ├── 固定 AgentVersion
  ├── 执行过程
  ├── TaskEvent
  └── 执行结果
```

职责约定：

- **Conversation**：代表用户与某个 Agent 之间的一段对话。
- **Message**：代表一次用户输入、助手回复或其他必要的消息记录。
- **Task**：代表一次需要进入任务运行时执行的工作。
- **Memory**：从历史对话或运行过程提炼出的辅助上下文。
- **File**：独立的文件资源，可以被 Message 引用，也可以在授权后用于 Task。

继续遵循前面已经确定的规则：

1. 一个 Conversation 只绑定一个 Agent。
2. 切换 Agent 时创建新的 Conversation。
3. 一条用户 Message 最多关联一个 Task。
4. 普通闲聊不创建 Task；当模型判断需要调用 Tool 时，才进入任务执行链路。
5. Task 创建后固定使用当时确定的 AgentVersion。
6. Conversation 保存完整历史，但模型默认只使用近期 5 轮对话和必要的记忆摘要。

### 3.2 上下文组装机制

上下文组装不应分散在 Chat API、Worker 和各个 Skill 中，而应由统一的上下文组装模块负责。

建议模块名称为 `ContextBuilder`。

主要输入：

- 当前用户的 SecurityContext。
- 当前 Conversation。
- 当前 AgentVersion。
- 当前用户 Message。
- 当前 Task（如果已经创建）。
- 可访问的 Memory。
- 已授权且当前请求需要使用的附件内容。
- AgentVersion 绑定的 SkillVersion 及其允许暴露的工具定义。

主要输出：

- 符合当前模型接口的消息列表。
- 必要的上下文来源信息。
- 输入 Token 或上下文长度估算。
- 被截断、未加载或无法解析的内容提示。

建议的组装顺序：

```
ContextBuilder
  │
  ├── 1. 系统安全策略
  ├── 2. AgentVersion 固定规则
  ├── 3. 可用的 Short-term Memory 摘要
  ├── 4. 最近 5 轮对话
  ├── 5. 当前用户消息
  ├── 6. 当前请求授权使用的文件内容
  └── 7. 当前 AgentVersion 允许使用的 Tool 定义
          │
          ▼
      ModelGateway
```

注意事项：

- 系统安全策略必须处于受控的系统级消息或等效的可信策略位置，不能被记忆摘要和文件内容覆盖。
- Agent 规则必须来自固定的 AgentVersion，而不是实时读取可能变化的草稿。
- Memory 摘要属于辅助上下文，不具有系统指令级别的权威。
- 近期消息应按时间顺序组织，不能把不同 Conversation 的消息混在一起。
- 文件内容只有在当前用户有权访问、且当前请求需要使用时才加入上下文。
- Tool 定义必须来自当前 AgentVersion 绑定的能力范围，不允许根据文件内容临时扩展权限。

### 3.3 上下文长度控制

模型具有上下文长度限制，因此不能仅按消息条数决定是否发送历史内容。

建议采用以下控制策略：

1. 先读取当前 AgentVersion 的模型配置和上下文限制。
2. 组装系统策略与 Agent 固定规则。
3. 添加可用的 Memory 摘要。
4. 添加最近 5 轮对话。
5. 添加当前消息及必要附件内容。
6. 加入当前允许使用的 Tool 定义。
7. 估算最终上下文长度。
8. 超出预算时，优先压缩或省略较旧的非关键上下文。
9. 不得静默删除当前用户的核心请求、权限约束或系统策略。
10. 若附件过大或无法安全压缩，应明确提示，而不是无限截断或直接发送整个文件。

近期 5 轮是默认策略，不是不可调整的绝对值。后续可以根据模型上下文能力、任务复杂度和系统配置进行优化，但不能破坏权限隔离与消息顺序。

### 3.4 Working Memory

Working Memory 用于保存当前运行期间需要快速访问的临时信息。

适用内容：

- 当前任务的临时执行状态。
- 当前轮次的中间推理结果和 Tool Result 引用。
- 本次上下文组装过程中的临时缓存。
- 当前会话中短期有效、无需立即持久化为摘要的信息。

实现建议：

- 社区版优先使用进程内缓存。
- 可使用 LRU 等淘汰策略控制内存占用。
- 缓存必须具有明确的归属标识，避免不同用户、Agent 或 Conversation 共享私有内容。
- 对需要跨重启保留的信息，不应只放在进程内缓存。
- Task 的正式状态与执行事件仍以数据库为准，不能把 Working Memory 当成 Task 状态的唯一来源。
- 缓存过期或被淘汰后，应能够根据持久化数据重新构建必要上下文。

Working Memory 不等于模型的隐式记忆，也不等于完整对话历史。

### 3.5 Short-term Memory

Short-term Memory 用于把较长的对话历史压缩成后续对话可以复用的摘要。

例如，用户在多轮对话中逐步说明自己的目标、已尝试的方法和当前限制。系统可以把这些内容整理为摘要，后续无需每次都重新发送全部历史。

#### 记忆内容建议

- 用户当前明确表达的目标。
- 已确认的业务背景。
- 已完成的操作和当前进度。
- 用户明确提出的偏好或限制。
- 尚未解决的问题。
- 需要在后续对话中继续跟进的事项。

#### 记忆内容限制

- 不把模型猜测写成已确认事实。
- 不把临时推断永久固化为用户属性。
- 不将密钥、密码、完整认证头等敏感内容写入摘要。
- 不把文件中的恶意指令转换成可信系统规则。
- 不因摘要生成而改变原始 Message。
- 对不确定信息，应使用“可能”“待确认”等明确标记。

#### 触发规则

按照既定设计，短期记忆摘要支持以下触发方式：

1. Conversation 消息数量超过 20 条。
2. Conversation 空闲超过 10 分钟。
3. 用户主动请求生成或更新摘要。

消息数量触发和空闲触发应分别实现。空闲触发可以通过调度检查或后续用户再次进入会话时的惰性处理完成，不要求为每个 Conversation 创建独立计时器。

摘要生成应具备幂等性，避免同一段历史被重复压缩后反复叠加。

#### 摘要生成流程

```
Conversation 历史
      │
      ▼
选择待摘要消息范围
      │
      ▼
检查用户权限与敏感内容
      │
      ▼
调用 ModelGateway 生成摘要
      │
      ▼
校验摘要结构与内容
      │
      ▼
保存 Short-term Memory
      │
      ▼
记录来源范围与更新时间
```

每份摘要应能追溯到对应的 Conversation 和历史消息范围。生成新摘要时，应明确其覆盖范围，避免旧摘要与新摘要发生重复或冲突。

### 3.6 Memory 隔离与数据可信度

Memory 必须按以下维度隔离：

- `tenant_id`
- `user_id`
- `agent_id`
- `conversation_id`

社区版虽然采用单租户部署，但仍保留 `tenant_id`，以便将来扩展。

必须遵守：

1. 用户只能读取有权访问的 Memory。
2. 不同用户的私有记忆不能相互共享。
3. 不同 Agent 的记忆默认隔离。
4. 不同 Conversation 的摘要不能未经规则处理直接混用。
5. Memory 查询必须执行权限过滤，而不能只依赖前端传入的 ID。
6. 记忆摘要中的信息属于模型生成的上下文，不代表经过系统验证的事实。

若未来需要跨会话长期记忆，应单独定义其授权、来源、过期和删除策略。本阶段不默认开启 Long-term Memory。

### 3.7 文件上传与存储

支持以下文件类型：

| 类型     | 格式         | 处理方式                             |
| -------- | ------------ | ------------------------------------ |
| 文本文档 | TXT、MD      | 文本提取                             |
| PDF      | PDF          | 提取可读取文本；扫描件可能需要 OCR   |
| 表格     | CSV、XLSX    | 结构化解析与行列限制                 |

默认单文件上传上限为 50 MB，实际限制必须配置化，并同时受部署环境和解析器资源限制。

存储规则：

- 文件元数据保存到数据库。
- 文件内容保存到 `data/files/{file_id}`。
- 文件 ID 使用 UUIDv7。
- 文件访问必须经过后端授权检查。
- 不直接向客户端暴露任意本地文件路径。
- 不允许仅凭猜测文件 ID 就下载或读取文件。
- 文件删除和清理不能破坏仍被保留的历史任务、审计或业务记录。

建议为文件记录保存：

- 文件 ID。
- 所属用户和租户。
- 原始文件名。
- 检测到的文件类型。
- 文件大小。
- 文件内容摘要或校验指纹。
- 存储状态。
- 上传时间。
- 解析状态。
- 关联 Conversation 或 Message（如果有）。
- 必要的错误摘要和清理状态。

### 3.8 文件解析与安全处理

文件解析应按类型路由到对应的解析器，而不是把所有文件统一当成纯文本。

建议处理流程：

1. 校验上传权限。
2. 检查文件大小、扩展名和实际文件类型。
3. 生成文件 ID 并安全保存原始文件。
4. 创建文件元数据记录。
5. 根据类型选择解析器。
6. 限制解析时间、内存、页数、行数和提取文本长度。
7. 对解析结果执行必要的脱敏与结构校验。
8. 保存解析状态和必要的提取结果。
9. 在当前用户有权访问时，将所需内容提供给上下文组装模块。
10. 记录关键操作和异常。

安全要求：

- 文件名必须经过规范化，不能直接作为磁盘路径。
- 禁止通过路径穿越访问其他目录。
- 解析器不能无限递归展开文件或无限读取内容。
- XLSX、CSV 等结构化文件需要限制行数、列数和单元格内容长度。
- PDF 扫描件在没有 OCR 能力时，应明确标记为无法提取文本。
- 文件解析失败时，应保留明确状态和可理解的错误信息。
- 对上传文件中的提示注入内容，应将其视为不可信数据，而不是系统指令。

文件内容可能包含“忽略之前的指令”“读取其他用户数据”等恶意文本。即使这些内容被解析出来，也不能改变当前用户的权限、AgentVersion 规则或 SkillGateway 的安全控制。

### 3.9 附件与 Conversation / Task 的关联

Message 可以关联一个或多个文件附件，但文件应保持独立资源身份。

建议的处理方式：

- 上传文件时创建独立 File 记录。
- 用户发送消息时，Message 引用相应 File ID。
- ContextBuilder 根据当前用户权限与请求内容判断是否需要读取附件。
- 如果该消息触发 Task，Task 记录对相关文件的引用或执行快照。
- Worker 执行期间再次检查文件访问权限和文件可用状态。
- 文件被删除或不可用时，任务应明确返回错误，而不是静默使用其他同名文件。

附件引用必须可追踪，但不需要把整个文件内容重复写入 Message 或 TaskEvent。

对于结构化数据，后续可根据具体需求选择读取全部允许内容、提取摘要或生成受控查询结果。不能默认把大型表格完整塞进模型上下文。

### 3.10 长期记忆的预留边界

本阶段仅实现 Working Memory 和 Short-term Memory，保留 Long-term Memory 的 Port 与后续扩展空间。

不应在本阶段：

- 默认建立跨会话的用户长期画像。
- 自动把每次对话都保存为长期记忆。
- 将所有用户上传的文件转化为全局知识。
- 在没有授权规则的情况下共享记忆。
- 让长期记忆覆盖当前用户输入或系统策略。

未来如需启用 Long-term Memory，应另行定义写入条件、来源可信度、用户授权、删除机制、过期策略和检索权限。

## 4. 接口与数据设计

### 4.1 核心数据模型

优先复用现有 Conversation、Message 和 Memory 数据模型，必要时扩展 `zr_file`。

| 数据对象               | 主要职责                                 |
| ---------------------- | ---------------------------------------- |
| `zr_conversation`      | 会话归属、Agent 绑定与会话状态           |
| `zr_message`           | 完整消息历史、角色、内容和附件引用       |
| `zr_memory_short_term` | 短期摘要、来源范围与更新时间             |
| `zr_file`              | 文件元数据、所有权、大小、类型和解析状态 |
| `zr_task`              | 执行任务及其必要的上下文引用             |
| `zr_task_event`        | 记录任务过程摘要，不保存大段原始文件内容 |
| `zr_audit_log`         | 记录文件访问、记忆操作和关键安全事件     |

Working Memory 可以优先使用进程内缓存，不必为了临时数据额外建立持久化表。

### 4.2 Conversation 与 Message 约束

- Conversation 必须关联明确的用户和 Agent。
- Message 必须属于一个 Conversation。
- 历史 Message 应完整保存，不因摘要生成而覆盖。
- 消息内容可采用结构化 `content_parts`，支持文本和文件引用。
- Message 可关联附件，但不能仅靠原始文件名定位文件。
- 一条用户 Message 最多关联一个 Task。
- 助手最终答复与 Task 运行结果应分别保存，并保持关联关系。
- 历史消息查询必须执行会话权限检查。

### 4.3 Memory 数据建议

Short-term Memory 至少应能表达：

- Memory ID。
- 所属 `tenant_id`、`user_id`、`agent_id`、`conversation_id`。
- 摘要内容。
- 摘要覆盖的消息范围。
- 来源消息标识或可追踪范围。
- 创建时间和更新时间。
- 摘要生成状态。
- 必要的版本或更新标识。

摘要更新不能直接覆盖或破坏原始消息。若需要保留历史摘要版本，应采用明确的版本记录或更新历史机制，而不是依赖模型自行记住过去的摘要。

### 4.4 建议 API

统一使用 `/api/z-torque/*` 前缀。开发时应优先扩展已有接口。

| 方法     | 路径                                                         | 用途                       |
| -------- | ------------------------------------------------------------ | -------------------------- |
| `GET`    | `/api/z-torque/conversations`                                | 查询当前用户可访问的会话   |
| `GET`    | `/api/z-torque/conversations/{conversation_id}`              | 查询会话详情               |
| `GET`    | `/api/z-torque/conversations/{conversation_id}/messages`     | 分页读取完整消息历史       |
| `POST`   | `/api/z-torque/conversations/{conversation_id}/memory/summarize` | 手动生成或更新短期摘要     |
| `GET`    | `/api/z-torque/conversations/{conversation_id}/memory`       | 查询当前会话的记忆状态     |
| `POST`   | `/api/z-torque/files`                                        | 上传文件                   |
| `GET`    | `/api/z-torque/files/{file_id}`                              | 查询文件元数据             |
| `GET`    | `/api/z-torque/files/{file_id}/content`                      | 在授权后读取或下载文件     |
| `GET`    | `/api/z-torque/files/{file_id}/status`                       | 查询文件解析状态           |
| `DELETE` | `/api/z-torque/files/{file_id}`                              | 请求删除文件或进入清理流程 |

以上接口是职责建议。若前面阶段已经定义了同类路由，应扩展已有接口，不要重复创建相同功能。

### 4.5 API 约束

- Conversation、Message、Memory 和 File 查询均必须检查用户权限。
- 文件上传必须检查类型、大小和存储状态。
- 文件内容接口不能直接接受任意本地路径。
- Memory 接口不能返回其他用户或其他 Agent 的私有摘要。
- 手动摘要接口必须校验会话归属和操作权限。
- 删除文件时应检查引用关系和保留策略。
- API 错误应使用稳定的 `AI_` 错误码。
- 不在接口响应中返回不必要的绝对路径、内部解析器堆栈或敏感内容。

### 6.1 Conversation 与上下文验收

- 

  完整消息历史能够持久化保存。

- 

  会话只绑定一个 Agent。

- 

  切换 Agent 会创建新的 Conversation。

- 

  一条用户 Message 最多关联一个 Task。

- 

  普通闲聊不创建 Task。

- 

  Task 创建后使用固定的 AgentVersion。

-

-

-

### 6.2 Memory 验收

- 

  Working Memory 可以在运行期间保存临时上下文。

- 

  Working Memory 不作为 Task 正式状态的唯一来源。

- 

  超过 20 条消息时可以触发短期摘要。

- 

  空闲超过 10 分钟时可以触发短期摘要。

- 

  用户可以手动触发摘要。

- 

  摘要有明确的来源范围。

-

### 6.3 文件验收

- 

  支持指定类型文件上传。

- 

  默认 50 MB 限制可通过配置调整。

- 

  文件元数据与原始文件能够正确关联。

- 

  文件下载和解析均执行权限检查。

- 

  TXT、MD、PDF、CSV、XLSX 可以按预期解析。


- 

  文件解析超限时能够安全失败。

- 

  文件内容只有在授权且当前请求需要时才加入上下文。

- 

  文件名不能造成路径穿越。

- 

  文件中的恶意指令不能改变系统策略或用户权限。

### 6.4 安全与稳定性验收

- 

  用户无法读取其他用户的私有文件和记忆。

- 

  删除请求不会意外破坏仍需保留的历史记录。

- 

  解析器异常不会导致整个 Runtime 崩溃。

- 

  超大文本和结构化文件受到资源限制。

- 

  敏感信息不会无条件写入摘要、TaskEvent 或 Audit。

- 

  上下文缓存丢失后可以恢复必要的持久化数据。

- 

  文件不可用时，任务能返回明确错误而不是使用错误文件。

- 

  记忆摘要生成失败不会破坏原有对话历史。

## 7. 风险项

| 风险                     | 影响                       | 应对措施                               |
| ------------------------ | -------------------------- | -------------------------------------- |
| 每次发送完整历史         | Token 成本高、上下文超限   | 默认近期 5 轮加摘要                    |
| 摘要生成错误             | 后续回答依据失真           | 保留来源范围，摘要作为辅助上下文       |
| 不同用户记忆串线         | 私有数据泄露               | 按用户、Agent、Conversation 进行隔离   |
| 文件提示注入             | 诱导模型越权               | 文件内容按不可信输入处理               |
| 文件路径处理不当         | 越权读取服务器文件         | UUIDv7 文件 ID、路径规范化和目录约束   |
| 解析器资源消耗过大       | 内存耗尽或服务卡顿         | 限制文件大小、解析时间和提取内容       |
| 文件删除过早             | 历史任务无法追溯           | 检查引用关系并执行可配置清理策略       |
| 长期记忆默认开启         | 产生非预期的跨会话数据保留 | Long-term Memory 默认关闭              |
| 缓存被当成正式状态       | 重启后状态不一致           | Task 与 Message 的正式状态以数据库为准 |
| 附件无条件加入模型上下文 | 隐私暴露与 Token 浪费      | 按权限、请求需要和上下文预算加载       |

## 9. 阶段总结

阶段 9 的核心是建立稳定的上下文管理机制，让 Z-Torque 不只是能够执行任务，还能够在连续对话中合理使用历史信息。

完成后，应形成以下关系：

- Conversation 保存完整对话历史。
- Message 保存用户输入、助手回复及附件引用。
- ContextBuilder 决定哪些信息进入当前模型上下文。
- Working Memory 保存运行期间的临时状态。
- Short-term Memory 压缩并保留近期重要信息。
- File 管理上传文件及其访问权限。
- Task 引用本次执行所需的会话和文件上下文。
- ModelGateway 负责模型调用，SkillGateway 继续控制所有技能与 Tool 执行。

本阶段需要始终坚持三个原则：

1. **保存全部历史，不代表发送全部历史。**
2. **记忆摘要是辅助信息，不是绝对事实，也不能覆盖系统策略。**
3. **文件可被读取，不代表文件内容可信，更不代表文件内容有权触发任何操作。**

下一阶段建议进入阶段 10：Community 控制台与前后端完整集成。届时把前面实现的 Agent、Skill、模型、会话、Connector、审计、Task、Memory 和 File 能力整合到轻量管理界面中，并完成从用户操作到后端执行的端到端验收。
