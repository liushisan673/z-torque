# 1. 阶段目标

## 1.1 建设目标

本阶段的目标是建立 Z-Torque 社区版的统一开发基线，为后续工程搭建、内核开发、Agent 执行、工具接入、控制台建设和最终发布提供明确依据。

完成本阶段后，开发者应当能够：

2. 理解 Kernel、Port、内置实现、Module、Profile 之间的关系。

4. 明确项目目录、代码依赖方向、接口规范和数据建模原则。
5. 明确身份、权限、任务、版本、审计和模型调用的内核约束。
6. 根据阶段开发文档独立完成后续开发，不需要依赖此前的聊天记录。
7. 使用统一的任务清单、测试命令和验收标准判断每个阶段是否完成。

这些内容从阶段 1 开始，按照后续阶段文档逐步实现。

# 2. 需求范围

## 2.1 产品定位

Z-Torque 是独立的 AI Runtime 产品，中文名称为“极矩”。

社区版的定位是：面向中小企业和开发者的、可独立运行的受控 AI 运行平台，能够统一管理模型、Agent、Skill 和外部能力，并对 AI 执行过程中的身份、权限、任务状态及审计进行控制。

Z-Torque 不绑定某个特定的业务系统。它可以独立运行，也可以通过 API 和 Connector 与现有企业管理系统集成。

### 默认父 Agent 与单层协作

社区版支持受控的单层父子 Agent 协作。系统提供一个已发布的默认父 Agent：当用户未在聊天界面选择具体 Agent 时，Chat API 使用该默认父 Agent 的当前有效版本处理请求。默认父 Agent 可以根据请求拆分任务，并在其版本快照声明的授权子 Agent 范围内创建子 Task；子 Agent 继续复用现有 Agent、AgentVersion、Task、ModelGateway、SkillGateway 和 PEP 机制执行。

该能力不等同于开放式 A2A 网络，也不引入可视化工作流编排器。一个用户消息最多创建一个根 Task；根 Task 可以创建多个子 Task，但子 Task 不得继续创建下一层子 Task。子任务继承原始用户 SecurityContext，不得提升权限，结果只能回到父 Task 汇总后再写入用户会话。

社区版首先建设单机、单租户的运行内核及轻量控制台。后续企业版可在保持内核和 Port 契约兼容的基础上，通过官方插件、部署形态和企业级能力扩展产品。

## 2.2 产品架构原则

Z-Torque 采用以下产品形态：

- 一个开源内核。
- 官方能力插件。
- Community 与 Enterprise 两种许可层级。
- 三种预设装配形态。
- 内置控制台为主要管理入口，同时保留 API 优先和前端可替换能力。

社区版不需要在首期实现企业版的所有能力，但必须避免把社区版设计成无法扩展的独立原型。

## 2.3 社区版功能范围

社区版以以下能力为建设目标：

| 能力域     | 社区版范围                                                   |
| ---------- | ------------------------------------------------------------ |
| 内核基础   | 身份上下文、任务状态与事务边界、Agent 版本快照、审计、权限裁决点、模型与技能统一网关 |
| Agent      | 官方 Agent、用户自建 Agent、复制、发布和版本管理             |
| Skill      | 独立 Skill 对象、版本管理、复用及 Tool 绑定                  |
| Tool       | 最小可执行动作、版本管理、权限声明和统一执行入口             |
| 模型       | Provider、Model、Endpoint 管理与统一调用                     |
| MCP        | JSON-RPC 2.0、工具发现与调用、stdio 和 HTTP 传输             |
| MD-Skill   | 指令型和脚本型两种实现方式                                   |
| Connector  | 外部 REST API、只读数据库及连接配置                          |
| 会话       | Conversation、Message、上下文组装和对话流                    |
| 记忆       | Working Memory 和 Short Memory；Long Memory 预留接口，默认不启用 |
| 文件       | 文件上传、元数据、权限校验和按类型处理                       |
| 审计       | 关键操作审计、审计查询及敏感信息脱敏                         |
| 控制台     | 对话、Agent、Skill、模型、连接器、审计六个核心页面           |

以上为整个社区版的目标范围，并不代表这些能力必须在阶段 1 同时实现。

## 2.4 社区版明确不纳入首期的功能

以下能力不作为社区版首期必做功能：

- 完整的可视化流程编排平台。
- A2A 多 Agent 网络网关和跨实例 Agent 网络；本阶段仅支持受控的单层父子 Task 协作。
- Kubernetes 集群编排。
- Kafka、Redis 等独立基础设施依赖。
- Milvus 等独立向量数据库的强制依赖。
- 第三方插件代码的任意动态加载。
- 通用任意代码执行环境。
- 企业级 SSO、LDAP、OIDC 和多租户管理。
- 完整的长期记忆产品。
- 复杂审批流和完整企业治理控制台。
- 语音交互和多媒体生成产品。

若后续确有必要增加，必须先判断其属于内核、Port、Module、官方插件还是企业版能力，再单独评估和排期。

## 2.5 用户与身份边界

社区版虽然是单租户，但允许多个用户并发使用。

必须区分：

- 用户自己的 Conversation 和 Memory。
- 用户可管理的个人资源。
- 全体用户可见的官方资源。
- 管理员可以管理的连接配置和平台资源。

私有会话及记忆应按用户隔离。官方资源可共享，但不可直接修改或删除。用户需要修改官方 Agent、Skill 或 Tool 时，应先复制到自己的资源空间，再独立演进。

所有 AI 执行都必须遵守当前用户身份的权限边界。

本项目首期以 Windows + VS Code 为本地开发环境。

基础要求：

## 3.3 总体架构

Z-Torque 采用模块化单体架构（Modular Monolith）。

模块化单体的含义是：社区版初期可以部署为一个应用进程，但内部代码必须按稳定职责划分模块，避免形成相互依赖的巨大单体代码。

逻辑架构如下：

```
Console / API Client
        |
        v
     API Layer
        |
        v
   Kernel Layer
   |    |    |
Identity Task Audit
   |    |    |
AuthZ  Gateways
        |
        v
    Port Contracts
        |
        v
 Community Built-in Implementations
        |
        v
 Database / Model Providers / MCP / External Systems
```

上图表达逻辑依赖，不代表所有能力在第一阶段就会实现。

## 3.4 Kernel 的职责

Kernel 负责不可被业务插件绕过的基础机制。

内核固定包含六项不变量：

1. Identity & Session：身份和会话上下文。
2. Task State Machine & Transaction Boundary：任务状态机及事务边界。
3. Agent Version Snapshot：Agent 版本快照。
4. Audit Event Stream：审计事件流。
5. Permission Enforcement Point（PEP）：权限执行裁决点。
6. ModelGateway 与 SkillGateway：模型和技能统一拦截、调用及结果标准化。

上述机制必须由内核保证，不能仅依赖 Agent 提示词、前端按钮或插件自身自律。

## 3.5 Port 体系

内核通过 Port 调用外部能力，Port 定义稳定契约，具体实现可以替换。

21 个 Port 分为四组。

### Entry

- `identity.provider`
- `authz.provider`
- `secret.provider`
- `notify.channel`
- `approval.provider`

### Execution

- `model.provider`
- `model.selector`
- `skill.executor`
- `sandbox.driver`
- `connector`
- `queue.driver`
- `lock.provider`

### Information

- `memory.working`
- `memory.short`
- `memory.long`
- `vector.store`
- `knowledge.provider`
- `object.store`

### Cross-cutting

- `interceptor`
- `observability.sink`
- `policy.source`

Port 的详细接口、输入输出、异常类型和版本兼容要求，在阶段 1 的开发文档中固定。

注册规则遵循：

**显式配置 > 插件优先级 > 内置默认 > UNAVAILABLE。**

同优先级存在歧义且未显式指定时，启动失败。必需 Port 缺失时启动失败；可选 Port 缺失时明确标记为 `UNAVAILABLE`，不得伪装成可用。

## 3.6 Profile、Module、Plugin 的边界

- **Profile**：定义一套运行预设及其能力组合。
- **Module**：承载一个相对完整的业务或基础能力域。
- **Plugin**：通过既有 Port 为内核提供具体实现。

新增能力时，必须先分类，不得默认每项功能都创建新 Port。

第三方插件代码动态加载不属于社区版首期范围。内核不得因为未来要支持插件而提前允许任意外部代码进入执行链。

## 3.7 运行形态

社区版首期采用单机运行方式：

- 一个后端应用实例。
- 本地 SQLite 数据库。
- 本地文件目录。
- 进程内事件发布与订阅。
- 进程内任务队列与并发控制。
- 单机任务恢复和超时处理。
- 模型和外部系统通过 Port 接入。

该形态不承诺多实例部署，也不承诺跨机器分布式任务调度。

后续 Enterprise 可以在保持内核与 Port 契约兼容的基础上，替换队列、锁、存储、部署方式和其他基础设施。

## 3.8 架构依赖约束

代码必须遵守以下规则：

1. Kernel 不得导入 `builtin_plugins`。
2. Kernel 不得导入业务 `modules`。
3. API 层负责协议转换，不承担复杂业务流程。
4. 业务模块不能直接绕过 Kernel 调用模型或工具。
5. 所有模型调用必须经过 ModelGateway。
6. 所有 Tool 执行必须经过 SkillGateway。
7. 所有外部能力调用必须经过明确的 Port 契约。
8. 所有安全敏感操作必须进入审计链。
9. 未实现的能力必须显式不可用。
10. 模块之间不得通过直接修改对方内部数据结构来绕过公开服务接口。

# 4. 接口与数据设计

## 4.0 API 与父子任务统一约束

正式 API 前缀固定为 `/api/z-torque`，不得再使用 `/api/v1` 作为正式路径。Chat API 的核心语义保持不变：一个用户消息最多创建一个根 Task；内部子 Task 属于该根 Task 的执行树，不视为新的用户消息。

父子协作相关字段和规则由后续阶段共同遵守：`parent_task_id` 表示直接父 Task，`root_task_id` 表示根 Task，`delegation_depth` 在社区版只能为 0 或 1。Task 创建时固定根 AgentVersion、子 AgentVersion 及授权关系快照；发布新版本不得改变已创建 Task 的执行语义。

父 Agent 的委派能力必须显式开启，并显式列出允许调用的子 Agent 及其已发布版本绑定关系。系统不得因为 Agent 被父 Agent 调用而扩大其 Skill、Tool、Connector、文件、Memory 或数据访问权限。

## 4.1 API 统一规范

后端 API 前缀固定为：

```
/api/z-torque
```

不强制把 `/v1` 写入 URL。API 版本兼容性通过接口契约、字段兼容规则和变更策略管理。

健康检查路径：

```
GET /health
```

健康检查用于判断应用及基础依赖是否正常，不应把“所有可选 Port 都可用”作为应用启动的必要条件。

能力查询路径：

```
GET /api/z-torque/capabilities
```

该接口返回 Port 的解析结果和能力状态，不暴露密钥、密码或其他秘密配置。

## 4.2 统一响应结构

成功响应采用统一格式：

```
{
  "code": 0,
  "message": "ok",
  "data": {},
  "trace_id": "..."
}
```

错误响应同样使用稳定字段，并根据错误类型返回适当 HTTP 状态码。

所有普通 HTTP API 必须返回 `code`、`message`、`data` 和 `trace_id`。成功时 `code` 固定为数字 `0`；失败时 `code` 必须使用统一主表中登记的 `AI_` 错误码。错误消息不得包含堆栈、凭证、密钥、数据库连接信息或内部文件路径。

HTTP 状态码统一映射：400 参数错误，401 认证失败，403 无权访问，404 资源不存在，408 HTTP 处理超时，409 状态或幂等冲突，413 文件过大，415 文件格式不支持，422 业务语义无法处理，429 限流或配额超限，500 未预期内部错误，502 上游响应无效，503 能力暂不可用，504 上游调用超时。

1. 新增错误码必须先在本主表登记：错误码名、HTTP 映射、领域、语义、触发条件、用户可见提示、是否可重试。
2. 不得创建与现有码语义重复的同义码。
3. 已发布错误码的语义与 HTTP 映射原则上不可改变；若必须调整，需升文档版本并给出迁移说明。
4. 各阶段开发文档引用错误码时，只写码名，不重复定义语义。
5. 实现代码中的错误抛出必须使用统一错误工厂或枚举，禁止硬编码字符串错误码。

每个外部请求必须生成或校验 `trace_id`，并贯穿 Task、ModelGateway、SkillGateway、SSE 和审计事件。SSE 建连前使用普通 HTTP 错误，建连后使用包含错误码、消息、任务标识和 `trace_id` 的错误事件；断线重连继续使用 `Last-Event-ID` 和事件序号。

禁止把 Python 堆栈、SQL 原始错误、密码哈希、Access Token、Refresh Token 或供应商密钥返回给客户端。

## 4.3 数据设计原则

### 主键

业务实体采用 UUIDv7。

主键生成必须通过统一方法实现，不允许部分表使用自增整数、部分表使用随机字符串而没有统一约定。

### 租户字段

社区版为单租户，但核心业务对象保留 `tenant_id`，为后续 Enterprise 的多租户兼容预留数据边界。

单租户不等于可以忽略用户级数据隔离。

### 时间字段

可变业务实体通常包含：

- `created_at`
- `updated_at`

不可变事件记录通常只需要：

- `created_at`

所有时间字段应统一采用带时区的时间语义，存储及序列化规则在阶段 1 中进一步固定。

### 删除策略

核心业务对象采用软删除，物理清理默认保留期为 90 天，并允许配置。

但物理清理不能破坏历史 Task、Audit、Agent Version、Skill Version 或 Tool Version 所依赖的记录。存在历史引用时，应保留必要的快照或引用数据。

官方资源不能直接删除。

### 版本

Agent、Skill、Tool 使用整数版本号，如 `v1`、`v2`、`v3`，同一父对象下唯一递增。

已发布的版本是不可变快照。修改内容必须创建新版本，不允许直接修改已经发布的快照。

## 4.5 Agent、Skill、Tool 的关系约束

- Agent 不能直接绑定 Tool。
- Agent Version 绑定具体 Skill Version。
- Skill Version 绑定具体 Tool Version。
- Skill 可以被多个 Agent 复用。
- Tool 可以被多个 Skill 复用。
- Skill 是能力组合包。
- Tool 是最小执行动作。
- MD-Skill 是 Skill 的一种实现类型，不是独立于 Skill 的另一套业务对象。
- Tool 的具体实现类型包括 HTTP、DB_QUERY、MCP、MD_SKILL 执行相关能力；具体执行路径和对象职责在相应阶段文档中固定。
- 官方 Agent、Skill、Tool 不能直接修改；需要复制后再独立修改。
- 复制时保留来源资源 ID 和来源版本 ID。

## 4.6 会话与任务关系

Conversation 与 Message 构成基础对话记录。

一条用户 Message 最多产生一个 Task；闲聊不创建 Task。

当用户从闲聊转入明确任务，且 Agent 判断需要调用工具时，系统创建 Task，并将相关会话上下文带入执行过程。

Conversation 绑定一个 Agent。用户切换 Agent 时创建新的 Conversation。

每个新消息使用当前 Published Agent Version。已创建 Task 则固定使用创建时的 Agent Version，不受后续发布影响。

Task 记录运行过程和执行结果；Message 记录面向用户的对话内容。二者不能混为同一个对象。

## 4.7 幂等、事件与快照

- Chat 请求层使用 `Idempotency-Key` 防止网络重试重复创建任务。
- Task 执行层使用内核幂等机制防止重复执行。
- Task 状态变化必须产生 TaskEvent。
- TaskEvent 保存执行摘要和脱敏后的参数信息，不保存大体积原始敏感数据。
- Skill Version 必须固定绑定 Tool Version。
- Agent Version 必须固定绑定 Skill Version。
- Agent Version 同时保存必要的完整配置快照。
- 模型调用结果应记录所使用的模型、供应商、端点、延迟和用量元数据。

详细字段、索引、外键、唯一约束和迁移脚本在对应阶段确定。

# 7. 风险项

## 7.1 架构过度设计

**风险：** 在社区版尚未跑通核心执行链之前，提前建设企业版的分布式调度、多租户和复杂插件体系。

**应对：**

- 社区版优先采用模块化单体。
- 为未来能力保留稳定 Port，不提前部署复杂基础设施。
- 未进入当前阶段的功能不实现业务流程。
- 所有扩展都必须说明当前收益和维护成本。

## 7.2 内核与插件耦合

**风险：** 内核直接导入某个供应商 SDK 或内置实现，导致后续替换困难。

**应对：**

- 内核只依赖 Port。
- 具体实现放在独立适配模块。
- 使用注册机制装配能力。
- 通过架构测试检查非法依赖。

## 7.3 权限在 AI 链路中丢失

**风险：** 用户通过 Agent 调用模型或 Tool 时，执行链没有继续传递原用户身份。

**应对：**

- 将 `SecurityContext` 作为执行上下文的基础字段。
- API、Task、Worker、Skill 和外部调用必须沿用同一身份链。
- 所有敏感操作在服务端执行权限裁决。
- 不允许通过提示词要求模型“自行判断权限”代替系统权限检查。

## 7.4 版本快照不完整

**风险：** Agent 发布后仍引用可变的 Skill 或 Tool 配置，导致历史执行无法复现。

**应对：**

- Agent Version 固定绑定 Skill Version。
- Skill Version 固定绑定 Tool Version。
- 发布快照不可原地修改。
- 任务创建后固定使用对应 Agent Version。

## 7.5 审计失效

**风险：** 审计只是普通日志，或写入失败时被静默忽略。

**应对：**

- 审计采用独立持久化模型。
- 关键事件必须记录。
- 统一脱敏。
- 不提供关闭审计的开关。
- 后续任务一致性阶段明确审计失败的处理策略。

## 7.6 任务执行与数据库状态不一致

**风险：** 任务创建成功但未进入队列，或进程崩溃后任务永久停留在中间状态。

**应对：**

- 任务创建、事件和 Outbox 采用明确的事务边界。
- 调度器负责处理待发送事件。
- Worker 执行时检查幂等性和任务状态。
- 启动恢复流程必须可测试。

## 7.7 模型供应商差异

**风险：** 不同模型的 API 格式、工具调用格式、错误结构和能力声明存在差异。

**应对：**

- 统一 ModelGateway 契约。
- 使用独立 Provider Adapter。
- 统一错误映射与结果结构。
- 不支持的模型能力明确标记不可用。
- 使用 Mock Adapter 保证自动化测试不依赖外部网络。

## 7.8 开发文档与代码不一致

**风险：** AI 编程工具擅自增加接口、改变字段、替换依赖，造成后续阶段无法复用。

**应对：**

- 每阶段开始前读取正式文档。
- 实现前列出文件变更清单。
- 实现后运行测试并更新文档。
- 未确认的架构变更必须单独提交决策。
- 代码、测试、接口文档和 README 必须描述同一份实际能力。

# 9. 阶段总结

阶段 0 的核心成果不是代码，而是一套能够约束后续开发的工程基线。

完成本阶段后，Z-Torque 社区版应具备清晰且统一的：

- 产品定位与社区版范围。
- 模块化单体架构。
- 技术栈与开发环境。
- Kernel、Port、Module、Plugin 的职责边界。
- 核心数据对象和版本快照原则。
- API、错误码及接口兼容规范。
- 身份、权限、审计与密钥安全基线。
- 阶段推进、测试验收和交付机制。

后续阶段必须遵循以下总原则：

1. 先完成可验证的基础能力，再构建依赖它的业务能力。
2. 先定义接口和数据契约，再实现具体模块。
3. 所有模型调用必须经过 ModelGateway。
4. 所有 Tool 执行必须经过 SkillGateway。
5. 身份与权限不能在执行链中丢失。
6. 已发布的版本快照不可原地修改。
7. 审计不能被关闭或静默绕过。
8. 未实现能力必须明确不可用。
9. 每个阶段都必须有可执行的测试和验收标准。
10. 未经确认，不擅自改变上位契约或扩大阶段范围。

**阶段 0 的最终完成标志：开发者可以仅依靠项目正式文档，理解产品、搭建环境、明确模块边界，并知道后续每个阶段应实现什么、如何验证以及何时算完成。**
