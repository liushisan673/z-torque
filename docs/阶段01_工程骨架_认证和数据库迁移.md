# Z-Torque 社区版阶段 1：工程骨架、配置、数据库与基础安全

**文档编号：** ZT-COMMUNITY-P1  
**文档版本：** 1.1（P1/P2 优化）  
**阶段名称：** 工程骨架、配置、数据库与基础安全  
**适用版本：** Z-Torque Community  
**前置阶段：** 阶段 0《项目基线与工程规范》  
**阶段状态：** 待实施  
**开发原则：** 先建立可验证的工程基础，再承载后续业务能力。

## 父子协作配置基础（本阶段必须提供配置入口）

本阶段只建立父子 Agent 所依赖的配置、身份和权限基础，不提前实现委派执行。

API 前缀统一使用 `/api/z-torque`。配置层必须为以下项提供类型化配置入口（默认值见阶段 0）：

- `default_parent_agent_id`
- `delegation.enabled_global`
- `delegation.max_children_per_root`
- `delegation.max_concurrency`
- `delegation.max_total_timeout_seconds`
- `delegation.max_rounds_per_child`
- `delegation.max_depth`（强制校验 ≤1）
- `delegation.default_child_timeout_seconds`

未确认的默认数值不得被写成固定产品承诺。SecurityContext 必须能够从请求传递到根 Task、子 Task、Worker、ModelGateway、SkillGateway 和 Connector。子 Task 只继承原始用户身份及其有效授权，不得使用 Agent 身份替换用户身份。

# 1. 阶段目标

## 1.1 建设目标

本阶段从空项目目录开始，建立 Z-Torque 社区版的基础工程，使项目具备持续开发、运行、测试和维护的能力。

阶段完成后，系统应当具备：

1. 规范的后端工程结构和前端工程预留结构。
2. 统一的环境配置加载机制。
3. 统一的日志、异常和 API 响应规范。
4. 基于 SQLAlchemy 2.x 的数据库访问层。
5. 基于 Alembic 的数据库版本迁移能力。
6. UUIDv7 主键生成和统一时间处理机制。
7. 基础用户、角色、权限及登录认证能力。
8. Access Token、Refresh Token 和安全退出机制。
9. 本地 Secret Store 的基础能力。
10. 健康检查、能力状态查询和自动化测试。
11. 可重复执行的本地启动、初始化和测试流程。

本阶段结束时，即使 Agent、Skill、Tool 和模型调用功能还没有实现，应用也应能够独立启动、检查配置、访问数据库、完成登录并通过基础测试。

## 1.3 阶段完成标准

完成本阶段后，应能够执行以下完整流程：

```
创建项目环境
    ↓
安装后端依赖
    ↓
加载环境配置
    ↓
执行数据库迁移
    ↓
初始化管理员
    ↓
启动 FastAPI
    ↓
检查健康状态
    ↓
登录获取 Token
    ↓
访问受保护的基础接口
    ↓
退出登录并验证 Token 失效
    ↓
运行自动化测试
```

上述流程必须可重复执行。不能依靠手动修改数据库、临时硬编码密码或人工修补运行状态才能成功。

# 2. 需求范围

## 2.1 工程基础

建立一个模块化单体后端工程。

项目必须具备清晰的职责划分，不能将全部代码集中到 `main.py`，也不能让 API 路由直接编写 SQL、处理密码、生成 Token 或实现业务逻辑。

工程基础包括：

- 应用创建入口。
- 配置管理。
- 数据库引擎与 Session 管理。
- ORM 模型基类。
- 数据库迁移。
- 依赖注入。
- 统一异常处理。
- 日志与请求追踪。
- 基础安全模块。
- 自动化测试框架。

## 2.2 配置管理

系统使用环境变量和本地环境文件管理运行配置。

配置至少覆盖：

| 配置类别 | 主要内容                                                |
| -------- | ------------------------------------------------------- |
| 应用     | 环境名称、应用名称、监听地址、调试模式                  |
| 数据库   | 数据库 URL、连接参数                                    |
| 安全     | Access Token 有效期、Refresh Token 有效期、登录失败阈值 |
| 管理员   | 首次初始化管理员账号                                    |
| 密钥     | 本地 Secret Store 主密钥来源                            |
| 文件     | 文件存储根目录、最大上传大小                            |
| 任务     | 并发数、任务超时的预留配置                              |
| 审计     | 保留天数的预留配置                                      |
| 日志     | 日志级别、输出格式                                      |

任务、审计和文件配置可以在本阶段先建立配置项，但不能因此提前实现对应的业务模块。

所有配置必须经过类型校验。关键配置缺失、格式错误或相互冲突时，应在启动阶段给出明确错误。

## 2.3 数据库与迁移

社区版默认使用 SQLite WAL。

数据库访问必须通过 SQLAlchemy 2.x 管理，所有正式数据库结构变化通过 Alembic 迁移完成。

必须具备：

- 统一数据库连接配置。
- 统一 Session 创建与释放。
- ORM 模型基础类。
- UUIDv7 主键生成。
- 统一时间字段规范。
- 外键、唯一约束和索引定义能力。
- 可重复执行的迁移流程。
- SQLite WAL 初始化。
- 测试数据库隔离机制。

不得通过启动时自动创建全部业务表来代替迁移管理。

正式环境不得依赖 `Base.metadata.create_all()` 隐式建立或更新全部表结构。数据库结构由迁移脚本负责。

## 2.4 基础身份与认证

本阶段实现基础用户认证，包括：

- 用户名和密码登录。
- Argon2id 密码哈希。
- Access Token。
- Refresh Token。
- Token 刷新。
- 登录失败限制。
- 退出登录。
- 基础用户状态检查。
- 基础角色与权限关联结构。

登录策略：

- 连续登录失败达到 5 次后锁定 15 分钟。
- 登录成功后清除连续失败计数。
- 锁定状态必须在服务端校验。
- 密码不能以明文保存。
- Token 不能被写入普通日志。
- Refresh Token 必须支持撤销。
- 已退出或已撤销的 Refresh Token 不得继续刷新会话。

浏览器后续使用 HttpOnly Cookie；API Client 使用 Bearer Token。阶段 1 必须明确两种认证方式的服务端支持边界，控制台页面在阶段 10 实现。

## 2.5 权限体系基础

本阶段建立权限数据结构，但不实现完整的业务资源权限闭环。

角色和权限采用 Resource + Action 模型，例如：

- `agent.read`
- `agent.create`
- `skill.read`
- `model.read`
- `audit.read`

多个必需权限默认采用 AND 关系。

社区版不建立角色继承层级。

本阶段应能识别用户、角色、权限以及它们之间的关系，并提供统一的认证用户上下文。

后续阶段再将权限裁决落实到 Agent、Skill、Tool、Task 和外部调用等真实业务操作中。

## 2.6 Secret Store

Secret Store 用于安全保存模型密钥、Connector 凭证和 MCP 敏感环境变量等信息。

本阶段建立基础实现，要求：

1. 使用本地加密存储。
2. 使用 Fernet 等受支持的对称加密机制。
3. 主密钥通过环境配置提供，不与加密数据保存在同一位置。
4. 数据库和普通配置中只保存 `secret_ref` 等引用。
5. 普通 API 不返回密钥明文。
6. 日志、异常、审计摘要中不得输出密钥。
7. 主密钥缺失或格式错误时，不得静默退化为明文存储。
8. 密钥读取通过统一服务接口，不允许业务模块自行解密数据库字段。

本阶段不接入 Vault 等外部密钥管理服务。

## 2.7 健康检查与能力状态

本阶段提供基础健康检查和能力状态查询。

健康检查用于判断应用是否可以正常服务，包括数据库连接等关键基础依赖。

能力状态查询用于展示内核当前已注册、不可用或尚未实现的能力。

必须区分：

- 应用运行状态。
- 必需基础依赖状态。
- 可选 Port 的可用状态。
- 尚未进入开发阶段的业务能力。

未实现的能力不能伪装成已经可用。

## 2.8 统一日志与错误处理

本阶段遵循阶段 0 的统一错误码主表。认证失败使用 `AI_AUTH_FAILED`，权限不足使用 `AI_FORBIDDEN`，参数校验使用 `AI_PARAM_INVALID`，未知异常使用 `AI_INTERNAL_ERROR`。统一异常处理必须返回 `code`、`message`、`data` 和 `trace_id`，不得返回堆栈或敏感信息。

本阶段建立：

- 统一 Trace ID。
- 统一请求日志。
- 统一异常映射。
- 统一响应格式。
- 敏感字段脱敏。
- 开发环境与生产环境的日志级别控制。

业务异常必须转换为稳定的错误码。未经处理的内部异常必须记录必要的诊断信息，但不能将堆栈返回给客户端。

审计是内核不可关闭的机制。阶段 1 可以建立必要的基础结构和接口，但完整审计事件模型、关键业务事件写入与查询能力在阶段 8 完成。

## 3.3 模块职责

### `app/main.py`

负责应用创建和生命周期管理。

只处理：

- 加载配置。
- 初始化日志。
- 创建 FastAPI 应用。
- 注册中间件。
- 注册路由。
- 注册统一异常处理。
- 在启动和关闭时管理资源。

不得在此处编写用户登录、数据库查询或未来的 Agent 执行逻辑。

### `app/config.py`

负责：

- 环境变量加载。
- 类型校验。
- 默认值。
- 配置分组。
- 关键配置的启动检查。

其他模块通过统一配置对象读取配置，禁止每个模块自行读取 `.env` 或直接访问系统环境变量。

### `app/core/`

放置跨模块共享的基础设施：

- `errors.py`：异常类型及错误码。
- `logging.py`：日志初始化与脱敏规则。
- `ids.py`：UUIDv7 生成。
- `time.py`：统一时间工具。
- `responses.py`：公共响应结构。

这里不能依赖具体业务模块。

### `app/db/`

负责数据库引擎、Session、ORM 基类和公共数据类型。

业务服务不能自行创建多个数据库引擎，也不能自行管理全局 Session。

### `app/models/`

存放 SQLAlchemy ORM 模型。

ORM 模型只描述持久化结构及必要约束，不承担复杂业务流程。

### `app/repositories/`

负责数据库读写封装。

Repository 不应直接返回 SQLAlchemy Session 给 API 层，也不应承担认证策略和权限决策。

### `app/services/`

负责应用级业务逻辑。

本阶段主要实现认证服务。后续阶段再增加任务、Agent、Skill 等服务。

### `app/api/`

负责 HTTP 协议处理：

1. 接收请求。
2. 校验请求数据。
3. 获取认证上下文。
4. 调用 Service。
5. 返回统一响应。

API 路由不直接实现复杂 SQL 和密码处理。

### `app/kernel/`

保留内核公共能力边界。

内核不得导入 `builtin_plugins` 和未来的业务 `modules`。具体依赖关系必须通过明确的契约实现。

## 3.4 配置方案

### 配置文件

项目提供：

- `.env.example`：配置模板，可提交到 Git。
- `.env`：本地实际配置，不提交到 Git。
- `app/config.py`：配置加载和校验逻辑。

示例配置：

```
APP_NAME=Z-Torque
APP_ENV=development
APP_HOST=127.0.0.1
APP_PORT=8000
APP_DEBUG=false

DATABASE_URL=sqlite:///./data/z_torque.db

ACCESS_TOKEN_TTL_MINUTES=30
REFRESH_TOKEN_TTL_DAYS=7
LOGIN_FAILURE_LIMIT=5
LOGIN_LOCK_MINUTES=15

SECRET_STORE_KEY=
SECRET_STORE_DIR=./data/secrets

FILE_STORAGE_DIR=./data/files
MAX_UPLOAD_SIZE_MB=50

LOG_LEVEL=INFO
```

这是配置字段的设计示例。正式实现时应明确哪些字段允许默认值、哪些字段必须由部署者提供。

特别注意：

- `SECRET_STORE_KEY` 不能使用空值启动生产环境。
- 不能把真实密钥填入 `.env.example`。
- 不允许将开发环境默认密码用于生产初始化。
- `APP_DEBUG` 不得在生产环境开启。
- 监听地址、CORS 和 Cookie 安全属性应根据开发及部署环境分别配置。

### 配置加载规则

1. 应用启动时统一加载配置。
2. 使用 Pydantic Settings 或同等方式完成类型校验。
3. 配置格式错误时立即失败。
4. 敏感配置不允许通过日志输出。
5. 生产环境不允许使用不安全的默认密钥。
6. 配置对象应作为依赖传入服务，不允许模块各自维护互相冲突的配置副本。

## 3.5 数据库方案

### 数据库初始化

使用 SQLAlchemy 2.x 创建数据库引擎和 Session 管理机制。

SQLite 模式下：

- 启用 WAL。
- 设置合理的连接超时。
- 开启外键约束。
- 正确处理并发写入与事务。
- 避免把 SQLite 误当成无写入锁限制的数据库。
- 测试数据库与开发数据库相互隔离。

### 事务原则

数据库写操作必须具有明确事务边界。

Repository 不应在内部任意提交事务，使 Service 无法控制多个操作的一致性。

推荐的职责划分：

- Repository：执行数据访问。
- Service：组织业务事务。
- 数据库 Session 管理：保证会话释放和异常回滚。

后续 Task 和 Outbox 的一致性事务由阶段 2 单独设计。

### ORM 基类

统一基类应提供：

- UUIDv7 主键。
- 时间字段。
- 可复用的数据类型和约束规范。
- 与 Alembic 兼容的元数据。

本阶段不要求所有未来业务实体一次性建模。

### Alembic 迁移

数据库结构修改遵循：

1. 修改 ORM 模型。
2. 生成迁移脚本。
3. 人工检查迁移内容。
4. 在测试数据库执行迁移。
5. 验证新建数据库可以从头升级。
6. 验证已有数据库可以升级。
7. 提交模型与迁移脚本。

不允许只修改 ORM 模型而不生成迁移脚本。

## 3.6 UUIDv7 与时间规范

所有核心业务实体使用 UUIDv7。

必须提供统一的 ID 生成函数，并通过测试验证：

- 生成结果符合 UUIDv7 规范。
- 每次调用产生不同 ID。
- 能正确序列化为字符串。
- 数据库存储类型统一。
- API 返回格式统一。

时间规范：

- 内部统一使用带时区的时间对象。
- 数据库和 API 的时间语义必须一致。
- API 时间序列化采用 ISO 8601。
- 不使用本地无时区时间作为跨模块的事件时间。
- 测试使用可控时间或时间注入，避免依赖真实系统时钟。

SQLite 的时间存储能力与 PostgreSQL 不完全相同，必须通过 SQLAlchemy 类型和统一序列化规则保持应用层语义一致。

## 3.7 统一 API 响应

成功响应：

```
{
  "code": 0,
  "message": "ok",
  "data": {},
  "trace_id": "..."
}
```

错误响应：

```
{
  "code": "AI_VALIDATION_ERROR",
  "message": "请求参数不合法",
  "data": null,
  "trace_id": "..."
}
```

规则：

- 成功响应使用 `code = 0`。
- 失败响应使用稳定的 `AI_*` 错误码。
- HTTP 状态码必须与错误性质匹配。
- `trace_id` 用于关联请求日志。
- 不将内部异常堆栈暴露给客户端。
- Pydantic 校验失败应转换成统一错误结构。
- 未知异常统一映射为内部错误，并记录服务端诊断信息。

不得在不同路由中自行设计互不兼容的响应结构。

## 3.8 日志与 Trace ID

每个 HTTP 请求必须能够关联一个 Trace ID。

处理规则：

1. 如果请求携带合法的追踪 ID，按统一规则处理。
2. 如果没有，则生成新的 Trace ID。
3. Trace ID 写入请求上下文。
4. 日志包含 Trace ID、请求路径、耗时和结果状态。
5. 异常日志与请求日志可以关联。
6. 不记录密码、完整 Token、API Key 或密钥明文。

外部调用的追踪字段如何向 ModelGateway、Task 和 SkillGateway 传递，在相应阶段进一步实现。

## 3.9 基础认证设计

### 用户数据模型

`zr_user` 至少需要以下概念字段：

| 字段                 | 说明                       |
| -------------------- | -------------------------- |
| `id`                 | UUIDv7 主键                |
| `tenant_id`          | 单租户社区版仍保留租户标识 |
| `username`           | 登录用户名，具有唯一约束   |
| `password_hash`      | Argon2id 密码哈希          |
| `status`             | 用户状态                   |
| `failed_login_count` | 连续登录失败计数           |
| `locked_until`       | 锁定截止时间，可为空       |
| `created_at`         | 创建时间                   |
| `updated_at`         | 更新时间                   |

正式实现时，应补充用户名长度、大小写规则、索引和状态枚举。

禁止保存明文密码或可逆密码密文。

### 角色与权限

建立以下基础实体：

- `zr_role`
- `zr_permission`
- `zr_user_role`
- `zr_role_permission`

关系：

```
User ──< UserRole >── Role
                         |
                         v
                  RolePermission
                         |
                         v
                    Permission
```

权限采用 `resource.action` 命名。

本阶段可以初始化必要的系统角色和基础权限记录，但完整的业务资源授权及三处权限裁决机制留到阶段 8。

### 会话与 Token

建立独立的认证会话存储，至少能关联：

- 用户 ID。
- Refresh Token 的安全标识或摘要。
- 创建时间。
- 到期时间。
- 撤销时间。
- 最近使用时间。

Refresh Token 不应以可直接使用的明文形式存储在数据库中。应采用安全摘要或等效的不可逆标识，并在刷新时验证。

Access Token 应包含最小必要的身份信息及会话标识。若采用 JWT，应明确签名算法、密钥管理、有效期和撤销策略。

不能仅凭前端传入的用户 ID 认定用户身份。

### 登录接口

建议接口：

| 方法 | 路径                         | 说明             |
| ---- | ---------------------------- | ---------------- |
| POST | `/api/z-torque/auth/login`   | 用户登录         |
| POST | `/api/z-torque/auth/refresh` | 刷新访问令牌     |
| POST | `/api/z-torque/auth/logout`  | 退出当前会话     |
| GET  | `/api/z-torque/auth/me`      | 获取当前登录用户 |
| GET  | `/health`                    | 健康检查         |
| GET  | `/api/z-torque/capabilities` | 查询能力状态     |

请求与响应模型必须由 Pydantic Schema 定义。

浏览器 Cookie 模式应正确处理 `HttpOnly`、`Secure`、`SameSite` 和 CSRF 风险。API Client 模式使用 Bearer Token。

不应在同一个接口中模糊混合 Cookie 与 Bearer 的优先级；具体认证来源应有明确规则。

### 登录失败限制

登录失败达到 5 次后，账号锁定 15 分钟。

必须测试：

- 连续失败会触发锁定。
- 锁定期间不能登录。
- 锁定到期后可重新尝试。
- 登录成功后失败计数清零。
- 不泄露用户名是否存在等不必要信息。
- 并发登录失败不会因简单的内存计数而失效。

在本阶段使用数据库保存计数和锁定时间，避免服务重启后锁定状态丢失。

## 3.10 Secret Store 设计

### 数据与密钥分离

Secret Store 负责加密和解密秘密值。

业务数据库只存引用，不保存秘密明文。

建议接口：

- `put_secret(value) -> secret_ref`
- `get_secret(secret_ref) -> value`
- `delete_secret(secret_ref)`

这些是内部服务接口，不是允许普通用户读取秘密明文的公共 HTTP API。

### 加密要求

- 使用成熟加密库。
- 每个秘密值都必须通过认证加密机制保护。
- 主密钥不得写入业务数据库。
- 不允许使用固定硬编码密钥。
- 解密失败必须显式报错。
- 不允许将秘密值拼接到异常消息中。
- 不允许将秘密值写入审计摘要。

后续模型、MCP 和 Connector 模块只能使用 Secret Store 提供的接口，不得直接读取密钥文件。

## 3.11 Port 注册与能力查询的基础设计

本阶段建立 Port 的基础描述结构及能力查询机制，但不实现全部 21 个 Port 的业务功能。

基础能力描述应支持：

- Port 名称。
- 是否必需。
- 是否已注册。
- 当前状态。
- 实现来源。
- 不可用原因。

状态至少能够表达：

- `AVAILABLE`
- `UNAVAILABLE`

后续可根据运行需要扩展更细的状态。

解析规则遵循内核契约：

**显式配置 > 插件优先级 > 内置默认 > UNAVAILABLE。**

相同优先级存在歧义且没有显式配置时，应启动失败。

必需 Port 缺失时必须拒绝启动；可选 Port 缺失时可以启动，但必须标记不可用，调用时返回 `AI_CAPABILITY_UNAVAILABLE` 并进入审计链。

由于完整业务 Port 会在后续阶段逐步接入，本阶段必须区分“尚未进入实现阶段”和“已经实现但当前配置不可用”，不得将二者混为一谈。

- 权限编码唯一。

- 角色权限关系不能重复。
- Refresh Token 会话标识唯一。

3. 不允许在源代码中硬编码管理员密码。

5. 首次密码来源应通过受控环境变量或安全的交互式输入提供。

7. 管理员角色和初始权限必须通过可追踪的初始化逻辑建立。

## 4.5 API 认证行为

### 未认证请求

请求访问受保护接口时：

- 无 Token：返回 `401`。
- Token 无效或过期：返回 `401`。
- 会话已撤销：拒绝请求。
- 不得仅因请求中存在 `user_id` 就允许访问。

### 已认证但无权限

当用户已认证，但不具备对应权限时：

- 返回 `403`。
- 不泄露敏感资源的内部信息。
- 后续阶段必须将此类裁决纳入统一权限与审计链。

### Refresh Token

刷新接口必须验证：

- Token 格式。
- 签名或安全摘要。
- 过期时间。
- 会话是否撤销。
- 用户是否仍处于有效状态。

刷新策略应明确是否轮换 Refresh Token。推荐采用刷新轮换，并在检测到已使用的旧 Refresh Token 再次使用时，按安全策略撤销关联会话。

## 4.6 健康检查接口

```
GET /health
```

成功响应示例：

```
{
  "code": 0,
  "message": "ok",
  "data": {
    "status": "healthy",
    "database": "healthy"
  },
  "trace_id": "..."
}
```

数据库异常时应返回非健康状态和适当 HTTP 状态码。

不得在健康检查中返回数据库连接字符串、密钥、服务器敏感路径或完整内部异常。

## 4.7 能力查询接口

```
GET /api/z-torque/capabilities
```

返回内容应包含：

- 当前应用版本。
- 社区版运行模式。
- 已注册 Port。
- Port 的可用状态。
- 不可用原因摘要。
- 尚未实现的能力标记。

响应不得包含秘密配置或可被用于攻击的内部敏感信息。

# 7. 风险项

## 7.1 数据库迁移与 ORM 不一致

**风险：** 模型修改了，但迁移文件没有同步；本地能运行，干净环境无法启动。

**应对：**

- 所有结构变更通过 Alembic。
- 每次交付都验证从零迁移。
- 检查迁移文件是否被提交。
- 不以本地已有数据库能够运行作为验收依据。

## 7.2 SQLite 并发限制

**风险：** SQLite 在高并发写入时出现锁竞争，开发者误以为只要使用异步框架就不会阻塞。

**应对：**

- 明确 SQLite WAL 的能力边界。
- 为写操作设置合理的超时和事务范围。
- 不长时间持有写事务。
- 不在数据库事务中等待外部模型响应。
- 在后续任务调度阶段设计可恢复机制。

## 7.3 Token 被错误处理

**风险：** Token 写入日志、Refresh Token 长期有效，或者退出登录后仍可刷新。

**应对：**

- 明确 Access 与 Refresh Token 的生命周期。
- Refresh Token 采用可撤销会话设计。
- 敏感字段统一脱敏。
- 编写撤销、过期和重放测试。

## 7.4 管理员初始化不安全

**风险：** 硬编码管理员密码，或重复执行初始化命令覆盖现有账号。

**应对：**

- 使用安全的初始化流程。
- 不设置可公开预测的生产默认密码。
- 已初始化时拒绝隐式重置。
- 不记录初始化凭证。

## 7.5 Secret Store 主密钥丢失

**风险：** 已保存的密钥无法解密。

**应对：**

- 文档说明主密钥备份和恢复要求。
- 生产部署时要求安全保存主密钥。
- 密钥轮换策略后续另行设计。
- 不将密钥备份放在公开仓库或同一明文配置文件中。

## 7.6 基础工程过早承载业务

**风险：** 在数据库、认证和依赖边界未稳定前，提前开发大量 Agent、Tool 和模型逻辑，导致重复重构。

**应对：**

- 本阶段只完成明确范围内的基础能力。
- 后续模块按照阶段顺序建设。
- 不为了提前演示而跳过接口契约。
- 不将临时实现直接视为最终架构。

## 7.7 权限系统只做了数据表

**风险：** 系统虽然有 Role 和 Permission 表，但业务接口没有真正检查权限。

**应对：**

- 本阶段明确这是基础结构，不宣称完整授权闭环已经完成。
- 受保护接口必须先完成身份认证。
- 角色权限关系在数据层建立。
- 阶段 8 必须补齐统一权限裁决、资源过滤和 Skill 调用前检查。

## 7.8 Port 状态被错误表达

**风险：** 系统把未实现的能力显示为可用，或缺失必需能力仍然正常启动。

**应对：**

- 能力状态必须来自真实注册和配置结果。
- 区分未实现、未配置和运行失败。
- 必需 Port 缺失必须启动失败。
- 可选 Port 不可用时必须明确返回错误，不得静默降级。
