## 父子 Task 数据预留（本阶段必须实现）

Task 数据模型必须实现以下父子关系字段：

| 字段 | 类型原则 | 说明 |
|:---|:---|:---|
| `parent_task_id` | UUID / NULL | 直接父 Task；根 Task 为 NULL |
| `root_task_id` | UUID | 根 Task ID；根 Task 指向自身 |
| `delegation_depth` | INT | 社区版仅允许 0（根）或 1（子） |
| `child_sequence` | INT / NULL | 同一父下的子任务序号，从 1 开始 |
| `delegation_id` | UUID / NULL | 一次委派请求的幂等标识 |
| `depends_on_task_ids` | JSON 数组 / NULL | 串行前置子 Task 列表（阶段 8 完整治理） |

根 Task 的 `parent_task_id` 为空且 `root_task_id` 指向自身；子 Task 必须指向同一根 Task。服务层必须拒绝跨根关联、循环关联和深度大于 1 的创建。

子 Task 必须通过现有 Task 创建服务进入队列、Outbox 和 Worker，不得直接调用 Agent 执行器。创建接口应支持幂等键，幂等范围至少覆盖同一根 Task、同一委派请求和同一子任务序号，避免重复消费产生重复子 Task。

父子状态聚合、取消传播和资源治理由阶段 8 完成；本阶段只完成数据表达与创建约束。

# 1. 阶段目标

## 1.1 建设目标

阶段 1 已经建立基础工程、数据库、认证和配置能力。本阶段开始构建 Z-Torque 的任务内核。

后续 Agent、Skill、Tool、ModelGateway 和 MCP 等能力，都将依赖任务内核提供统一的运行边界。

本阶段必须完成：

1. Task 核心数据模型。
2. Task 状态机与合法状态迁移。
3. Task 创建、查询、取消等基础服务。
4. TaskEvent 任务事件记录。
5. Outbox 事务消息机制。
6. 基于数据库的任务调度与进程内 Worker 执行框架。
7. 任务幂等与重复执行保护。
8. 任务超时、协作式取消和异常处理。
9. 服务启动后的任务恢复机制。
10. 任务状态和事件的查询接口。
11. 可用于后续 SSE 的事件序号和断点续传基础。
12. 针对状态机、事务一致性和故障恢复的自动化测试。

本阶段不接入真实模型，也不执行实际 Skill 或 Tool。通过可控的模拟执行器验证任务内核。

## 1.2 核心设计原则

### 原则一：Task 是执行单元，不是普通聊天消息

Conversation 和 Message 属于用户交互层；Task 属于 Runtime 执行层。

同一条 Message 最多触发一个 Task，一个 Task 可以包含多轮模型调用和多个 Tool Call。

阶段 2 不实现完整聊天链路，但必须为未来的消息触发任务预留关联字段。

### 原则二：状态只能通过合法迁移改变

所有状态更新都必须经过统一的状态迁移服务。

禁止 API、Worker 或其他模块直接随意修改 Task 的状态字段。

### 原则三：任务创建与执行投递必须具有一致性

创建 Task、写入初始 TaskEvent、创建 Outbox 记录，必须在同一个数据库事务中完成。

不能先提交 Task，再依靠另一个独立步骤发送任务；否则进程可能在两个步骤之间崩溃，造成任务永远没有被执行。

### 原则四：执行允许重试，业务副作用必须有边界

本阶段不承诺所有外部操作都能做到数学意义上的“恰好执行一次”。

系统通过幂等键、状态检查、条件更新和可恢复调度，避免同一个 Task 被多个 Worker 重复启动。

未来 Skill/Tool 执行时，外部写操作还必须有独立的幂等或确认策略。

### 原则五：终态不可逆

进入终态的 Task 不得再被改回运行中，也不能通过普通接口修改最终结果。

### 原则六：运行记录不能依赖进程内存

进程内队列只负责短期调度，数据库中的 Task、TaskEvent 和 Outbox 才是可靠运行状态的依据。

即使进程重启，也必须能够根据数据库恢复未完成的任务。

## 2.2 社区版运行模式

本阶段采用单机、单应用实例的运行模式：

- FastAPI 提供 HTTP API。
- 数据库持久化任务状态。
- Outbox Scheduler 定期扫描待投递记录。
- 进程内 `asyncio.Queue` 暂存可执行任务。
- Worker Pool 负责执行任务。
- `asyncio.Semaphore` 限制并发数。
- 数据库状态用于防止重复领取。
- 应用启动时恢复未完成任务。

默认 Worker 并发数为 10，通过配置调整。

本阶段不引入 Redis、Celery、Kafka 或其他独立消息中间件，也不宣称已经支持多实例分布式执行。

## 3.2 Task 状态机

### 状态定义

本阶段采用以下状态：

| 状态               | 含义                           | 是否终态 |
| ------------------ | ------------------------------ | -------- |
| `PENDING`          | 任务已创建，尚未进入执行队列   | 否       |
| `QUEUED`           | 任务已投递，等待 Worker 领取   | 否       |
| `RUNNING`          | 任务正在执行                   | 否       |
| `WAITING_HUMAN`    | 任务等待用户确认               | 否       |
| `CANCEL_REQUESTED` | 已请求取消，正在等待执行器停止 | 否       |
| `SUCCESS`          | 任务成功完成                   | 是       |
| `FAILED`           | 任务执行失败                   | 是       |
| `TIMEOUT`          | 任务超过允许执行时间           | 是       |
| `CANCELLED`        | 任务已取消                     | 是       |

其中，`CANCEL_REQUESTED` 用于表达“取消请求已发出，但执行器尚未确认停止”，避免把发出取消请求误认为任务已经停止。

### 合法状态迁移

```
PENDING
   │
   ├──> QUEUED
   │      │
   │      ├──> RUNNING
   │      │      │
   │      │      ├──> SUCCESS
   │      │      ├──> FAILED
   │      │      ├──> TIMEOUT
   │      │      ├──> WAITING_HUMAN
   │      │      └──> CANCEL_REQUESTED
   │      │
   │      └──> CANCELLED
   │
   └──> CANCELLED

WAITING_HUMAN
   ├──> QUEUED       用户确认后重新排队
   ├──> SUCCESS      用户拒绝后以业务结果结束
   └──> CANCELLED    任务被取消

CANCEL_REQUESTED
   ├──> CANCELLED   执行器确认已停止
   ├──> SUCCESS     执行器确认任务已正常完成
   ├──> FAILED      执行器确认任务执行失败
   └──> TIMEOUT     超时策略确认任务已终止
```

说明：

1. 状态迁移必须由统一迁移服务执行。
2. 用户拒绝人工确认不等于技术异常，可以用 `SUCCESS` 表示“任务已按拒绝决策结束”，同时在结果中标记业务结果为拒绝。
3. `CANCEL_REQUESTED` 不能无限期停留，必须由执行器协作取消或超时恢复策略处理。
4. 不允许从 `SUCCESS`、`FAILED`、`TIMEOUT` 或 `CANCELLED` 迁移回非终态。
5. 每次成功迁移必须记录 TaskEvent。
6. 状态迁移失败不得伪造事件。

### 状态迁移的唯一入口

建议提供统一内部接口：

```
transition_task(
    task_id,
    expected_state,
    target_state,
    event_type,
    event_summary
)
```

此处是接口设计示意，不是要求照抄某个具体函数签名。

该接口必须：

- 检查当前状态。
- 检查迁移是否合法。
- 防止并发覆盖。
- 在同一事务内更新状态并记录事件。
- 对已终止的 Task 拒绝非法变更。
- 返回明确的迁移结果。

所有 Worker、Scheduler、取消处理和未来人工确认流程都必须通过该入口迁移状态。

## 3.3 Task 核心数据模型

### `zr_task`

Task 是运行时执行单元。

至少包含以下概念字段：

| 字段                  | 类型原则     | 说明                           |
| --------------------- | ------------ | ------------------------------ |
| `id`                  | UUIDv7       | 任务主键                       |
| `tenant_id`           | 统一租户标识 | 社区版保留该字段               |
| `owner_user_id`       | 用户 ID      | 任务所有者                     |
| `conversation_id`     | UUIDv7，可空 | 所属对话，供后续阶段关联       |
| `message_id`          | UUIDv7，可空 | 触发任务的消息，供后续阶段关联 |
| `agent_id`            | UUIDv7       | Agent 标识                     |
| `agent_version_id`    | UUIDv7       | 任务固定使用的 Agent 版本      |
| `status`              | 状态枚举     | 当前状态                       |
| `idempotency_key`     | 字符串       | 请求幂等标识                   |
| `request_summary`     | 文本或 JSON  | 脱敏后的任务输入摘要           |
| `result`              | JSON，可空   | 任务运行结果                   |
| `error_code`          | 字符串，可空 | 最终错误码                     |
| `error_message`       | 文本，可空   | 脱敏后的错误说明               |
| `created_at`          | 时间         | 创建时间                       |
| `updated_at`          | 时间         | 更新时间                       |
| `started_at`          | 时间，可空   | 开始时间                       |
| `finished_at`         | 时间，可空   | 结束时间                       |
| `deadline_at`         | 时间，可空   | 任务截止时间                   |
| `cancel_requested_at` | 时间，可空   | 取消请求时间                   |
| `attempt_count`       | 整数         | 调度或执行尝试计数             |
| `last_event_seq`      | 整数         | 当前任务最新事件序号           |

重要约束：

- `owner_user_id` 必须来源于服务端认证上下文，不能相信客户端自行传入的所有者 ID。
- `agent_version_id` 表达任务绑定的固定版本，不能在运行过程中自动切换到最新版本。
- 阶段 3 才完整建设 AgentVersion，因此阶段 2 可以先保留版本引用字段；在 AgentVersion 尚未实现时，测试执行器使用受控的测试版本标识。进入正式 Agent 执行前，阶段 3 必须补齐有效版本校验和外键约束。
- `conversation_id` 和 `message_id` 在当前阶段可以为空，但正式聊天任务链路必须建立关联。
- 结果和错误信息必须经过脱敏，不能保存完整秘密值。

### 幂等约束

建议使用以下唯一性约束：

```
UNIQUE(tenant_id, owner_user_id, idempotency_key)
```

同一用户在同一租户范围内，使用相同幂等键重复提交请求时，应返回已创建的 Task，而不是再次创建新任务。

幂等键必须具有合理的长度限制和格式校验。

不能只在 Python 代码里先查询是否存在，再插入记录。并发情况下必须由数据库唯一约束兜底。

## 3.4 TaskEvent 设计

### `zr_task_event`

TaskEvent 用于记录单个 Task 的运行轨迹。

字段建议：

| 字段              | 说明               |
| ----------------- | ------------------ |
| `id`              | UUIDv7 主键        |
| `tenant_id`       | 租户标识           |
| `task_id`         | 所属 Task          |
| `seq`             | 任务内递增序号     |
| `event_type`      | 事件类型           |
| `from_state`      | 迁移前状态，可空   |
| `to_state`        | 迁移后状态，可空   |
| `summary`         | 简短事件说明       |
| `payload_summary` | 脱敏后的结构化摘要 |
| `trace_id`        | 关联请求或运行链路 |
| `created_at`      | 事件创建时间       |

唯一约束：

```
UNIQUE(task_id, seq)
```

事件记录以追加为主，不允许通过普通业务接口修改历史事件。

事件至少包含：

- `TASK_CREATED`
- `TASK_QUEUED`
- `TASK_STARTED`
- `TASK_STATE_CHANGED`
- `TASK_CANCEL_REQUESTED`
- `TASK_CANCELLED`
- `TASK_COMPLETED`
- `TASK_FAILED`
- `TASK_TIMEOUT`
- `TASK_RECOVERED`
- `OUTBOX_RETRY`

后续阶段会扩展模型调用、Skill 调用、工具结果和人工确认等事件。

### 事件序号

同一 Task 的事件序号必须严格递增。

分配序号时需要考虑并发写入。建议在事务中锁定或条件更新 Task 的事件序号字段，再写入事件。

SQLite 下应通过事务和写入竞争处理保证序号唯一；不能依赖内存计数器。

### 事件数据原则

TaskEvent 记录的是执行摘要，而不是无限量的原始数据。

不得直接记录：

- API Key。
- Access Token 或 Refresh Token。
- 密码。
- Secret Store 解密结果。
- 未脱敏的敏感业务参数。
- 超大模型输出全文。

后续 Tool 调用只记录脱敏参数摘要和结果摘要；必要的大结果应使用文件或对象存储引用。

TaskEvent 与正式审计日志 `zr_audit_log` 的职责不同。TaskEvent 负责任务运行轨迹，审计日志负责安全、权限和关键操作留痕。

## 3.5 Outbox 设计

### 为什么需要 Outbox

以下实现不可靠：

```
创建 Task
    ↓
提交数据库事务
    ↓
向内存队列投递
```

如果进程在提交事务后、队列投递前崩溃，数据库中会存在任务，但任务不会执行。

因此必须采用 Outbox 模式。

### `zr_outbox`

字段建议：

| 字段             | 说明                               |
| ---------------- | ---------------------------------- |
| `id`             | UUIDv7 主键                        |
| `tenant_id`      | 租户标识                           |
| `aggregate_type` | 聚合对象类型，例如 TASK            |
| `aggregate_id`   | 对应 Task ID                       |
| `event_type`     | 投递事件类型                       |
| `payload`        | 最小必要的内部投递数据             |
| `status`         | PENDING、PROCESSING、SENT、DEAD 等 |
| `attempt_count`  | 投递尝试次数                       |
| `next_retry_at`  | 下次重试时间                       |
| `last_error`     | 脱敏错误摘要                       |
| `created_at`     | 创建时间                           |
| `updated_at`     | 更新时间                           |
| `sent_at`        | 成功投递时间，可空                 |

建议为待投递记录建立查询索引。

Outbox 的 `payload` 不应复制完整用户输入或敏感参数；通常只需要任务 ID 和执行所需的最小元信息。

### 创建事务

Task 创建必须在同一个数据库事务中完成：

1. 插入 Task。
2. 插入初始 TaskEvent。
3. 插入 Outbox。
4. 提交事务。

只要其中任一步失败，整个事务都必须回滚。

### 调度流程

```
Scheduler 定期扫描
    ↓
查找到期的 PENDING Outbox
    ↓
在事务内认领记录
    ↓
投递 task_id 到进程内队列
    ↓
记录投递结果
    ↓
Worker 领取并校验 Task
    ↓
执行任务
```

由于队列是进程内的，不能把 `SENT` 理解为任务已经成功完成。它只表示该次调度投递已经发生。

如果进程在投递后、Worker 开始前崩溃，恢复机制必须根据 Task 状态重新安排任务。

### 重试策略

采用有上限的指数退避，例如：

```
第一次失败：短暂等待
后续失败：逐步增加等待时间
达到最大次数：标记 DEAD 并产生可查询错误
```

具体初始间隔、最大间隔和最大重试次数由配置确定。

进入 `DEAD` 不意味着可以删除 Task。系统必须保留失败记录，并提供可诊断的状态和事件。

对于仍然处于可恢复状态的 Task，恢复逻辑可以重新建立 Outbox 投递记录。

## 3.6 Worker 执行框架

### 执行器接口

本阶段定义统一的任务执行器接口。

概念上至少包括：

- 接收 Task 执行上下文。
- 执行任务。
- 返回标准结果。
- 支持协作式取消。
- 将可恢复错误和不可恢复错误区分开。

本阶段只实现一个模拟执行器，用于验证状态机和调度，不调用真实模型。

### 标准执行结果

成功结果示例：

```
{
  "success": true,
  "data": {
    "message": "模拟任务执行成功"
  },
  "error": null,
  "metadata": {
    "duration_ms": 120
  }
}
```

失败结果示例：

```
{
  "success": false,
  "data": null,
  "error": {
    "code": "AI_TASK_EXECUTION_FAILED",
    "message": "任务执行失败"
  },
  "metadata": {
    "retryable": false
  }
}
```

这只是任务执行器的内部结果约定，不是最终 Chat API 响应格式。

### Worker 执行顺序

1. 从队列获得 Task ID。
2. 检查 Task 是否存在。
3. 检查 Task 是否已经进入终态。
4. 通过条件更新或事务竞争确认自己获得执行权。
5. 将状态迁移到 `RUNNING`。
6. 设置 `started_at` 和执行截止时间。
7. 生成运行上下文。
8. 调用执行器。
9. 根据执行结果和当前取消状态决定最终状态。
10. 写入结果、结束时间和 TaskEvent。
11. 释放执行资源。

Worker 不得直接跳过状态机更新，也不得仅根据队列消息判断 Task 仍然需要执行。

### 并发限制

通过 `asyncio.Semaphore` 限制并发执行数量，默认 10。

并发限制只是资源控制，不能代替数据库级的领取保护。

多个 Worker 同时拿到同一 Task ID 时，只有成功完成合法状态认领的一方可以执行。

## 3.7 任务幂等与执行保护

本阶段必须区分三个概念。

### 请求幂等

防止客户端网络重试导致重复创建 Task。

机制：`Idempotency-Key` 加数据库唯一约束。

### 调度幂等

防止 Scheduler 因重复扫描 Outbox 而重复投递任务。

机制：Outbox 状态、条件更新、投递状态检查。

### 执行幂等

防止同一 Task 被多个 Worker 同时执行。

机制：Task 状态检查、条件更新、事务保护。

这三层不能互相替代。

对于未来会产生外部副作用的 Tool 调用，仅靠 Task 层幂等仍然不够。外部操作需要在 SkillGateway 和 Tool 层继续实现自己的调用幂等、确认与重试边界。

## 3.8 超时处理

每个 Task 必须具有明确的执行截止时间。

默认任务超时应由配置控制，例如默认 300 秒。具体值可以在阶段实施时结合测试结果确定，但不能没有上限。

超时处理要求：

1. Worker 执行期间能够识别截止时间。
2. 到达截止时间后请求执行器取消。
3. 支持取消的执行器应尽快停止。
4. 不支持取消的外部请求不得被假定为已经停止。
5. 任务状态和事件必须准确反映最终结果。
6. 终态只能由合法状态迁移写入。
7. 超时错误使用稳定错误码 `AI_TASK_TIMEOUT`。

不能仅使用 `asyncio.wait_for()` 就宣称外部副作用已经终止。超时后仍在外部系统执行的请求，必须在后续 Tool 设计中单独处理。

## 3.9 协作式取消

用户取消任务时，首先发出取消请求，而不是直接将任意运行中的任务标记为 `CANCELLED`。

处理流程：

```
用户提交取消请求
    ↓
验证用户身份和任务所有权
    ↓
验证任务当前状态
    ↓
记录 TASK_CANCEL_REQUESTED
    ↓
通知 Worker / 执行器取消
    ↓
执行器确认停止
    ↓
状态迁移为 CANCELLED
```

不同状态的处理规则：

- `PENDING`：可以直接取消。
- `QUEUED`：可以取消，并确保 Worker 不再启动该任务。
- `RUNNING`：进入 `CANCEL_REQUESTED`，请求执行器协作停止。
- `WAITING_HUMAN`：可以取消等待中的任务。
- 终态：返回任务已经结束，不再修改状态。
- `CANCEL_REQUESTED`：重复取消请求应幂等处理。

如果外部调用无法立即停止，应保留取消中状态并继续跟踪。不能为了让接口立即返回成功而伪造任务已经停止。

## 3.10 进程启动恢复

应用启动时，恢复服务必须检查数据库中的未完成任务。

### 恢复规则

| 数据状态                   | 恢复策略                                     |
| -------------------------- | -------------------------------------------- |
| Outbox 为 `PENDING` 且到期 | 重新进入调度                                 |
| Task 为 `PENDING`          | 确保存在可调度记录                           |
| Task 为 `QUEUED`           | 重新投递到进程内队列                         |
| Task 为 `RUNNING`          | 根据执行器恢复能力决定恢复、重试或失败       |
| Task 为 `WAITING_HUMAN`    | 保持等待，不自动执行                         |
| Task 为 `CANCEL_REQUESTED` | 恢复取消处理；无法确认停止时不能直接假定成功 |
| Task 为终态                | 不重新执行                                   |

### RUNNING 任务恢复策略

本阶段的模拟执行器不具有跨进程恢复运行现场的能力。

因此，如果进程重启后发现某个模拟任务仍处于 `RUNNING`，应根据执行策略将其标记为失败或重新排队，并写入 `TASK_RECOVERED` 事件。

本阶段应选择并固定一种默认策略，建议：

- 对明确可安全重试的模拟任务，恢复为可调度状态。
- 对执行状态不确定、可能已经产生外部副作用的任务，不盲目重放。
- 对无法恢复的任务，以明确错误结束并记录恢复原因。

后续接入模型和 Tool 后，必须按执行阶段和副作用类型重新审查恢复策略。

## 3.11 Task 查询与数据隔离

所有公开 Task 查询都必须检查当前用户的访问范围。

本阶段社区版采用用户所有权隔离：

- 用户只能查询自己拥有的 Task。
- 用户只能读取自己 Task 的事件。
- 用户不能通过猜测 UUID 读取其他用户任务。
- 取消操作必须检查任务所有权。
- 管理员访问其他用户任务的规则必须明确实现，不能因管理员角色存在就自动绕过所有检查。

查询列表应支持分页、状态筛选和合理的时间排序。

事件查询必须支持 `after_seq` 等参数，为后续 SSE 断点续传提供基础。

## 3.12 与六项内核不变量的对应关系

| 内核不变量                                | 本阶段落地内容                                   |
| ----------------------------------------- | ------------------------------------------------ |
| Identity & Session                        | Task 记录所有者，执行上下文预留安全身份传递      |
| Task State Machine & Transaction Boundary | 状态机、合法迁移、事务与 Outbox                  |
| Agent Version Snapshot                    | 保留固定版本引用；完整快照由阶段 3 实现          |
| Audit Event Stream                        | 保留事件和追踪接口；完整审计链由阶段 8 闭环      |
| Permission Enforcement Point              | Task API 执行所有权检查，完整权限裁决后续完善    |
| ModelGateway / SkillGateway               | 本阶段不实现业务网关，只通过执行器接口预留集成点 |

需要明确：阶段 2 不是六项不变量全部完成，而是先完成任务状态机和事务边界，为其他不变量提供可靠基础。

# 4. 接口与数据设计

## 4.1 创建任务接口

```
POST /api/z-torque/tasks
```

请求头：

```
Authorization: Bearer <access_token>
Idempotency-Key: <unique-request-key>
Content-Type: application/json
```

请求体建议：

```
{
  "agent_id": "uuid",
  "agent_version_id": "uuid",
  "input": {
    "text": "执行一个测试任务"
  },
  "timeout_seconds": 300
}
```

约束：

- `owner_user_id` 从认证上下文取得。
- `tenant_id` 从服务端运行上下文取得。
- 幂等键从请求头读取并校验。
- 用户不得自行指定任务所有者。
- 用户不得通过请求参数任意改变任务权限。
- 阶段 2 使用测试版本标识验证内核；阶段 3 完成后，必须校验 Agent 和 AgentVersion 的有效关系。
- 超时时间不能超过系统允许的最大值。

成功响应：

```
{
  "code": 0,
  "message": "ok",
  "data": {
    "task_id": "uuid",
    "status": "PENDING"
  },
  "trace_id": "..."
}
```

对于相同用户和幂等键的重复请求，返回已有任务标识及当前状态，不创建第二个 Task。

HTTP 状态码和响应体必须在正式实现中统一确定；不能让相同幂等请求有时返回新任务、有时重复创建任务。

## 4.2 查询任务详情

```
GET /api/z-torque/tasks/{task_id}
```

返回内容至少包括：

- Task ID。
- 当前状态。
- 所属 Agent 与版本引用。
- 创建时间。
- 开始时间。
- 结束时间。
- 执行耗时。
- 当前运行摘要。
- 最终结果或脱敏错误信息。
- 最新事件序号。

不得返回内部密钥、未脱敏调用参数或不属于当前用户的数据。

## 4.3 查询任务列表

```
GET /api/z-torque/tasks
```

建议支持：

- `page`
- `page_size`
- `status`
- `created_after`
- `created_before`

列表默认按创建时间倒序。

必须在数据库查询阶段限制用户范围，而不是先查询所有任务后在 Python 内存中过滤。

分页大小必须设置上限，防止一次请求读取大量数据。

## 4.4 查询任务事件

```
GET /api/z-torque/tasks/{task_id}/events?after_seq=0&limit=100
```

响应包含：

- 任务 ID。
- 事件列表。
- 每条事件的序号。
- 事件类型。
- 时间。
- 摘要。
- 下一次查询可使用的序号。

必须验证用户是否有权读取该 Task。

此接口是事件查询 API，不等同于 SSE 实时流接口。后续阶段可以复用相同的事件数据结构。

## 4.5 取消任务

```
POST /api/z-torque/tasks/{task_id}/cancel
```

请求体可为空，取消原因可以作为可选字段，但不得允许用户传入任意目标状态。

服务端根据当前状态决定：

- 是否直接取消。
- 是否请求执行器协作取消。
- 是否已经处于终态。
- 是否返回冲突状态。

重复提交取消请求应幂等处理。

## 4.6 内部执行器接口

执行器不通过公开 HTTP API 调用。

内部接口至少需要表达：

- Task 执行上下文。
- 执行截止时间。
- 取消信号。
- 结构化执行结果。
- 可恢复或不可恢复的错误信息。

模拟执行器必须可控制：

- 成功。
- 失败。
- 延迟。
- 超时。
- 取消。
- 执行过程中进程重启的测试情景。

模拟执行器只用于验证运行内核，不应成为生产任务的默认业务执行逻辑。

## 4.7 数据迁移

本阶段新增至少三张表：

- `zr_task`
- `zr_task_event`
- `zr_outbox`

迁移必须保证：

- 外键约束正确。
- 唯一约束正确。
- 查询索引完整。
- 事件序号唯一。
- 幂等键约束正确。
- 状态字段使用明确枚举或受控字符串。
- 终态和运行时间字段能够正确持久化。

由于 Agent、Conversation 和 Message 的完整模型由后续阶段建立，相关外键需要按阶段顺序补齐。任何临时引用都必须在阶段 3 的迁移中完成正式关联，不得成为永久的数据完整性缺口。

# 6. 测试验收

## 6.1 状态机测试

必须验证：

- 

  `PENDING → QUEUED` 合法。

- 

  `QUEUED → RUNNING` 合法。

- 

  `RUNNING → SUCCESS` 合法。

- 

  `RUNNING → FAILED` 合法。

- 

  `RUNNING → TIMEOUT` 合法。

- 

  `RUNNING → WAITING_HUMAN` 合法。

- 

  `RUNNING → CANCEL_REQUESTED` 合法。

- 

  `PENDING → CANCELLED` 合法。

- 

  `QUEUED → CANCELLED` 合法。

- 

  `WAITING_HUMAN → QUEUED` 合法。

- 

  `WAITING_HUMAN → CANCELLED` 合法。

- 

  终态不能迁移回运行态。

- 

  不允许的状态迁移返回明确错误。

- 

  状态更新失败时不会写入虚假的状态事件。

## 6.2 事务一致性测试

必须验证：

- 

  Task、初始 TaskEvent、Outbox 在同一事务内创建。

- 

  任意一步失败时事务整体回滚。

- 

  不存在已提交 Task 但缺少初始 Outbox 的情况。

- 

  不存在已提交 Task 但缺少初始事件的情况。

- 

  状态更新和对应 TaskEvent 保持一致。

- 

  并发状态更新不会相互覆盖。

- 

  事件序号不会重复。

## 6.3 幂等测试

必须验证：

- 

  相同幂等键重复提交不会创建第二个 Task。

- 

  并发重复提交仍然只创建一个 Task。

- 

  相同幂等键对应不同请求内容时，服务端按确定规则处理，不得静默复用错误任务。

- 

  同一个 Outbox 被重复扫描时不会导致任务并行执行。

- 

  多个 Worker 同时领取同一个 Task 时，只有一个能够成功认领。

- 

  终态 Task 不会被重新执行。

建议为幂等键同时保存请求摘要，重复请求时比较摘要。若同一幂等键对应不同请求，应返回明确冲突错误，而不是返回内容不匹配的旧任务。

## 6.4 Worker 测试

必须验证：

- 

  模拟任务能够成功执行。

- 

  模拟任务失败后能生成正确错误码。

- 

  并发执行数量不会超过配置上限。

- 

  Worker 异常不会导致 Task 永久处于 `RUNNING`。

- 

  执行结束后能正确释放资源。

- 

  不同任务的结果不会互相覆盖。

- 

  Worker 不会执行已经取消或已经终止的任务。

## 6.5 取消测试

必须验证：

- 

  待执行任务可以取消。

- 

  已排队任务可以取消。

- 

  运行中任务进入取消请求状态。

- 

  模拟执行器收到取消信号。

- 

  执行器确认停止后任务进入 `CANCELLED`。

- 

  终态任务不会因取消请求而改变。

- 

  重复取消请求不会产生重复执行副作用。

- 

  无法立即停止的执行器不会被错误标记为已经停止。

## 6.6 超时测试

必须验证：

- 

  未超过截止时间的任务可以正常完成。

- 

  超过截止时间的任务会触发超时处理。

- 

  超时后记录 `AI_TASK_TIMEOUT`。

- 

  超时状态变化有对应事件。

- 

  超时任务不会被普通调度重新执行。

- 

  超时后的外部执行状态不确定时，系统不会错误声称副作用已经停止。

## 6.7 恢复测试

必须模拟至少以下情景：

1. Task 创建事务提交前进程异常。
2. Task 已创建，但 Outbox 尚未投递。
3. Outbox 已投递，但 Worker 尚未开始。
4. Task 处于 `QUEUED` 时进程重启。
5. Task 处于 `RUNNING` 时进程重启。
6. Outbox 多次投递失败。
7. Worker 执行时发生异常。
8. 任务取消过程中进程重启。

必须验证：

- 

  待处理 Outbox 能被重新扫描。

- 

  已排队任务可以重新调度。

- 

  已终止任务不会被重新执行。

- 

  无法恢复的任务能以明确状态结束。

- 

  恢复过程有 TaskEvent 记录。

- 

  恢复不会破坏事件序号。

- 

  恢复不会绕过幂等检查。

## 6.8 API 与隔离测试

必须验证：

- 

  未登录用户不能创建任务。

- 

  用户只能查询有权访问的任务。

- 

  用户不能读取其他用户的任务事件。

- 

  用户不能取消其他用户的任务。

- 

  分页参数具有合理范围。

- 

  任务不存在时返回统一错误。

- 

  非法状态和非法输入得到统一错误响应。

- 

  API 不泄露原始异常、秘密参数或其他用户的数据。

## 6.9 阶段验收门槛

出现以下任一问题，本阶段不得通过验收：

- Task 状态可以被任意修改。
- 终态可以回退。
- Task 创建和 Outbox 写入不具备事务一致性。
- 重复请求能够创建重复任务。
- 多 Worker 能并行执行同一个 Task。
- 进程重启后任务状态无法恢复或解释。
- TaskEvent 序号冲突。
- 取消请求被直接当作停止成功。
- 用户可以读取或取消其他用户的任务。
- 自动化测试只验证正常路径，没有覆盖并发和异常路径。

# 7. 风险项

## 7.1 将内存队列误认为可靠消息队列

**风险：** 任务只进入 `asyncio.Queue`，进程重启后消息丢失。

**应对：**

- 数据库始终作为运行状态依据。
- Outbox 保留未完成投递记录。
- 启动恢复时重新扫描。
- 队列丢失不能导致任务永久丢失。

## 7.2 状态更新与事件记录分离

**风险：** Task 显示成功，但没有成功事件；或事件显示成功，Task 实际仍在运行。

**应对：**

- 状态更新与事件写入使用同一事务。
- 所有状态迁移经过统一服务。
- 禁止其他模块直接写状态字段。

## 7.3 Outbox 重试造成重复执行

**风险：** Scheduler 因超时或进程异常重复投递同一个任务。

**应对：**

- Outbox 投递具备幂等性。
- Worker 必须再次校验任务状态。
- 数据库条件更新负责最终认领。
- 外部副作用在未来 Skill/Tool 层单独设计幂等策略。

## 7.4 任务取消不彻底

**风险：** API 返回取消成功，但外部模型或工具仍在执行。

**应对：**

- 区分取消请求和取消完成。
- 使用 `CANCEL_REQUESTED` 表达中间状态。
- 为执行器建立协作式取消接口。
- 不可取消的外部调用必须明确其限制。

## 7.5 RUNNING 任务恢复后重复执行

**风险：** 进程重启时无法判断外部操作是否已经产生副作用，直接重新执行可能造成重复操作。

**应对：**

- 恢复策略区分安全重试和状态不确定。
- 不把所有运行中任务一律重新执行。
- 未来 Tool 层必须声明副作用与幂等能力。
- 对高风险外部写操作采取确认与状态核验策略。

## 7.6 事件表无限增长

**风险：** TaskEvent 长期累积，导致数据库不断膨胀。

**应对：**

- 阶段 2 不直接删除历史事件。
- 为查询建立必要索引。
- 后续结合审计保留策略、任务归档与数据清理策略统一设计。
- 删除任务前必须检查历史引用和保留要求。

## 7.7 SQLite 写竞争

**风险：** Outbox Scheduler、Worker 和 API 同时写数据库时出现锁竞争。

**应对：**

- 缩短事务。
- 不在事务中等待模型或外部服务。
- 合理配置数据库超时。
- 对可重试的数据库竞争进行受控重试。
- 用并发测试验证实际行为。

# 9. 阶段总结

## 9.1 阶段 2 的核心成果

阶段 2 完成后，Z-Torque 应具备可靠的任务执行基础：

- Task 有明确的生命周期。
- 所有状态变化经过统一校验。
- Task、TaskEvent 和 Outbox 保持事务一致性。
- 请求重试不会重复创建任务。
- Worker 能通过状态保护避免重复执行。
- 任务可以取消、超时并记录结果。
- 进程重启后能够恢复或明确终止未完成任务。
- 任务执行过程可以通过事件查询追踪。
- 后续模型、Skill 和 Agent 执行流程可以接入统一执行器。

## 9.2 本阶段仍然没有完成的能力

即使阶段 2 全部验收通过，也不能宣称以下功能已经完成：

- Agent 创建、复制、发布与版本管理。
- AgentVersion 完整不可变快照。
- Skill 与 Tool 关系管理。
- ModelGateway。
- SkillGateway。
- Function Calling 多轮循环。
- 完整 Chat API 和 SSE 对话流。
- MCP 连接与执行。
- MD-Skill 运行。
- 完整权限裁决与审计闭环。
- 最终控制台。

## 9.3 进入阶段 3 的前置条件

只有以下条件全部满足，才能进入阶段 3：

1. Task 状态机测试全部通过。
2. Task、TaskEvent 和 Outbox 事务一致性得到验证。
3. 幂等与并发领取测试通过。
4. 取消和超时流程可重复验证。
5. 进程重启恢复测试通过。
6. 任务所有权隔离测试通过。

8. README 和阶段验收报告完整。
